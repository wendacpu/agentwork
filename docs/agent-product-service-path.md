## 1. 项目背景与问题

### 1.1 业务痛点（早期问题假设，需按当前业务复核）

短视频平台的推荐文案（标题）有三个互相冲突的约束：

1. **要有吸引力**——决定点击；
2. **不能失真**——不能把转述写成事实、把观点写成结论、把局部写成完整；
3. **要短**——竖屏信息流里通常 20 字以内。

早期问题假设：人工写作难规模化，端到端生成出错时不易归因；这些判断需结合目标业务流程验证。

### 1.2 早期方案比较（不是当前行业现状审计）

| 做法 | 缺陷 |
|---|---|
| 人工写 | 一致率低、不可规模化、经验无法沉淀 |
| 端到端生成模型 | 输出不可审计；无法定位"是理解错了还是表达错了" |
| 规则 + 模板填空 | 覆盖不了语义判断（"这句话算不算被支持"）；表达僵硬 |
| 单纯加 Prompt 约束 | 约束是软性的，模型可以遵守也可以不遵守，且没有独立复核 |

### 1.3 可量化目标

**线上业务指标**：CTR、完播率、举报率、审核驳回率；本文形成时未采集这些指标，当前可得性需重新确认。

2026-10-31 的历史快照记录 `gold.csv` 有 14 行 / 6 个视频（2 行 mock、12 行真实人工判定）；真实判定为可用 0、勉强通过 2、不可用 10。当前样本以重新读取 CSV 为准。

**离线指标定义与历史数值（详见第 9 节；不代表当前表现）**：

| 指标 | 定义 | 目标线 | 现状 |
|---|---|---|---|
| 一次通过率 | 同一视频至少 1 条候选被人工判"可用"的比例 | 待金标准确定 | 历史快照记录 1 个视频；当前须重算 |
| 人工一致率 | 系统推荐的候选与人工实际选择一致的比例 | ≥ 80%（历史暂定目标，未校准） | 截至 2026-10-31 盘点为 0 条可比；当前须重新统计 |
| 长度合格率 | 候选 ≤ 20 字的比例 | ≥ 90%（历史目标，未复核） | 历史记录含 9 候选 100% 与更早 19% 超长；口径不同，当前须重算 |
| G1 漏拦率 | 人工判"事实有问题"但系统 G1=pass 的比例 | ≤ 10%（暂定） | 历史单条对照曾记录 100%；当前须重测 |
| 结构校验通过率 | 模型输出通过 schema + 引用白名单的比例 | 100% | 历史记录为 29 个单测覆盖；当前以测试结果为准 |

目标线均为待金标准验证的暂定值，**不是已达成值**。

### 1.4 本版定位

这是一个 **(a) 能证明"规则约束 + 独立评审"是否有效的离线实验**，不是 **(b) 可交付业务使用的系统**。

这是文档形成时的定位与验收判据，不代表当前产品范围或人工数据；线上接入、反馈情况和闭环样本须重新盘点。

## 2. 产品设计

### 2.1 服务路径（纵向五层；历史设计图，以现行实现为准）

参考图 `_ref/懂车帝复杂 agent 产品.md` 是横向按业务环节切（准入→尽调→审查→审批→放款）。本项目**不横向切**，因为那条链路 30 秒内跑完，没有岗位/时间边界，硬切是"为切而切"。

改按**纵向分层 + 责任域分块**：

```
L1 输入层    视频素材（mp4）｜ASR ｜OCR ｜抽帧 ｜主表字段（领域/形态/时长/画幅）
                │
L2 横切编排   规则包 U/V/F ｜业务政策 P1–P3 ｜G4 机械校验 ｜Q01 程序裁决
                │（跨域，不属于任何 Agent；Q01 是唯一总决策者）
                ▼
L3 Agent 域   ┌── A 理解域 ──┐ ┌── B 表达域 ──┐ ┌── C 裁决域 ──┐
              │ N03→N04→N05  │ │ N07→N08→N09  │ │     R01      │
              │ →N06         │ │ →N10→N11     │ │              │
              └──────────────┘ └──────────────┘ └──────────────┘
                │ 输出 BoundarySet │ 输出 Candidate[≤3] │ 输出 ReviewGate+issues
                ▼
L4 人工层     H01 人工确认（采用 / 驳回 / 人工重写）→ case 固化
                │
L5 数据资产   判据库(C01–C21)｜金标准(gold)｜bad case 库｜规则包｜事件日志｜案例库
                └──── 回流箭头：改规则 / 改 Prompt / 改判据 → 回到 L2、L3 ────┘
```

**早期方案与原参考图的差异（非当前实现审计）**：
1. 它把"规则/编排"画成中间一层但每个 Agent 内部也带规则；本项目把机械校验和程序裁决**上提到横切层**，保证"评审不判自己"。
2. 它有 5 个人工确认闸门；本项目只有 1 个（H01），所以只画 1 个，不虚增。
3. 它有从左到右的单向流程；本项目多一条回环（L5→L2/L3），这是"越用越好"的实体。

### 2.2 三个 Agent 域

早期设计提出按失败方式、指标与修复手段划分责任域；该切分仍应按当前代码与产品目标验证：

| 域（设计映射） | 节点 | 回答的问题 | 输入契约 | 输出契约 | 关注的失败方式 | 参考指标 | 相关实现 |
|---|---|---|---|---|---|---|---|
| **A 理解** | N03→N04→N05→N06 | 这条视频里**有什么能写** | `VideoInput` + `Evidence[]` | `BoundarySet`（claims + usable/limited/excluded + 限定 + 核验任务） | 判错 / 漏拦 | G1 漏拦率、claim 引用合法率 | `rulepacks/common.md` U 条 |
| **B 表达** | N07→N08→N09→N10→N11 | **怎么写** | `BoundarySet` + `HighlightSet` + 规则切片 | `Candidate[≤3]` + 机械检查结果 | 写超 / 丢限定 / 主看点错 | 长度合格率、一次通过率 | `prompts.py`、策略枚举、看点选择 |
| **C 裁决** | R01 | **写得行不行** | 候选 + 原始材料 + 边界 + 规则切片 + 机械结果 | `ReviewGate`(G1–G3) + Q1–Q3 + `issues` + 改写指导 | 放水 / 过严 | 人工一致率 | `criteria.csv`、rubric |

**早期设计决定：表达域不拆成“看点 / 生成”两个包。** 当时认为两者共享边界与指标；这是设计理由记录，不是当前结构审计结论。

**早期设计理由：裁决域不含 Q01。** 当时将 Gate 聚合与路由视为横切编排层，以避免评审与最终裁决混为一体；当前分层以代码为准。

### 2.3 核实策略分级表（当前设计仍待按业务口径复核）

这是一个仍需业务确认的策略点，也关联决策点 D11。外部事实核查 N03V 已接入，配置默认关闭；目前资讯域可路由，未证明其他领域的核查效果。

`attribution_required`（标题是否必须写来源）和 `verification_required`（是否暂缓核验）是不同决策：前者要求标题保留归属，后者阻止未解决事实进入可写集合。娱乐、剧情、表演类不应机械套用资讯类的核实方式；具体要求仍需按内容形态与领域确定。

截至 2026-10-31，资讯域路由与可选 N03V 已接入，但默认关闭；领域策略覆盖及真实批量效果未验证。这里的建议矩阵是待业务确认的设计，不等同于已实施或已校准的策略。

**推荐按「内容形态 × 内容领域」查表，而不是让模型逐条自由判**：

| 形态 | 领域 | 核实要求 | 理由 |
|---|---|---|---|
| F11 资讯播报 | 资讯（时事社会/财经/科技等） | **强制**：必须可识别信源，冲突须暂缓核验 | 涉及真实事件与他人名誉 |
| F02 讲解分享 | 知识科普 / 健康运动 | **强制**：事实类陈述须归属或限定，观点须标注 | 易被当成专业结论 |
| F03 测评试用 / F05 探店 | 消费相关 | **条件**：涉及数据/对比须归属 | 有商业误导风险 |
| F09 剧情短片 / F08 表演展示 | 泛娱乐 / 生活记录 | **豁免**：不要求归属；只需标注虚构/演绎属性 | 不涉及真实事件核实 |
| F06 成果展示 / F07 现场记录 | 美食 / 生活 / 宠物等 | **豁免**：只约束"画面可见"与"不得推断" | 无信源概念 |
| 任意 | 任意 | 若 claim_type=opinion/prediction | **条件**：须保留归属或标注为主观 | 与形态无关 |

落地方式：`rulepacks/common.md` 增加一条 `U-S08 核实要求按形态分级`，N05 Prompt 引用该表；程序侧对"豁免类却被要求归属"给出 warning（可观察，不阻断）。

**这不是"让模型少做事"，是把一个不该由模型做的元决策收回到规则层。** 详见 4.4。

## 2.5 前缀标注位（2026-10-31 新增）

`agent_system/labels.py` 负责标题呈现标签，不让模型自由拼写：程序按内容形态和属性计算受控枚举（当前为「剧情演绎」「AI生成」），并把标签与正文分开存储。展示时渲染完整标题；长度限制作用于完整串，前缀**计入** `max_chars`，正文预算由 `body_budget()` 扣除前缀长度。模型自报的非受控标签会被丢弃。

当时提出的产品约束是：若前缀压缩正文预算，不应截断标签或豁免字数。具体现行行为与回归测试以 `agent_system/labels.py` 和相关测试为准。

## 3. 模块说明（设计与实现映射；状态须结合代码核验）

每个模块按参考图的五元组写：**组件构成、输入、输出、判据依据、失败模式与兜底、指标**。

### 3.1 A 理解域 Agent

**设计职责**：整理可写事实及其限定，供下游生成使用；具体字段与执行路径应以当前实现为准。

| 组件 | 做什么 | 谁判 | 输出字段 |
|---|---|---|---|
| 材料装配 | 合并 ASR/OCR/画面/标题，去重，保留定位 | 代码 | `Evidence[]`（含 quality 标注） |
| 事实抽取 | 从材料里抽出 0–N 条原子陈述，标注类型/时态/断言权限/传播链 | 模型 S1 | `Claim[]` |
| 外部核查（可选 N03V） | 按配置与领域筛选可核查断言，汇总 supported/refuted/unverifiable 与风险；高风险转人工 | 代码 + 核查器 | 核查记录、风险摘要 |
| 规则切片 | 按领域+形态+属性选 U/V/F 规则 | 代码 | `RuleBundle`（含 match_trace/gaps） |
| 边界判定 | 逐条判 usable/limited/excluded，写必要限定、禁止推断、核验标记，并应用已证伪事实约束 | 模型 + 程序 | `BoundarySet` |
| 可写路由 | 高风险核查先转人工；无可用信息时停止或交人工核验 | 代码 | 任务状态 |

**输入**：`VideoInput`（`title / asr_segments / ocr_segments / evidence / domain / format`）+ `RuleBundle`
**输出**：`BoundarySet`（`decisions[]` 含 `claim_type / evidence_status / temporal_status / assertion_permission / required_limits / forbidden_inferences / attribution_required / verification_required`）

**判据依据**：通用规则与本次匹配规则切片；外部核查约束仅在 N03V 启用且有结果时生效

**失败模式** | **兜底**
--- | ---
漏抽事实（该写的没抽） | 早期分析认为缺少直接兜底；当前检测能力需按现行实现复核
编造事实（不在 evidence 里） | `evidence_refs` 白名单程序校验，非法 ID 直接判错
把历史写成当前 | 程序 `programmatic_g1_flags` + R01 复核 + 人工
核查误报或无结果 | 记录 supported/refuted/unverifiable；高风险转人工，未解决事实由边界判定继续限制
领域规则缺口（历史盘点约 38% 覆盖） | 记 `gaps` 继续，不静默；当前覆盖率需重跑统计

**早期指标记录**：G1 漏拦率未测；claim 引用合法率曾记录为单测 100%；领域规则覆盖率曾记录为 38%。上述数值均需按当前代码和样本重测。

### 3.2 B 表达域 Agent

**设计职责**：在边界允许的范围内选看点与策略并生成候选；数量和长度约束以当前配置及代码为准。

| 组件 | 做什么 | 谁判 | 输出字段 |
|---|---|---|---|
| 看点选择 | 选 1 主 + ≤2 备，写代表性依据与淘汰原因 | 模型 S1/S2 | `HighlightSet`（含 `eliminated[]`） |
| 上下文装配 | 拼装 看点+边界+规则切片+案例+策略枚举+字数限制 | 代码 | 生成入参 dict |
| 案例检索 | 按 issue_code/标题查历史案例（最多 6 次） | 代码触发 | `memory_cases`、`memory_trace` |
| 候选生成 | 产出标题 + 引用的 claim/highlight/evidence + 策略 + 限定表达 | 模型 S1 | `AgentDraft` |
| 机械校验 | 长度 / 问号结尾 / 引用白名单 / 策略与材料不符 | 代码 S0 | 错误码列表 |
| 交付路由 | 按 Gate 与 Q 分聚合出 handoff/needs_review/rewrite/reject | 代码 S0 | `route` |

**输入**：`BoundarySet` + `HighlightSet` + 规则切片 + 案例

## 4. 决策登记与自主度审计

### 4.1 为什么需要这套分级

行业里"Agent"一词最常见的误用是把**调用模型**说成**自主**。两者差别决定了一个系统能否被信任：

- 调用模型 = 在固定的执行路径上，某个位置替换成模型生成 → 行为可预测、可测试、可审计；
- 自主调度 = 模型自己决定下一个动作 → 行为空间不由代码定义，需要更强的护栏与更严的验收。

本节用档位区分模型调用与自主调度；下表是 2026-10-31 对当时登记决策点的分类，不作为当前逐项审计。

### 4.2 四级定义

| 级别 | 名称 | 判据 | 可测试性 |
|---|---|---|---|
| **S0** | 确定性 | 能写成 if-else，输入相同则输出必相同 | 单测 |
| **S1** | 生成 | 模型产出内容/判断，但**动作由代码固定**（一次调用、无后续动作选择） | 固定输入回归 |
| **S2** | 枚举内选择 | 从代码/rubric 定义的有限集合里选一个 | 选项覆盖测试 |
| **S3** | 自主调度 | 模型自己决定要不要调工具、调什么、调几次、走哪个分支 | 需要轨迹级验收 |

### 4.3 截至 2026-10-31 登记决策点的档位（历史分类）

| ID | 决策点 | 登记为 | **核验后实际** | 依据 |
|---|---|---|---|---|
| D01 | 抽哪些事实 | 模型 | S1 | 一次调用产出 claims，动作固定 |
| D02 | 能否写/带什么限定 | 模型 | S1 | 三档状态由语义定，无动作选择 |
| D03 | 选哪个主看点 | 模型 | **S1** | 看点是同一节点产出（含 eliminated），不是从外部集合里选 |
| D04 | 要不要检索/用什么词 | 模型（原记"唯一自主"） | **S1，且为伪自主** | 见 4.4 |
| D05 | 用哪个表达策略 | 模型 | **S2** | `STRATEGY_ENUM` 5 个写死 |
| D06 | 机械约束 | 程序 | S0 | 长度/格式/引用纯计算 |

### 5.3 判定口径（2026-10-30 业务方确认的历史记录）

#### 长度：≤20 字符，无豁免

截至 2026-10-30 的历史口径记录为：NFC 后 Unicode 码点数 ≤ 20，归属前缀计入、不扣减且不设 24 字放宽。该规则在当前代码/配置中的实际执行仍须核对。

当时的策略提案是把“是否带归属”与“长度限制”分开处理，并建议在冲突时优先保证长度与可理解性。具体规则及代码执行状态请以现行规则包、Rubric 和测试为准。

#### 三档判定词的含义

`criteria.csv` 的「判定结果」列是给人看的统一口径（代码不读这一列，代码读 Gate 状态与 Q 分）。三档对应的代码路径不同：

| 口径词 | 含义 | 代码怎么落地 | 后果 |
|---|---|---|---|
| **不可用** | 这条不能上线 | Gate fail，或某维 Q < `quality_min_each`(2) | → **重写**；只有命中已批准 policy 的 rule_id 才 `reject` |
| **待人工** | 系统不敢判死、也不敢放行 | **仅** Gate = `needs_review`（G1 未解冲突 / G2 未配政策 / schema 非法） | → 进人工队列，不给推荐 |
| **排序靠后** | 可用，但不该排第一 | Q 分刚好 = 2（不低于阈值） | → 可 handoff，按 Q 分和排名靠后 |

**注意：Q1/Q2/Q3 类判据没有「待人工」通道**——代码里 Q 分低只通往 `rewrite`，只有 Gate 级（G1/G2/G3）才有 `needs_review`。所以判据表填「待人工」只对 G 类有效；Q 类填了是悬空的。这条限制在扩展判据时要记住。

#### C14 / C15 定案

| 判据 | 归属 | 判定结果 | 落地方式 | 业务方理由 |
|---|---|---|---|---|
| C14 指代不清 | Q1 | **不可用** | Q1 分 < 2 → 重写；改到能指代清楚，重写耗尽才停 | 人工一定不通过 |
| C15 空泛无信息 | Q2 | **排序靠后** | Q2 恰好 2 分 → 可 handoff，排名靠后 | 视情况勉强通过 |

C14 的处置是"重写"而非"直接毙"，因为"指代不清"是可修的表达问题（换成主体名即可）；重写两轮仍不清才停止，此时候选仍进人工队列。
