# Bad Case 定义与治理规范

> 版本 v0.8 · 2026-11 · 配套 [agent-product-service-path.md](agent-product-service-path.md) / [nodes.md](nodes.md) / [templates/bad_cases.csv](../templates/bad_cases.csv)
> 变更：v0.8 按你确认的「三种判定」修正案例库规则（可用=正例、勉强=反例+正例、不可用=反例）；v0.7 定档按离线阶段校准；v0.6 21 列表；v0.5 渠道二脚本；v0.4 案例库三件。
> 一句话结论：**Bad Case 分级不看「哪个模块错了」，只看「错误造成了什么后果、流出到了哪一层」。** 本文把 bad case 从「按环节记流水账」升级为「按后果分级、按等级投资源、按渠道回收、按闭环修复」，并回答「case 库 / Memory 到底什么时候该被 Agent 调用」。

---

## 0. 为什么现有定义不够用

现有 [bad_cases.csv](../templates/bad_cases.csv) 有 3 条，列结构是「现象 / 出错环节 / 错误类型 / 严重度 / 归因决策点 / 回退节点 / 修复手段…」。它有三个结构性问题：

1. **「出错环节」用「感知 / 规划 / 执行 / 经验」**——这是按认知模块分，不是按后果分。同一个模块的错误后果可以天差地别（N05 边界判错了但被人工拦下 vs N05 判错了直接发布），而「感知错误」该多快修，从这列里答不出来。
2. **「严重度」拍脑袋，且与后果脱节**。BC02「重写耗尽」、BC03「超长」被标成 P0，但它们根本没流出——一条停在人工队列，一条被 G4 机械校验拦下。真正的 P0 是「错误被执行 / 发布」，这三条里没有一条够格。P0 被稀释，真事故会被淹没。
3. **没有「流出层级」字段**，于是「被拦截的错误」和「流出的错误」被混记。拦截量大不丢人，说明防线在工作；穿透才是事故。两者不分级，就没有办法区分「该马上修」和「该攒着看趋势」。

模块只是 bad case 的**归因维度**，不是**分级维度**。分级维度永远是后果。

## 1. Bad Case 的定义（针对本产品）

本产品（短视频推荐文案 / 标题生成 Agent）的核心契约是：

> 正常用户只看标题、不看视频时形成的内容预期，应当能被视频实际内容兑现。

**Bad Case 的定义**：一条输出（候选标题或它依赖的上游结果）一旦偏离「可兑现 / 合政策 / 可交付」三条底线，无论它被哪一层拦下，都是 bad case。

**先把系统边界说清楚**：当前系统是**离线实验 + 人工批量标注**，不接推荐、不把标题推给用户。所以「标题事实错 / 政策违规」这类风险是真实存在的（内容本身错），但目前是在**人工标注环节**被拦下，不会真的触达用户。下面的分级据此校准：L3/L4 当前不可达，P0 是预留档。

展开说，它有三个等价描述，对应三种后果：

| 底线 | 违背时叫什么 | 后果 | 影响 |
|---|---|---|---|
| 可兑现 | 标题背叛视频（把转述写成事实、把局部写成完整、把旧事写成当前、把观点写成结论） | 误导用户 → 客诉 / 举报 / 舆情 | 高 |
| 合政策 | 标题违反业务政策（低俗性暗示 / 暴力猎奇 / 营销导流） | 平台处罚 / 下线 | 高 |
| 可交付 | 标题质量不达（空泛、读不懂、主看点错、必要限定丢失、超长） | 返工 / 点击低 / 人工多改几笔 | 中 / 低 |

**为什么它算 bad case**，不看它发生在哪个模块（理解 / 边界 / 看点 / 生成 / 评审），而看它**造成了什么后果、停在了哪一层**。一条被 C22 一手证据守卫拦下的编造情节，和一条被人工驳回的编造情节，是同一个错误类型，但后果完全不同——前者防线在工作（P2），后者穿透了自动防线（P1）。

## 2. 你说的两类（源头错 / 传导错）是归因维度，不是分级维度

你直觉上把 bad case 分两类，方向是对的，但它们是**归因维度**（回答「改哪里」），不是**分级维度**（回答「多严重」）：

| 大类 | 归因到哪个域 | 对应节点 | 典型表现 |
|---|---|---|---|
| 第一类：源头错（视频解析结果就错） | A 理解域 | N03 理解 / N05 边界 / N03V 核查 | 漏抽事实、编造事实、把历史写成当前、边界把「不该写」判成「可写」、核查漏报 |
| 第二类：传导错（中间流程偏离） | B 表达域 / C 裁决域 | N07 看点 / N09 生成 / R02 重写 / R01 评审 | 主看点选错、丢限定、策略与材料不符、评审放水 / 过严 |

这两类最终都落到同一个动作上：**回退到出错的节点去修**（`rollback_to` 字段，N05 / N07 / N09 / R01）。所以它们在记录里是一个字段，不是等级。

## 3. 分级框架：两轴取交

> **先对齐系统所处阶段（这决定哪几层是真实可达的）**：当前系统是**离线实验 + 人工批量标注**，不接推荐、不把标题推给用户。所以防线链实际只有 **L1（自动防线）** 和 **L2（人工标注）** 两层；**L3（触达业务）/ L4（实际损失）当前不可达**，只是「假设接入推荐之后」才存在。四层定义都保留，但**定档以当前可达层为准**：当前最重的一档是 **P1**（高影响 × 被人工标注拦下），**P0 是预留档**，等接入推荐再说。

### 轴一：错误流出到了哪一层（Exposure）

本产品天然存在一条防线链。错误停在越靠前的层越轻，穿透到越靠后的层越重：

| 层 | 防线 | 本产品的具体形态 |
|---|---|---|
| **L1 自动防线** | 被校验 / 规则 / 熔断挡住 | G4 机械校验（长度 / 问号结尾 / 引用白名单 / 策略不符）；C22 一手证据守卫（claim 必须命中 ASR/OCR/原题）；`programmatic_g1_flags`（历史写成当前等程序化事实标志）；G2 政策 `reject/rewrite/review`；schema 校验 + 结构重试；输入质量闸 `assess_material`；N03V 核查 `refuted` 强制排除 |
| **L2 人工拦截** | 穿过自动防线，被人拦下 | H01 人工三档判定（`rejected` / `marginal`）；`needs_review`（系统不给推荐、交人） |
| **L3 触达业务** | 穿过所有防线，进入执行 / 触达 | **当前不可达**（离线实验，不接推荐、不推用户）；仅「假设接入推荐」后才存在 |
| **L4 实际损失** | 不仅流出，还造成损失 | **当前不可达**；接入推荐后才可能是客诉、举报、平台处罚、舆情 |

> 关键认知：**「被拦截的错误」和「流出的错误」是两个等级的东西。** 拦截量大不丢人；穿透才是事故。

### 轴二：错误如果流出，后果的严重度（Impact）

| 档 | 本产品的具体形态 |
|---|---|
| **高** | 事实错误（编造 / 可核实断言被证伪）、政策违规、信源权威性造假、不可逆舆情 |
| **中** | 主看点错、必要限定丢失、业务效果受损（返工） |
| **低** | 表达瑕疵、空泛无信息、人工需要多改几笔、非关键环节技术故障 |

### 分级 = 两轴取交

| 等级 | 定义 | 典型情况 | 当前阶段（离线实验） |
|---|---|---|---|
| **P0** | 高影响 × 穿透全部防线（L3/L4 × 高） | 错误被执行 / 发布，造成或可能造成事实误导、政策违规、舆情 | ❌ **不可达**（不接推荐、不推用户）；预留到上线后 |
| **P1** | 高影响 × 被人工拦住（L2 × 高），**或**高风险环节系统性失效 | 防线存在漏洞但事故尚未发生（如 G1 事实漏拦、评审系统性过严 / 放水） | ✅ **当前最高档** |
| **P2** | 错误被自动防线正常拦截（L1 × 高/中） | 防线在工作，但反映上游质量问题（如规则冲突、生成超长被 G4 拦） | ✅ |
| **P3** | 低影响错误 | 内容修改比例高、误报被忽略、非关键环节故障 | ✅ |

**两条补充规则**：

1. **同一个错误类型可以落在不同等级，取决于这次它停在哪一层**——所以 bad case 记录里必须有「流出层级」字段。
2. **可用性故障和质量错误分开**。「Agent 没响应 / 超时」是可用性问题，按它所在环节的风险等级定级（高风险环节的熔断 = P1，非关键环节 = P3），不要一律塞进 P0。

## 4. 每个等级配三样东西

只贴 P0/P1/P2 标签没有意义，分级的目的是驱动不同的资源投入。每级定义三样：**响应方式 / 响应时限 / 回收阈值**。

| 等级 | 响应方式 | 响应时限 | 回收阈值 |
|---|---|---|---|
| **P0** | 一例即触发、逐例复盘。**第一动作是止损，不是修复**：先回滚 / 下线 / 转人工，再谈根因 | 立即止损；24h 内给出根因和修复方案 | 1 次即记录 |
| **P1** | 逐例记录 + 短周期归因，修复防线漏洞 | 24–72h 修复防线漏洞 | 1 次即记录 |
| **P2** | 批量统计、观察趋势 | 按周复盘 | 连续 N 次 / 比例 |
| **P3** | 批量统计、观察分布 | 双周 / 月度调优 | 按次数 / 比例 |

**背后的原则**：等级越高，越「逐例处理、零阈值」；等级越低，越「攒批量、看分布」。常犯的错是给所有 bad case 设同一个回收阈值（比如「连续 3 次才记录」）——阈值必须跟着等级走，P0 场景一次就要进案。

**当前阶段先只用 P1–P3**：离线阶段最重的一档是 P1——人工标注判了「不可用」且属高风险的事实 / 政策问题，就按 P1 逐例记录、短周期修复。P0 的「止损」动作（下线 / 回滚 / 转人工）是为接入推荐后准备的，现在没有「线上内容」可止损。

## 6. Bad Case 从哪里来（回收渠道）

### 渠道一：人工主动反馈（本产品已实现一半）

**载体**：调试台（`python -m agent_system.cli debug`，本机 8765）+ H01 人工三档判定。

**怎么来的**——每一个判定动作都是回收点：

| 人工动作 | 留下什么痕迹 | 落哪里 |
|---|---|---|
| 判「不可用」 | 必选驳回原因（事实错误 / 关键背景缺失 / 没写到核心看点 / 句子不完整 / 用词读不懂 / 其他）+ 一句理由 | `gold.csv` + `cases` 表（`_auto_case` 落 `confirmed` 反例）+ `labels` 表 |
| 判「勉强通过」 | 必写瑕疵说明 | 同上（落 `confirmed` 反例） |
| 判「可用」但改了终稿 | `final_headline` 与 `headline` 的 diff | `gold.csv` + `cases` 表（落 `confirmed` 正例） |

**现状与缺口**：入库这一环其实已经通了（判定即落 `cases` 表，自动沉淀 `confirmed` 正例 / 反例）。但还有三处没串起来：
- `case` CLI 已经支持 `rule / fact / expression` 三种案例类型，外加 `--confirm / case-confirm / case-from`——它就是「主动上报」入口，但只有命令行、调试台没有表单，业务人员不会用；
- `cases` 表（Memory）与 `bad_cases.csv` 是两张不联动的表：case 库管「下次生成怎么参考」，bad_cases.csv 管「这个错误怎么归因修复」，目前没人把两者串起来；
- 驳回时给了改写建议，也被直接沉淀成 `confirmed` 反例，没有区分「有建议待人工确认」和「纯反例」。

### 渠道二：系统自动回收（沿服务路径图逐节点）

方法不是凭空想，是**沿着服务路径图逐节点问两个问题**：

1. 这个节点会以什么方式失败？（误报、漏报、字段错、超时、内容质量差……）
2. 这种失败会在哪里留下痕迹？痕迹在哪，回收渠道就在哪。

痕迹只有四种，对应四类通用回收机制，映射到本产品如下：

| 通用机制 | 本产品的痕迹 | 回收的 bad case 类型 |
|---|---|---|
| **① 校验 / 规则日志 → 拦截告警** | G4 机械校验错误码；C22 一手证据守卫 `excluded`；`programmatic_g1_flags`；G2 政策命中 `rule_id`；schema 校验 `REVIEW_SCHEMA_INVALID` | 被防线挡住的错误（P2） |
| **② 人工修改行为 → diff / 否决 / 强制填值** | `final_headline != headline` 的 diff；驳回原因分布；勉强通过瑕疵说明 | 穿过自动防线的错误和质量问题（P1/P3） |
| **③ 人工旁路 → 对比「人工绕过 Agent」vs「Agent 建议」** | V1 全量人工确认，暂无旁路；上线后若人工绕开 Agent 直接写标题，要记一笔 | 漏报（P1） |
| **④ 业务结果异常 → 事故 / 客诉 / 指标回溯** | 离线实验暂无；上线后接举报率 / 审核驳回率 / 客诉 | 穿透全部防线的 P0 |

**逐节点痕迹表**（每个关键节点问「怎么失败 + 痕迹在哪」）：

| 节点 | 怎么失败 | 痕迹 | 回收类型 |
|---|---|---|---|
| N01 读素材 | 素材缺 / 空 ASR / OCR 中文占比低 | `assess_material` 分级 `low`；`INPUT_LOW_CONFIDENCE` / `INSUFFICIENT_MATERIAL` | ② |
| N03 理解 | 漏抽事实 / 编造事实 | `claims` 数量异常；`evidence_refs` 白名单非法 | ① |
| N03V 核查（可选） | 核查误报 / `refuted` 漏报 | `verification_risk`；`refuted` 命中数 | ① |
| N05 边界 | 把「不该写」判成「可写」/ 丢必要限定 | `BoundarySet.decisions`；`required_limits` | ①/② |
| N07 看点 | 主看点选错 | `HighlightSet`；`eliminated[]` | ② |
| N09 生成 | 超长 / 丢限定 / 策略与材料不符 | G4 机械错误码 | ① |
| R01 评审 | 放水（该拦没拦）/ 过严（好标题判死） | `ReviewGate` 与人工判定不一致 | ② |
| Q01 裁决 | 路由优先级 / 阈值 | 终态分布 | ① |

## 8. Case 库 / Memory 什么时候被调用（回答核心问题）

你问的「Agent 写标题会调用案例库 / memory」这件事，现状是**空转的**，原因查清了：

- 检索代码是**无条件触发**的（`memory_calls < memory_call_limit(6)`），首轮 `query = video.title`、`problem_types = ["表达", "事实与信源"]`，重写轮才用评审的 `memory_query / issue_code`。
- **版本和检索逻辑本身都是通的**：人工判定自动沉淀的 case 存在 `red-dot-v0.2-modular`，检索也用 `red-dot-v0.2-modular`；`test_case_retrieval_uses_rule_pack_version`（本次复测 1 passed）证明**同库、同 scope、文本有重叠时能命中**。
- `used_case_ids` 在真实运行里一次都没命中过，**主因是架构层面**：`Storage` 按 `output_dir` 建库（`Storage(output_dir / "agent.db")`，一个实验目录一个库），而实验流程是「**整批跑完再人工判定**」——判定产生案例时，同目录的生成早已结束；跨实验目录又不共享案例。所以下一次生成永远看不到上一次判定的案例。
- **次因**（即使同库也会压低命中率）：① `problem_type` 语义错位——自动沉淀用英文 `reason_type`（`fact` / `point` / `expression:wording_unclear`），首轮检索是中文 `["表达", "事实与信源"]`，`type_hit` 命不中；② 首轮 `query = video.title` 与 case 文本（生成标题 + 驳回理由）的 2-gram 词面重叠弱，`overlap` 偏低。
- 另外，手动 `case` CLI 仍用 `config.rule_version`（默认 `temporary-v1`），与检索的 `prompt_pack_version` 不一致——手动建的 case 会永远检索不到。

所以正确的问题不是「要不要调用」，而是**把「入库」和「读取」两件事分开定义**：

### 8.1 入库：什么时候写 case（唯一来源 = 人工判定）

你在调试台每判一条标题，系统会顺手把这条存进**案例库**（`cases` 表，就是给生成器以后参考的「例子清单」）。**只有三种可能**，用大白话说：

1. **判「可用」** → 存一条**正例**（`good_example` = 这条标题，`bad_example` 空）。意思是「这种写法是对的，下次照着来」。判可用时不会先改标题再通过——要改标题就是下面第 2 种了。
2. **判「勉强通过」** → 存**一对**：原标题进 `bad_example`（反例，「别这么写」），你改后的标题进 `good_example`（正例，「照这样改」）。你判勉强通过基本都会改标题，所以这条就是「原标题 → 改后标题」的对照。
3. **判「不可用」（驳回）** → 存一条**反例**（`bad_example` = 这条标题，`good_example` 空）。意思是「这么写不行」。

「正例 / 反例」不是好坏评价，而是「该学 / 该避」：正例告诉生成器「照这个来」，反例告诉它「别这么写」。

每条案例还有个状态：
- `confirmed`（已确认）：会真的被检索出来用；
- `draft`（草稿）：手动用 `case` 命令建的、或还没确认的，先放着不启用（`case-confirm` 确认后才生效）。

一句话：**可用 → 正例；勉强通过 → 反例（原标题）+ 正例（改后标题）；不可用 → 反例。**

**自动防线拦截的错误（G4 / C22 / policy）不直接入库**——先归因是「规则缺失」还是「模型没守规则」，再决定进不进 Memory。拦截日志进 bad_cases.csv（作为 P2 趋势），不进 Memory（Memory 只放「人工确认过对错」的语料）。

### 8.2 读取：什么时候 Agent 写标题调用 case 库

原则（来自 [handoff.md](handoff.md) 第九节）：**正式规则有约束力，Memory 只提供参考**。检索不到 / 超时 / 案例不适用时，在正式规则完整的前提下降级为「仅正式规则」继续，不阻塞。

三个明确的触发点：

| 触发点 | 时机 | query 来源 | 目的 |
|---|---|---|---|
| **首轮生成 N09** | 无条件检索一次（预防性） | `video.title` + 领域/形态 `scope` | 让生成器见过「这类视频以前哪些写法被判死 / 被判过」 |
| **重写轮 R02** | **必须**检索（纠正性） | 评审 `memory_query` / `issue_code` | 这个 issue 之前是怎么修好的（`good_example`） |
| **边界 N05**（可选） | 有 confirmed 事实类反例时 | 断言文本 | 提醒边界判定别把「以前判死的写法」再放进来 |

**要修的三处（本轮全部完成，96 tests passed）**：① ✅ **案例库跨实验共享**（`Storage(path, case_bank_path=...)`；配 `"case_bank": "runtime/casebank/agent.db"` 即启用，默认空 = 旧行为；`_auto_case` 写它、`Pipeline` 读它）；② ✅ **`problem_type` 归一**（`_canonical_problem_type`：`fact/context → 事实与信源`、`point/grammar/unclear/other → 表达`；原始值保留在 `raw_reason_type`）；③ ✅ **手动 `case` CLI 用 `prompt_pack_version`**（不再写 `rule_version` 的 `temporary-v1`）。
