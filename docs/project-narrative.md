# 短视频推荐标题质量优化 · 项目自述

## 一、这项工作要解决什么

短视频进推荐池，要在信息流里配一条标题。这条标题决定用户点不点，也决定他点进来之后觉不觉得被骗。

现在的运转方式是这样：每天 3—4 万条视频进入标题生成，模型出标题、模型初审，然后交人工。一线审核 20—30 人，每人每天工作约 10 小时，单条 30 秒，能审完其中八成。剩下两成，当天不发。

这条链路上有两个问题同时存在。

**第一个是产能。** 每天有六千到八千条视频，内容本身没问题，就是没人审，当天直接不发。这笔损失不会出现在任何报表里，因为它不是事故，是常态。

**第二个是质量。** 30 秒审一条，不可能逐字核对，实际动作是扫一眼材料、读标题，按对应品类的审核规则判断哪里最可能不符合，再翻回去对一下。规则本身是明确的——各品类都有合格、不合格和驳回标准，审核人员也要通过培训和线上试标才能上岗——但落到具体一条文案上，要害在哪仍要人自己找；判错了没有人反馈，判对了也没有人确认。

我做的是一套生成与评审系统，两件事一起处理：让人审得更快，把两成补回来；让人判得更准，把错误挡在发布之前。

需要说清楚的边界：这篇里的百分比全是设计门槛，没有一个是已有批次支撑的实测值。唯一有真实人工判定的是第五章那 18 条，而且是旧版本。

## 二、谁在用，他们原来卡在哪

### 2.1 一线审核（20—30 人）

**主要任务。** 判断每条视频生成的推荐标题能不能直接上。能上就过，不能上就驳回并写一句理由。

**工作强度。** 每人每天约 10 小时，单条 30 秒，人均一天判 1200 条左右。按 2.8 万条/天、30 秒/条、10 小时/人反推，实际在岗约 24 人。

**现在的难处。**

第一，30 秒里最贵的是不知道往哪看。材料几百字，标题二十几个字，要害得靠猜。猜偏了白耗时间，猜漏了错误就流出去。

第二，一天判 1200 条，到下午和晚上，同一个人对同一条标题的判断可能已经和上午不一样。这个漂移没有任何记录。

第三，驳回的代价落在自己身上。驳回等于这条视频当天没标题，等于供给损失，还可能被问为什么驳。代价高的时候，人的真实行为是倾向放行——「差不多能用就过」。这是质量事故最常见的来源，而它在数据上看不出来。

第四，同类问题每次从头判。小包装那条暴露的问题，换个题材再来一次，上一次的判断没有变成任何可复用的东西。

第五，每天都有两成审不完。他们知道，但没有办法。

**希望得到什么。**

- 别让我猜要害，告诉我该核哪句话。
- 驳回别等于废单，给我备选或者帮我改。
- 同一个问题别让我判第二遍。
- 判错了有人告诉我，判对了有人确认。
- 把那两成审完。

### 2.2 规则运营（2 人）

**主要任务。** 从驳回队列和客诉里发现问题，归类，归因，改规则或改提示词，验证影响面，上线观察。

**现在的难处。**

第一，2 个人对每天几千条驳回。归类、归因、验证影响面三件事都要做，实际只能抓最扎眼的。

第二，问题散在各处。驳回理由在不同表格和聊天记录里，同一个人写两次用的词都不一样。要回答「今天几千条驳回里有多少是同一类」，得靠人肉聚类。

第三，归因靠猜。「标题不够吸引人」和「标题抓错了主旨」是两个完全不同的原因，修法完全相反，而原链路只留下最终标题和一句理由，看不到中间发生了什么。猜错了，改的方向就错，白改一轮。

第四，规则只能加不能减。删一条规则，没人能证明删了不会出事，所以只能加。规则越堆越厚，互相打架，误伤越来越多，下游开始学着绕过规则。

第五，改完不知道会不会伤到别的题材，只能再加一条更精确的规则打补丁。复发也没有固定观察窗口，运营的成就感来自「这次的事故处理完了」，不来自「这类问题消失了」。

**希望得到什么。**

- 问题自动聚成类，告诉我哪类最值得修。
- 归因有线索可查，不是靠猜。
- 改之前知道会影响哪些内容。
- 敢删规则。
- 改完这类问题还来不来，给我个回音。

### 2.3 产品负责人（买单的人）

**主要任务。** 定标题生成策略，决定投不投、扩不扩、换不换模型、加不加人。

**现在的难处。** 「模型说通过」和「业务真能用」经常混着报；算不清省了多少人工、补回多少供给、多花了多少钱；那两成的丢弃是沉默损失，没有人报损。

**希望得到什么。** 一套能互比的口径，一笔能算的账，以及「复杂链路多花的钱买到了什么」这个问题的答案。

前两个是用户，第三个是掏钱的人。这个区分很重要——把产品负责人写成「用户」，价值主张就会飘。

## 三、痛点和解法

这一节是全文的骨架。每一行对应上面提出的一个难处，说明原来为什么解决不了、这个项目怎么解、怎么验证。

### 3.1 审不完

| | |
|---|---|
| 现象 | 每天六千到八千条视频因为没有标题当天不发 |
| 原来为什么解决不了 | 产能靠每天 10 小时工时顶着，再挤已经没有空间；加人要招一到两成并加倒班，慢且贵 |
| 怎么解 | 把「找要害、核证据」这两步从人转移到机器，单条用时下降，同等人力覆盖更多量 |
| 目标 | 单条 30 秒降到 24 秒（降 20%），覆盖率从 80% 补到 100% |
| 怎么验 | 单条审核用时、覆盖率、每任务总人工用时 |

这里有个纯比例关系值得记住：现在用全部工时审了八成的量，要审满，每条的时长就得是原来的八成。**降 20% 刚好补满，跟几个人、几小时都无关。** 再往下降到 21 秒（降 30%），产能够覆盖 4.1 万条，4 万的上限也能覆盖——多出来的部分该转成复核和抽检，不是继续加量。

### 3.2 判断靠猜

| | |
|---|---|
| 现象 | 30 秒里最贵的不是判断对错，是不知道往哪看 |
| 原来为什么解决不了 | 只给一条标题，没有主旨，没有出处，要害自己找 |
| 怎么解 | 交付时同时给出：推荐标题、备选两条、系统认为的主旨、每条标题引用了哪句话和哪个画面位置、标出的风险点 |
| 目标 | 问题定位人工认可率 ≥85% |
| 怎么验 | 认可率、单条用时、驳回理由里「偏题」类占比的变化 |

### 3.3 驳回即废单

| | |
|---|---|
| 现象 | 驳回代价高，人倾向放行；放行的错误就是质量事故 |
| 原来为什么解决不了 | 生成一条，不过就作废，没有回头路 |
| 怎么解 | 首轮给 3 条同主旨候选，方向分别是保守重述、核心概括、核心钩子；没有合格项但问题可修时，定向重写最多 2 轮 |
| 目标 | 重写挽救率 ≥35%，首推接受率提升，误放率 ≤5% |
| 怎么验 | 挽救率、人工修改率、驳回后改选其他候选的比例 |

### 3.4 同类问题反复判

| | |
|---|---|
| 现象 | 一个问题换题材又出现，每次从零判起 |
| 原来为什么解决不了 | 人工判断不进任何库，只留下一个通过或驳回 |
| 怎么解 | 判定结构化入库：适用场景、版本、证据、正确做法；生成时检索参考 |
| 目标 | 同根因复发率相对无案例对照下降 ≥30% |
| 怎么验 | 独立同类视频对照，按风险适用分母统计 |

### 3.5 规则只加不减

| | |
|---|---|
| 现象 | 规则库越来越厚，互相打架，误伤越来越多 |
| 原来为什么解决不了 | 删规则没有证据证明不出事，谁也不敢删 |
| 怎么解 | 建立必过场景集、历史判对过的案例、反例；删一条规则可跑回归，验证「必过项没退化、历史正确结果没坏」 |
| 目标 | 规则总数可增可减，误伤率不上升 |
| 怎么验 | 规则条数变化、回归通过率、误伤率 |

### 3.6 归因靠猜

| | |
|---|---|
| 现象 | 2 个人对几千条驳回，只能抓最扎眼的 |
| 原来为什么解决不了 | 只有最终标题和一句理由，中间过程无痕 |
| 怎么解 | 全链路留痕可回放：理解输出了什么、选了哪个看点、评审怎么判、为什么分流；问题带位置（流到哪一层、哪个环节、根因是否确认、影响多少条） |
| 目标 | 同类聚类耗时可测、变更从提出到批准有明确周期 |
| 怎么验 | 聚类耗时、变更周期、问题账本的重复率 |

### 3.7 质量是黑箱

| | |
|---|---|
| 现象 | 判错了没人知道，判对了没人确认 |
| 原来为什么解决不了 | 没有记录，没有回音，没有金标准 |
| 怎么解 | 人工判定回流、盲评、至少 20% 双人独立标注、争议讨论定案 |
| 目标 | 双人三档一致性 kappa ≥0.60，同时报原始一致率 |
| 怎么验 | kappa、放行准确率、合格召回率、误放率 |

## 四、系统怎么运转

### 4.1 改造后的链路

【视频信息提取】→【① 内容理解与边界：整片主线、可写信息及出处、必须保留的限定、待核验清单】→【② 看点与生成：选看点，产出最多 3 条同主旨候选，带证据】→【程序检查 + ③ 独立评审】→【分流：合格则推荐；有问题则定向重写，最多 2 轮】→【人工确认：校主旨、挑标题或驳回并指出偏题位置】→【通过则发布；驳回则换候选或重写；判定回流案例与问题账本】

### 4.2 三个环节为什么必须分开

原因只有一个：同一个东西自己判自己，判不准。让生成标题的模型评价自己的标题，它倾向于说好。这是位置问题，不是能力问题。

| 环节 | 职责 | 输出 | 不能做什么 |
|---|---|---|---|
| 理解与边界 | 看懂整片，分清事实、观点、推断、剧情，判断哪些能写 | 内容卡：主旨、可引用信息及出处、必须保留的限定、待核验清单 | 把描述当事实；用「据称」消掉风险 |
| 看点与生成 | 找到值得写的东西，写三条不同角度，按意见改 | 看点卡、候选、证据、改了什么 | 编造效果、偷换主旨、借别的视频的事实、给自己批 |
| 独立评审 | 站在用户角度检查这条标题 | 判断、分项理由、问题定位、能不能修 | 改标题；拿吸引力抵事实问题；代替人做最终决定 |

### 4.3 分流规则

| 情况 | 怎么处理 |
|---|---|
| 至少一条全项合格 | 保留全部合格项，推荐一条，停掉多余重写 |
| 没有合格项，但问题可修 | 定向重写，最多 2 轮，每轮重新完整评审 |
| 核心事实、主旨或政策没定 | 转核验或人工。文案变流畅不解除 |
| 明确禁止、没有安全写法 | 驳回或停，不循环试绕过 |
| 材料撑不起可靠看点 | 停并说明缺什么。这是保护，不算故障 |
| 重写用尽仍不合格 | 停自动生成，保留候选和理由交人 |
| 网络或临时故障 | 有限重试，保进度；不可重试的直接停 |

### 4.4 人和程序各管什么

程序管确定的：长度、必要标注、引用是否合法、风险状态有没有丢、候选排序、轮次上限、费用、统计。这些交给模型是错的，改提示词也修不好。

人管有责任的：争议事实、政策边界、最终采用、案例确认、规则批准。

模型没有权限的四件事：线上发布、对外发送、改生产数据、修改业务规则。不是现在没做，是设计上不给。

## 五、事实都对，标题却不对

这一节是这个项目最核心的发现，也是全部设计调整的起点。

### 5.1 问题的形状

上一批 20 条视频，18 条有标题并已判完。9 条系统推荐里，3 条可用、2 条勉强、4 条不可用。另外 9 条是非推荐状态的诊断标题。

「四成推荐不合格」这个结论没错，但它不解释问题。把四条驳回理由逐条读完会发现，它们指向同一个毛病。

### 5.2 四个案例

**案例一，论据顶替了主题**（系统推荐，被拒）。
标题：「博主：小包装不一定成本更低」。
人工意见：作者强调现在流行小包装，它可能成为新的消费潮流，跟成本没关系，标题没体现出这层关系。作者原题是《小配件 mini 包装如何成为新热点》。

**案例二，教程没有对象**（系统推荐，被拒）。
标题：「博主称新手也能看清细节的化妆教程」。
人工意见：重点是博主教怎么画这个古早娇妹妆。

**案例三，探访变成摘录**（停止任务时的诊断标题）。
标题：「博主称海惠花园附近早餐店油条豆腐脑花 5 块」。
人工意见：重点是看惠州真实物价，标题里这条只是其中一条事实。

**案例四，限定词被动丢**（技术失败任务的诊断标题）。
标题：「博主称新 iPad mini 官网未标刷新率」。
人工意见：原意是官网没有标高刷新率，标题把「高」丢了。

后两个是任务停下或技术失败时留下的诊断标题，不算推荐失败，但它们暴露的是同一个毛病，所以放在一起看。当批另外两条被拒的系统推荐也是同一类：一条把采访里的一个小片段当成了整片主题，一条把穿搭话题写成了「低俗」。

**四条没有一条是编造的假事实，每句话都能在片子里找到出处。错的地方在别处：这条标题不是这条视频的标题。**

原链路的基础审核只核「有没有事实错误」，所以这类错误能全部穿过去，一路走到人工面前。人工每次都要重新解释一遍「重点是那个，不是这个」。

### 5.3 往下查：四个代码级缺口

沿着这条线查代码，问题不是零散的，是四个确定的缺口：

1. **主旨字段被丢弃。** 模型按提示词必须输出 `main_thesis`，但归一化函数只读 `highlights`，从不读 `main_thesis`。该字段既不落库，也不传给下游，本批 18 条 state 里 `main_thesis` 全部为空。
2. **主看点没强制必须是核心单元。** `relation` 写进了 Highlight，但没有校验「主看点必须为 core」。案例一的主看点是一个 support 单元，仍然进了下游。
3. **结构化候选能顶掉主旨单元。** `_structural_candidates` 生成的片段候选会被 fallback 无条件注入，一个单条动作或单条反差就能替代整段主线。
4. **教程类主旨被写成元描述。** 演示和教程类视频里，主旨被写成「作者以超详细手法教……」，标题自然就写成「超详细教程」，用户真正想学的那个具体妆容没了。

这四条都不是调提示词能解决的。第一条是数据流断了，第二条是约束没校验，第三条是优先级错了，第四条是任务定义偏了。

### 5.4 怎么修的

| 缺口 | 修法 | 必须防的副作用 |
|---|---|---|
| 主旨没传下去 | 持久化 `main_thesis` 并传入生成 | 主旨本就模糊的记录类视频仍允许停止或转人工 |
| 主看点不是核心 | 主看点必须为 core，否则重选或转人工 | 真实以反差为核心的视频仍可用对比作主看点 |
| 结构候选顶掉主旨 | 结构候选不得无条件压过主旨单元，只有主旨不可兑现时才退用 | 真实反转类视频不受影响 |
| 教程主旨是元描述 | 教程和演示类主旨必须落到「动作＋效果」，禁止只写「这是教程」 | 纯观点视频保留观点型主旨 |

同时补了两样东西：一是主旨卡，要求生成阶段拿到明确的主旨和可写范围；二是主旨锁测试，明确更换主旨标识会被检查，遗漏标识可以继承。但标识相同不能证明内容没偏题，仍然要靠独立语义评审。

### 5.5 怎么防止修出新问题

修一条坏掉另一条，是这类改动的常态。所以每个修复都要配三类样本：

- **原例**：这条视频本身要过。
- **同类变体**：换个题材的同类问题也要过。
- **反例**：历史上本来就判对的相反情形，不能被新规则误伤。

案例一的修复最典型。为了防止「论据顶替主题」而禁止写成本细节，会误伤真正以成本为核心的视频。所以修法是「必须覆盖主旨」，不是「禁止提成本」——主旨覆盖了，成本细节写不写都行。

### 5.6 分级：先看流到哪一步

严重度是两个维度：错误流到哪一层，造成多大后果。

| 层级 | 判断标准 |
|---|---|
| L1 自动防线拦住 | 被规则、评审或熔断挡住，没进普通推荐 |
| L2 人工拦住 | 穿过自动检查，成了推荐，被人纠正或驳回 |
| L3 流到业务 | 已采用或发布，还没有确认损失 |
| L4 造成损失 | 有客诉、合规事件或经营损失 |

L3／L4 加高影响是 P0，立即止损，24 小时内给初步根因；L2 加高影响是 P1，24—72 小时修或建替代防线；L1 以及中影响问题按周聚类；措辞偏好类双周或月度看。

有个反直觉的点：被自动防线拦住的错误等级低，但不该被忽略。它说明上游有质量问题，只是防线有效。反过来，被拦住一次也不等于系统没问题。

当前没有真实发布回执，所以不会有 L3 和 L4。不能把「系统推荐待审核」写成已流出。

### 5.7 什么叫真的修好了

闭环节点是：发现 → 收证据 → 去重聚类 → 复现 → 确认第一处失效和哪道防线该拦没拦 → 修 → 原例加反例回归 → 新样本验证 → 人工批准 → 小范围观察 → 结案或重开。

已入库、已写归因、已改提示词、只在原例上通过、测试数量变多——这五样都不算闭环。

结案要同时满足四条：原问题有对照且同类变体通过；历史正确结果没退化；高风险漏放没增加、负担没转给人；版本和批准可追溯，有观察窗口和复发监控。观察方案是批准后两周或累计 20 条同类新视频，取较晚的那个。

## 六、指标和目标

### 6.1 项目目标（OKR）

下列目标值均为拟定目标，尚未实测，以斜体标注。三条目标分别对应一线审核、文案质量和规则运营，互不重叠：同类问题复发率只在目标三出现一次。

**目标一：让更多视频拿到可用的推荐文案。**

- KR1：在拟定的 *200 条*公开视频样本上，通过内容理解、多候选生成和质量评审，使首轮至少产出 1 条可用推荐文案的任务占比达到 *≥78%*。首轮全部不合格但问题可修时，按评审指出的问题定向重写。
- KR2：系统判定可放行的推荐文案经人工复核后，放行准确率达到 *≥95%*、合格召回率达到 *≥90%*、不合格误放率控制在 *≤5%*。
- KR3：首轮无可用候选的任务中，经重写后至少产出 1 条可用文案的比例达到 *≥35%*；最终交给人工的候选中至少 1 条可用的任务占比达到 *≥85%*。

**目标二：缩短审核人员的判断时间，补足审核覆盖。**

- KR1：单条推荐文案的审核用时从 30 秒降到 *≤24 秒*；同等人力下，审核覆盖率从 80%—90% 补到 *100%*（两者是同一个比例关系：要审满，每条用时就得降到原来的八成）。
- KR2：交付时同时给出推荐文案、备选文案、系统判定的主旨，以及每条文案引用的材料位置和标记的风险点；问题定位的人工认可率达到 *≥85%*，且每个任务的总人工用时不超过现状。

**目标三：缩短规则维护周期，让同类问题不再从零判断。**

- KR1：规则可增也可减——更新前用回归集检查原案例、同类变体和历史正确案例，误伤率不上升；P0 问题 *24 小时*内给出初步原因和方案，P1 问题 *24—72 小时*内修复或补上替代防线。
- KR2：人工确认的问题和处理经验结构化入库，供后续相似任务检索参考；与不使用案例复用的对照组相比，同根因复发率下降 *≥30%*。批准后观察至少 *2 周*、累计 *20 条*同类新视频再结案。

### 6.2 指标与口径

| 环节 | 指标 | 目标 |
|---|---|---|
| 理解 | 关键事实准确率／覆盖率 | ≥95%／≥90% |
| 理解 | 不可写信息拦截率／可写信息误拦率 | ≥95%／≤10% |
| 生成 | 主看点人工接受率 | ≥85% |
| 生成 | 首轮任务成功率／最终合格供给率 | ≥78%／≥85% |
| 生成 | 重写挽救率 | ≥35% |
| 评审 | 放行准确率／合格召回率 | ≥95%／≥90% |
| 评审 | 不合格误放率／问题定位认可率 | ≤5%／≥85% |
| 端到端 | 严格可用交付率（首推） | ≥50% |
| 端到端 | 高风险必过集／硬约束合格 | 100%／100% |
| 人工效率 | 单条审核用时 | 30 秒→≤24 秒，每任务总用时不增加 |
| 成本 | 每条严格可用交付综合成本 | 下降 ≥20% |
| 复用 | 同根因复发率 | 相对无案例对照下降 ≥30% |

三条容易混掉的口径：

**任务级和文案级不能互换。** 一条视频给三条候选，一条可用，文案可用率是 1/3，任务成功率是 1/1。首轮 78% 是任务级。

**100% 只表示验收集内已定义的硬约束全过。** 不表示未知场景永不出错。

**没能评的不等于不通过。** 未评的不能自动算失败，也不能从分母里悄悄消失。

## 六（续）、当前实测：离目标还有多远

2026-11-02 批：20 条视频（10 个领域各 2 条），固定分母 20，人工三档盲评。这是**批内诊断**，不是对照实验。

| 指标 | 目标 | 实测 | 差距 |
|---|---|---|---|
| 首轮任务成功率 | ≥78% | 65%（13/20） | −13pt |
| 重写挽救率 | ≥35% | 14%（1/7） | −21pt |
| 最终合格供给率 | ≥85% | 70%（14/20） | −15pt |
| 误放率 | ≤5% | 12%（1/8） | +7pt |
| 误拦率 | ≤10% | 19%（3/16） | +9pt |
| 首推严格可用率 | ≥50% | 35%（7/20） | −15pt |

六项全部未达标，但没有一项差出一个数量级。**最值得说的是误放和误拦这对数**：系统推出去的 8 条只有 1 条被判不可用，而人判可用的 16 条里有 3 条没进交付面——**系统偏保守，不是偏宽松**。

### 差距卡在三个位置

**一、交付面漏候选（已修，未复测）。** 两条真实误拦都是这个：

- 同一任务里「可交付」和「需核实」两类候选并存时，只交出前者，后者整组丢掉；
- 主旨契约不一致时把推荐降级成待核，顺手把交付列表清空。

两处都在 2026-11-02 修掉，改法是引入「交给人工但不自动放行」这一档，降级不再清空。**修复只影响后续跑批，这批的 19% 不会变**——要看到改善得复测。

**二、5 个视频零合规候选。** 约占四分之一，全部卡在 `G1_MISSING_LIMIT`（边界要求标注的信息没出现在标题里）。其中 R15 三条候选全被判否，而人判有 1 条可用——**规则在误杀**。

**三、重写救不回来。** 首轮失败 7 个任务，重写只救回 1 个。机制在，效果没有。

### 人工效率：只有一个数，而且它测的不是完整的审核

56 条判定、18 个视频、24 分 34 秒。相邻两条判定的**中位间隔 12 秒**，均值 27 秒，p90 40 秒。分任务看更明显：3 条候选的任务，从第一条判到最后一条只用 12—48 秒。

**这个数不能当「审核提速」的证据**，三个原因：

1. **没测看视频。** 3 条候选 12 秒判完，不可能看完原片。真实审核要先看完 60—180 秒的视频。
2. **没测改稿。** 记录里只有「可用／勉强／不可用」和理由，没有改标题花了多久。
3. **没测零产出。** 5 个没产出候选的视频不在这个计时里——而那恰恰是最费人工的部分（要查为什么没出）。

所以它是**下限**：材料已备好、任务已熟悉、不用改稿时的判定速度。

要给出可对外的效率结论，得补三处埋点：视频播放时长、改稿耗时、零产出处理耗时。**这三个都没有，就不能写「提速 30%」**——现在写在提案里的 30 秒→24 秒，基线和新链路两边都还没有真实测量。

### 这批数据不能当什么用

**不能当对照结论。** 旧基线的 20 条视频与本批只重合 3 条，而旧的自动口径（程序自己判可用）给出 −35pt、人工口径（人判）给出 +10pt，两个方向相反。自动口径测的是「自动审核有多松」，不是标题好坏，**不能引用**。

**不能当验收。** 20 条是批内诊断，验收要 200 条未参与调优的独立样本。

**不能当修复有效。** 两个 bug 修完没有复测。

### 下游业务价值：现在一个都证明不了

这套系统最终要回答的是「标题变好了，用户会不会更愿意点、更少觉得被骗」。**这个我一次都没测过。**

没有线上实验，就没有点击率、完播率、举报率任何一项的真实变化可写。**能写的只有设计**：后续要看哪个指标、样本多大、怎么分流、什么结果算成功。

判断这套东西值不值得继续投的，是那几个数——不是这 20 条的批内诊断。**在那之前，任何「提升 CTR」的说法都是编的。**

## 七、成本

单条综合成本必须压到几分钱量级，全量日成本控制在千元级以内。这是产品成立的前提，不是附加项。

按 1 元/任务估算，3.5 万条/天就是 3.5 万元/天，一年上千万，这笔钱远超省下来的人力，结论会直接变成「不值得做」。所以 1 元是防失控的护栏，不是平均成本。

护栏的完整口径：首轮最多 3 条候选，额外最多 2 轮重写；单次调用最多重试 1 次；每任务模型调用不超过 24 次（含失败和重试）；费用预留上限 1 元；单次请求不超过 60 秒；整任务 180 秒到时停止、保存进度、交人工。

## 八、现在到哪一步

链路能跑，能留痕，能回传人工判定，案例能复用。质量有了第一组读数（20 条批内诊断，六项全部未达标），但还没有真实基线和正式验收。

还缺三样：

1. **真实基线。** 现在人审的漏放率、驳回率的构成、规则误伤的实际规模，都没有测过。30 秒的质量是黑箱，得先打开。
2. **正式验收。** 200 条未参与调优的样本，盲评、固定分母、评完整候选。
3. **成本实测。** 单条调用的真实价格和调用结构，决定这套东西在 3—4 万条/天的量级上到底成不成立。

下一步按这个顺序走：补基线 → 固化必过场景 → 阶段对照给「继续还是停」的结论 → 200 条正式验收 → 验效率与案例净收益 → 再决定要不要进真实试用。

顺序不能倒。先证明机制，再谈覆盖。

## 九、还没解决的问题

**一、补满之后多的产能怎么用，不由我定。** 降到 21 秒时产能会超过 4 万条的上限。这部分是转复核、转抽检，还是接受更多供给，是业务的风险决策。我只能把证据准备好。

**二、规则运营那边的收益怎么量化。** 单条审核用时可以测。运营省的「发现、归因、验证」三段很难拆出工时。能记的是：同类聚类要多久、一个变更从提出到批准走几天、规则总数是增是减。这三个够不够当收益指标，我还不确定。

**三、简单基线如果赢了怎么办。** 单次模型直出加人工抽检，可能比这套三模块便宜得多，质量差不多。如果对照结果是这样，就该砍掉复杂度，不能因为已经写了很多代码就给自己找理由。

**四、必过场景是我自己造的。** 它们覆盖了我能想到的边界，但真实分布不是这样长出来的。这批场景能证明防线存在，不能证明真实场景下够用。

**五、驳回的构成没测过。** 每天几千条驳回里，多少是事实问题、多少是主旨偏、多少是表达，这个分布决定规则运营先修哪一块。不知道这个，第三章那些解法只能按经验排优先级。

## 附录：怎么讲给别人听

**30 秒。** 我做的是短视频推荐标题的生成与评审系统。原来的链路是模型直出、模型初审、人工终审，不过就作废。每天 3—4 万条，20—30 个人每天干 10 小时，只能审完八成，剩下两成当天不发。我把链路拆成三个位置：理解内容和可写边界、选看点写候选、独立评审能不能用。长度和分流给程序，最终采用留人。单条只要降 20%，覆盖率就能从八成补到 100%。

**2 分钟。** 加上这些：30 秒审一条，人靠猜定要害，判错了没人知道。系统把「猜哪查」变成「看证据判」，把「驳回即废单」变成「三条候选加两轮重写」，把「规则只加不减」变成「有回归所以敢删」。最核心的发现是那 18 条诊断：被拒的 4 条系统推荐全部是核心看点错位，没有一条是编假事实——原链路只核事实不核主旨，这才是这套系统存在的理由。

**被追问预算和护栏时，** 分清已实现和设计中。24 次、1 元、180 秒是这版的设计值，不是已生效的承诺。
