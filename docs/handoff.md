**一、项目背景与当时阶段**

项目目标是为视频号红点推荐入口构建「短视频推荐文案生成与质量优化工作流」。截至 2026-10-31，Python 链路已实现并可运行；本稿其余章节记录当时的方案，不代表当前进度。

目标用户是推荐文案生产、质量审核和规则维护的业务人员。原有业务主要通过模型审核与人工复审判断文案可用性，驳回后作废；重复出现的问题由人工归纳为规则。

主要痛点包括：

- 正式规则分散，包含通用要求、垂类要求和隐性经验，难以完整迁移给模型。
- 通用生成规则覆盖有限，同类 Bad Case 反复出现。
- 人工审核与规则维护成本高，历史案例难以有效复用。
- 视频理解、看点选择和标题表达之间缺少明确的约束传递。
- 实际业务量大，需要同时考虑质量、成本、延迟和吞吐。

整体方向是：通过正式规则约束、生成 Agent、独立评审、定向重写、人工确认及案例记忆，形成质量优化闭环。

**本稿写作时已实现可运行的 Python 工作流、真实模型调用路径、独立评审与人工队列；当时真实质量证据仍薄弱，不能据小样本宣称已验证有效。HTML 是交互式设计说明，不代表线上系统。当前进度须重新核对代码、配置与近期实验。**

**二、核心业务目标**

标题生成首先需要满足：

> 正常用户只看标题、不看视频时，形成的内容预期，应当能够被视频实际内容兑现。

这意味着不能只检查标题中的单个事实有没有出处，还需要判断：

- 是否改变了主体、关系、条件和确定程度。
- 是否把历史事件包装成当前状态。
- 是否把观点、预测或转述包装成确定事实。
- 是否把边角细节包装成视频的主要内容。
- 是否承诺了视频没有提供的结果、解释或观看价值。

吸引力可以优化，但不能抵消这些问题。

项目最终需要验证四类业务结果：效率、质量、成本、风险。具体包括处理时长、人工操作量、一次通过率、人工一致率、返工率、调用成本以及误导或错误放行情况。

**三、本轮最重要的框架结论：一组基础约束＋三个关键决策**

不再要求模型平行执行十几个分散的评分维度，而是将生成任务收束为以下结构：

| 层次 | 核心任务 | 包含的判断 |
|---|---|---|
| 基础约束 | 正确、清楚地表达已确定的信息 | 主体与指代、逻辑关系、否定与转述、必要条件、语言与展示规范 |
| 决策一：确定可写边界 | 判断能写什么、必须如何限定、不能推断什么 | 证据、时效、信源、内容性质、事实与观点及预测的区分 |
| 决策二：选择核心看点 | 判断重点写什么 | 内容主次、代表性、观看价值、视频实际交付 |
| 决策三：选择表达策略与分寸 | 判断怎样表达 | 信息排序、结果前置、反差、悬念、情绪与评价强度 |

三个决策的顺序是：

**能写什么 → 重点写什么 → 怎样表达。**

基础与关键的区别是判断复杂度，不是是否允许妥协。看点代表性虽然难判断，但把次要内容包装成主要内容仍然可能直接不合格。

生成规则与评审标准也需要区分：

- 生成规则说明“什么条件下，选择什么信息，执行什么表达动作，保留什么边界”。
- 评审标准判断生成结果是否准确、清楚、有代表性、有吸引力。

例如，“标题有反差”是评价语言；可执行的生成规则应是：视频确实展示前后变化时，使用有依据的两个状态组织对照，并保留比较条件，不放大变化幅度。

**四、时效与信源必须前置到可写边界判定**

它们应当先影响哪些信息可以作为看点，再进入生成，不能等标题写完后才补查。

**时效需要区分三个时间，并引入一个使用基准：**

| 信息 | 含义 |
|---|---|
| 视频发布时间 | 视频何时发布 |
| 事件发生时间 | 视频讲述的事情何时发生 |
| 信息有效期 | 状态、安排或结论在什么条件和时间内仍适用 |
| 本次使用时间 `reference_time` | 当前准备生成、使用标题的时间，由系统传入 |

已形成的原则：

- 新发布的视频可能讲旧事件；旧视频中的知识也可能仍然有效。
- 不能把发布时间直接当作事件时间。
- 不能统一规定“超过多少天的视频不能使用”。
- 删除“刚刚、近日”等词不一定消除时效误导，“某公园暂停开放”本身就可能暗示当前状态。
- 动态状态没有当前依据时，应限定在有依据的历史范围；如果看点必须依赖当前有效性，则不能采用。
- “近期窗口”、动态信息失效条件、交付延迟后是否重检，需要业务确认。

**信源需要分成三层：**

| 层次 | 判断内容 |
|---|---|
| 发布者身份 | 是否有平台核验信息，资质是否与内容领域相关 |
| 原始来源 | 亲历、自述、机构发布、引用、转载还是来源不明 |
| 具体证据 | 当前材料究竟支持哪一条陈述、支持到什么程度 |

已形成的原则：

- 不能根据账号名称、头像或简介自行认定资质。
- 作者身份可靠，不代表每条陈述都成立。
- “视频里有人这样说”不等于“事实已经得到外部核实”。
- “作者称”只能解决部分归属问题，不能自动满足所有准入要求。
- “网传、疑似、据说”不能成为来源不明信息的通用放行方式。
- 画面只能支持直接展示的内容，不能自动证明原因、人数或最终结果。
- 同源的概括、ASR 等材料不能被当作多个独立信源。
- 只有文本输入时，不能声称已经核验原始视频画面。

**判断粒度应落实到每条候选陈述，而不是给整条视频贴一个“可信”标签后全部放行。**

**五、五泳道表示执行职责，不是数据依次经过的楼层**

| 泳道 | 职责 |
|---|---|
| 业务交互层 | 接收任务、展示候选、承接人工处理 |
| 流程控制层 | 输入校验、规则匹配、上下文装配、输出校验、预算控制和路由 |
| 智能处理层 | 内容理解、可写边界判断、看点提炼、生成 Agent |
| 动作执行层 | 模型调用、规则读取、Memory 检索、日志写入 |
| 数据与知识层 | 原始材料、正式规则、案例 Memory、任务状态和运行记录 |

需要同时区分：

- 谁作语义判断。
- 谁调用模型或工具。
- 谁校验返回对象。
- 谁决定下一步路径。
- 数据从哪里读取、写到哪里。

**逻辑节点数量不等于模型调用次数。** 可以先把职责和数据契约拆清楚，再通过评测判断哪些模型任务适合合并，避免机械地增加串行调用。

**六、本轮形成的生成阶段主链路与输入输出**

当前设计细化为 13 个主节点，范围截止到“待评审候选输出”。

| 节点 | 执行者与职责 | 主要输入 | 主要输出 |
|---|---|---|---|
| N00 受理视频任务 | 业务入口／任务创建函数 | `TaskRequest + RunConfig` | `RunInput`：任务 ID、请求与配置快照 |
| N01 输入校验与规范化 | 流程程序 | `RunInput` | `InputCheck`：规范化材料或输入错误 |
| N02 读取基础规则 | 流程程序调用规则工具 | 固定规则版本、基础规则范围 | `RuleBundle`：实际规则和硬约束 |
| N03 理解内容与整理证据 | 固定 LLM 节点 | 视频材料、理解规则 | `Understanding`：内容形态、候选陈述、证据、时间、来源与冲突 |
| N04 匹配适用规则 | 流程程序 | 内容领域、形态、属性、基础规则 | `ApplicableRules`：适用规则、触发依据、规则冲突 |
| N05 确定可写边界 | 固定 LLM 节点 | 陈述、原始证据、时间、信源、适用规则 | `BoundarySet`：逐条可用性与必要限定 |
| N06 可写信息路由 | 流程程序 | 已校验的 `BoundarySet` | `BoundaryRoute`：继续或停止、可用陈述 ID、限定映射 |
| N07 提炼可兑现的看点 | 固定 LLM 节点 | 可用陈述及限定、全片材料、规则 | `HighlightSet`：主看点、备选、代表性与兑现依据 |
| N08 装配生成上下文 | 流程程序 | 看点、边界、规则、原始证据、运行配置 | `GenerationContext` 或停止结果 |
| N09 选择策略并生成候选 | 生成 Agent | `GenerationContext`、按需检索的案例 | `AgentDraft`：候选、引用、表达策略、检索记录 |
| N10 候选硬约束校验 | 流程程序 | 候选、硬约束、合法引用范围 | `CandidateCheck`：保留候选与逐条剔除原因 |
| N11 候选交付路由 | 流程程序 | 校验结果、目标候选数 | `CandidateRoute`：交付或停止、数量差额 |
| N12 输出待评审候选包 | 结果交付接口 | 路由结果及任务状态 | `CandidateBatch`，状态为 `pending_review` |

这里明确了两个重要依赖：

1. **正式规则不能等到生成前才首次读取。** 基础规则在理解前提供，内容属性识别后匹配适用规则，生成前再装配完整约束。
2. **Agent 必须收到实际规则、证据和限定内容。** 只传规则版本号或若干 ID，不足以让模型执行要求。

HTML 中的类型契约与伪代码仍是设计稿，正式开发前还需要统一函数签名、字段和依赖传参，不能直接视为可运行后端。

**七、核心数据对象与约束传递方式**

数据链条已经明确为：

**原始证据 → 候选陈述 → 陈述使用判定 → 看点 → 标题候选。**

每一层都需要引用上一层的 ID，避免生成结果失去来源。

- `Evidence`：原始片段、来源字段、定位、已知派生关系。
- `Claim`：候选陈述、陈述性质、证据引用、时间依据。
- `ClaimDecision`：实际支持的说法、使用结论、必要限定、禁止推断、规则依据。
- `Highlight`：关联陈述、观看价值、代表性依据、兑现证据。
- `Candidate`：标题、看点 ID、陈述 ID、表达策略、采用案例和生成轮次。

可写边界统一使用三个枚举：

| 枚举 | 含义 |
|---|---|
| `usable` | 可以在现有证据范围内使用 |
| `limited` | 必须保留指定限定才能使用 |
| `excluded` | 当前不能用于标题 |

早期讨论的 `usable_with_limits` 与 `limited` 含义相同；HTML 统一使用 `limited`，工程实现不能混用。

必要限定通过程序按 `claim_ids` 合并并传给看点和生成上下文，不能只依赖模型“记得保留”。但程序完成传递，并不证明最终标题在语义上保留正确，仍需要独立评审。

如果必要限定无法在长度内表达，应换看点或放弃候选，不能删掉改变原意的条件。

**八、彻底拆开“模型调用、输出校验、流程路由”**

所有模型节点采用公共调用包装器：

| 环节 | 输入 | 输出 | 负责什么 |
|---|---|---|---|
| C01 调用模型 | Prompt、输入对象、调用配置 | `ModelReply`：原始返回或调用错误 | 获取模型结果 |
| C02 校验输出 | 原始返回、Schema、允许引用集合 | `CheckResult<T>`：合法对象或错误报告 | 检查 JSON、字段、类型、枚举、引用和完整性 |
| C03 调用结果路由 | 校验结果、已用次数、重试上限 | 继续／重试原节点／停止 | 决定调用成功或失败后怎么走 |
| 业务路由，例如 N06 | 已通过校验的业务对象 | 继续生成或业务停止 | 根据业务结论决定路径 |

必须保留三个区别：

- **结构校验通过，不代表语义正确。**
- **候选硬约束通过，不代表质量合格。**
- **`pending_review` 不代表已批准或已发布。**

典型例子：

模型合法返回“所有陈述均为 `excluded`”，C02 应当校验通过，C03 将对象交给 N06；N06 再停止生成，原因是没有可用信息。不能把这种情况当作 JSON 错误要求模型不断重试。

相反，结构合法但把旧事件判断为当前事实，可能通过程序校验。这类错误需要独立语义评审与人工金标准识别。

此外，**结构重试与评审后的业务重写是两套机制，必须分开计数。**

**九、Agent、正式规则与 Memory 的权限边界**

采用“确定性 Workflow＋固定 LLM 节点＋有限自主能力的生成 Agent”的设计。

生成 Agent 可以自主决定：

- 是否需要检索历史案例。
- 用什么条件检索。
- 哪些案例适用。
- 在已允许的看点中选择什么。
- 使用什么表达策略。

生成 Agent 不可以：

- 修改或绕过正式规则。
- 用历史案例补充当前视频缺失的事实。
- 使用已被排除的陈述。
- 删除必要限定来凑长度。
- 无限调用工具。
- 自行决定最终质量放行或发布。

**正式规则具有约束效力，Memory 只提供参考。**

Memory 应优先使用人工确认、与当前规则版本兼容的案例。检索超时、无结果或案例不适用时，可以在正式规则完整的前提下降级继续；正式规则缺失时，不能用 Memory 替代。

结构重试不能重置同一任务的 Memory 预算。生成阶段的日志工具也不自动更新正式规则或案例记忆。

**十、完整闭环仍然保留，工程已实现主要后半段**

整体规划仍包括：

生成候选 → 独立评审 → 程序依据门槛与评分择优 → 必要时定向重写 → 人工最终确认 → 经确认的 Good/Bad Case 入库与 Memory 更新。

需要保留的约束：

- 独立评审可以访问原始材料，不能只相信上游整理后的“事实答案”。
- 硬性问题不能被吸引力等高分抵消。
- 业务重写最多两轮，耗尽仍不合格则停止或驳回。
- V1 保留全量人工最终确认。
- 不使用生成 Agent 自评分证明生成质量。
- 案例入库和 Memory 更新需要质量确认，不能把所有模型输出自动沉淀为经验。

该句记录的是本稿写作时的阶段判断，不代表当前优先级。
