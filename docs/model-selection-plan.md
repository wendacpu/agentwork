# 模型选型方案（生成 / 评审分两个实验 · 20 条起步）

> 版本 v3.0 · 2026-11 · **方案层**：定候选、定实验设计、定口径、定决策规则。
> 执行步骤与命令见 [model-selection-experiment.md](model-selection-experiment.md)。
> 口径权威仍是 [eval-spec.md](eval-spec.md)；样本是 [templates/eval_manifest.json](../templates/eval_manifest.json) 的 20 条，不扩不换。
> v2.0 的预算（¥195 / 300 条人工）是按坏假设估的，已按实测重算——见 §6。

## 0. 一句话

**20 条固定视频，3 个生成候选 + 参考臂，半天出第一版结论**：第一段 ¥27–73、人工 40–60 分钟；觉得不够再上第二段（评审深挖）。生成和评审是两个实验，因为一个要变生成、一个要变评审，混在一起两个都测不准。

## 1. 为什么必须拆

| 混着跑的问题 | 后果 |
|---|---|
| 变量不隔离 | 评审一换 → 放行/重写变 → 下一轮生成的输入也变，分不清差异来自哪 |
| 成本相乘 | 3 生成 × 4 评审 = 12 组 × 20 条 = 240 任务 |
| 指标互相污染 | 生成质量被「评审严不严」掩盖，评审能力被「生成给不给好样本」掩盖 |

拆开之后：

| | 实验 A（生成） | 实验 B（评审） |
|---|---|---|
| 变量 | `generation_model` | `review_model` |
| 冻结 | 评审模型、流程、prompt | **生成结果整个冻结**（state 不动） |
| 机制 | 走完整 pipeline | 从已存 state 重跑 R01，不重生成、不触发重写 |
| 主指标 | 人工一次通过率 | 放行准确率 / 召回 / kappa |
| 人工 | 240 条（可先判 120 条） | 0（复用 A 的标签） |

单价为硅基流动定价页 2026-11 快照；元/条 按实测 token 结构算（§7）。

## 3. 实验设计

### 3.1 第一段：半天，必做

```
① B0 快筛（10 分钟，<¥1）  → 决定 A 的裁判用哪个评审模型
② smoke  3 行 × 3 候选（¥2）→ 只验管道，不判质量
③ 横评   20 条 × 4 系统（含参考臂）= 80 任务（生成 ¥17 + 裁判 ¥7–53）
④ 人工   240 条三档判定（可先判 120 条）
⑤ 出结论
```

**为什么先跑 B0**：V4-Pro 每任务 ¥0.66，比生成贵 3 倍；V4-Flash 只要 ¥0.085。如果 B0 证明便宜评审的判别力够用，裁判就换便宜的，第一段总成本从 ¥73 掉到 ¥27。**先花 10 分钟省 46 块。**

**没设 A1 预筛阶段**：只有 3 个候选，不需要漏斗淘汰。smoke 3 条跑不通的直接换，剩下的全量跑。

### 3.2 第二段：可选，想深挖再上

```
B1 系统内 A/B：20 条 state 重跑 R01，4 个评审 × 20 = 80 次调用（¥4–15）
B2 稳定性：冠军评审再跑一次（¥1–12）
补判：冠军 60 条逐条三档（20 分钟，给 B1 算 kappa）
```

B1 的价值：B0 测的是「脱离系统、只看原始材料能不能判」，B1 测的是「在真实输入（含 understanding/claims/边界）下能不能判」。两个都过才敢换评审。

### 3.3 省力路径（如果连 240 条都不想判）

**序贯判定**：先只判「最有希望的候选 + 参考臂」= 120 条（20 分钟）。若差距 ≥ 3 条直接出结论，剩下的不判。差距 ≤ 2 条再补其余——此时说明本来就没差多少，补判的意义是确认「打平」这个结论，而不是找赢家。

## 4. 指标与口径（唯一权威定义）

| 指标 | 定义 | 用在哪 | 门槛 |
|---|---|---|---|
| **一次通过率（严格）** | 20 条视频里至少 1 条候选被人工判「可用」的视频数 / 20 | A 主指标 | 不低于参考臂 |
| **一次通过率（含勉强）** | 同上，放宽到「可用 + 勉强通过」 | A 参考项 | — |
| **JSON 通过率** | 任务状态不是 `technical_failed` 的比例 | A 硬门槛 | ≥ 18/20 |
| **超长流入率** | 交付层（handoff/needs_review）标题超 `max_chars` 的比例 | A 硬门槛 | 必须 = 0 |
| **单任务端到端耗时** | wall time 中位（秒） | A 打平时用 | — |
| **负例拦截率** | 案例库负例里被判「不可用」的比例（只算硬错误，见 §8） | B0 | 相对比较，不设绝对门槛 |
| **正例放行率** | 案例库正例里被判「可用」的比例 | B0 | 同上 |
| **放行准确率** | 系统判放行的候选里，人工判「可用」的比例 | B1 | ≥ 85% |
| **合格召回率** | 人工判「可用」的候选里，被系统识别出来的比例 | B1 | — |
| **评分一致性 kappa** | 系统三档 vs 人工三档 | B1 | ≥ 0.6 |
| **判定自洽率** | 同一输入两次判定完全一致的比例 | B2 | ≥ 90% |

**权重**：质量 85% / 延迟 15% / 成本 0（并列记录）。

## 5. 决策规则（预注册，跑完不改）

### 实验 A

```
Step 1 淘汰：JSON 通过率 < 18/20，或 超长流入率 > 0
Step 2 排名：一次通过率（严格）；差 ≥ 3 条（≥15pp）分胜负
Step 3 打平（差 ≤ 2 条）：比端到端耗时中位；仍差 <10% → 比元/条；再平 → 比 JSON 通过率
```

### 实验 B

```
Step 1 淘汰：B0 里「把硬错误判成可用」的比例明显高于其他模型，或 B2 自洽率 < 90%
Step 2 排名：放行准确率 → 合格召回率 → kappa
        互相矛盾时放行准确率优先（放错一条比多拦一条贵）
Step 3 打平：单条评审成本（评审占单条成本 78%，只有这里成本有意义）
```

## 6. 预算（实测重算）

单条生成 = 18.2 万 prompt + 1.23 万 completion（§7 实测）；单条评审 = 5.0 万 prompt + 2.3 万 completion。

| 项 | 单价 | 数量 | 合计 |
|---|---|---|---|
| ① B0 快筛 | ¥0.03–0.43/条 | 48 × 4 模型 | **< ¥1** |
| ② smoke | ¥0.7/任务 | 9 | ~¥2 |
| ③ 横评生成 | ¥0.20–0.23/任务 | 80 | ~¥17 |
| ③ 裁判（V4-Pro） | ¥0.66/任务 | 80 | ¥53 |
| ③ 裁判（V4-Flash） | ¥0.085/任务 | 80 | ¥7 |
| ④ 人工判定 | — | 240 条 / 40–60 分钟 | — |
| **第一段合计** | | | **¥27（便宜裁判）～¥73（V4-Pro）** |
| 第二段 B1 | ¥0.05–0.66/次 | 80 | ¥4–15 |
| 第二段 B2 | 同上 | 20 | ¥1–12 |
| 冠军补判三档 | — | 60 条 / 20 分钟 | — |
| **两段合计** | | | **¥32–100** |

对比 v2.0 估的 ¥195：主要错在 B0（算成 ¥40，实际 <¥1）和 A2（算成 ¥86，实际 ¥70 且可降到 ¥24）。

跑批时间：单任务 55s，20 条串行 18 分钟/系统，4 系统并行 2 路 ≈ 40 分钟。B0 约 10 分钟。B1 每模型 20 次调用 ≈ 5 分钟。

## 7. 实测基础（`runtime/real_run_flash_nothink/agent.db`）

22 个任务 / 141 次调用：

| 项 | 值 |
|---|---|
| 单任务 prompt / completion | 均值 181,684 / 12,301 |
| 单任务端到端模型耗时 | 中位 55s · 最大 166s |
| 单次调用耗时 | p50 8.1s · p90 20.8s |
| JSON 失败 | 8/26，全在 `N03`（2 万字符级输出）与 `R01` |
| **B0 单条评审输入** | **997 prompt tokens · 3.0 秒**（标题 + 20 条 ASR + 20 条 OCR） |

按节点（均值/任务）：`N03` 16.2k / 20.1s，`N05` 22.3k / 16.2s，`N07` 28.5k / 7.3s，`N09` 71.5k / 5.1s，`R01` 50.0k / 9.1s。

生成节点 prompt 是最大成本项（71.5k × 每任务 2 次）。要压成本该压这里，但压上下文会动流程，本实验冻结流程，所以只记录不优化。

## 8. 风险

| 风险 | 应对 |
|---|---|
| `GLM-5.3-Flash` 思考关不掉（5 种参数全试过，reasoning 仍有 70–360 tokens） | 成本按 completion 含 reasoning 估；延迟单独记录。若单任务 > 3 分钟，降为对照不入选 |
| **案例库极性参差**（63 条：硬错误 19、软瑕疵 32、正例 12；能在 20 条样本内取到视频的只有 48 条） | 「软瑕疵」是指代不清这类小毛病，评审判「可用」不算错。B0 只用 **19 条硬错误** 算拦截率、**11 条正例** 算误杀，软瑕疵 18 条只记录分布、不进门槛 |
| 正例也不干净（如「挪威首相驳斥《金融时报》…」的说明写的是修改建议而非判定理由） | 正例只用来测「误杀」，不作绝对门槛；B0 定位是**相对比较 + 淘汰明显不行**，不是定标准 |
| 20 条判不出 ≤2 条差异 | 打平规则；结论必须带「小样本」声明 |
| 生成/评审同源 | 硬约束：不同家族 |

**退路**：若 3 个候选都不如 `deepseek-flash`，结论就是「这个任务对开源模型还不够友好」，保留当前系统，把钱转去做「评审强 + 生成弱」的组合验证。

## 9. 与 baseline / eval-spec 的关系

- 本方案不是 baseline。baseline 是「当前系统跑 20 条出第一版数字」（[eval-spec.md](eval-spec.md) §4）。
- 参考臂（`deepseek-flash`）就是 baseline 的输入，共用一次跑批。
- 决策只回填 config 的 `provider` / `generation_model` / `review_model`，不动规则与 prompt。
