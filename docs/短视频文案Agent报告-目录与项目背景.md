# 一、项目背景

## 1. 目标用户与使用场景

本项目面向负责短视频推荐文案质量的审核与策略团队，包括一线审核人员和规则运营人员。一线审核负责结合视频材料判断模型生成的推荐文案是否可以采用；规则运营负责分析集中出现的问题，维护推荐文案规范和审核规则。

每天约有 3—4 万条新视频进入推荐文案生成链路，团队需要判断模型生成的推荐文案是否准确、是否体现视频重点、是否符合业务规范。推荐文案不能采用时，审核人员直接驳回，不填写驳回原因，也不选择其他候选，系统不会进行重写。规则运营通过抽样检查和用户反馈发现问题，分析是否需要调整规则或提示词，并检查对其他题材的影响。

## 2. 原业务链路及主要问题

**原有业务链路**

原流程按照“视频信息提取—规则约束—模型生成推荐文案—模型基础审核—人工审核”的顺序运行。

- 一线审核从队列领取任务，每条视频对应一条待审推荐文案；
- 审核人员打开视频原标题和转写片段，阅读系统生成的推荐文案，依据对应品类的审核规则核对内容，再决定通过或驳回；
- 通过的推荐文案进入后续发布流程，不通过的推荐文案直接作废；
- 对于当天未完成推荐文案审核的视频，发布时使用通过审核的视频原标题作为推荐文案，而不是等待模型生成的推荐文案完成审核。

规则运营通过抽样检查和用户反馈收集问题，人工归类、分析原因，再调整规则或提示词。由于不同题材的表达方式不同，每次修改都需要检查是否会误伤原本可用的推荐文案，或漏放原本不可通过的文案，并在上线后继续观察。

**主要问题**

**审核任务集中，产能有限。** 每天 3—4 万条视频进入推荐文案生成链路，而一线审核人员仅 20—30 人，即便将单条推荐文案审核压缩到 30 秒，审核覆盖率也仅为 80%—90%，无法完成所有审核任务。

**人工审核耗时，且判断过程难以复用。** 模型目前只做基础合规检查，不能说明推荐文案的生成依据，因此文案是否合规、表述是否偏题、事实是否准确，仍主要由人工从头查看材料后结合既有业务规则判断，既耗时，过程也难以沉淀和复用。

**审核结果只有通过或驳回，缺少可供修复的反馈。** 推荐文案存在事实偏差、看点不准或表达不清时，目前的做法是直接作废，审核结论只停留在“通过”或“驳回”，没有形成可供生成环节使用的问题说明和修改方向。

**规则维护依赖人工，迭代后难以验证效果。** 规则迭代目前主要靠人工完成：需要通过抽样检查和用户反馈识别问题、判断原因、提炼规则后修改提示词，定位依赖个人经验。规则修改后是否误伤其他题材，也难以判断，只能靠样本逐一验证，因此模型生成规则只加不减，越积越多，反而影响模型生成质量。

## 3. 项目 OKR

三个目标是一条链上的三段：先让文案写准（一），再让审核判得快、判得全（二），最后让判定结果回流，使规则修改有依据（三）；规则改准后，下一批文案又更准，回到一。只看其中一项都可能达标：只看一，可以靠少交付达标；只看二，可以靠少判断、多放行达标；只看三，可能只是积累了大量记录。

**目标一：提高模型生成的推荐文案质量**

- KR1：在拟定的 *200 条*公开视频样本中，通过内容理解、多候选生成和质量评审，使首轮至少产出一条可用推荐文案的视频任务占比达到 *78%*。首轮所有候选均不合格时，根据问题定向重写，减少推荐文案直接作废。
- KR2：系统判定可放行的推荐文案经人工复核后，放行准确率达到 *≥95%*、合格召回率达到 *≥90%*。

**目标二：缩短审核人员的判断时间**

- KR1：将单任务审核耗时从 30 秒缩短至 *24 秒*，下降 *20%*；同等人力下，审核覆盖率从 80%—90% 补到 *100%*。
- KR2：交付时同时给出推荐文案、备选文案、系统判定的主旨，以及每条文案引用的材料位置和标记的风险点。问题定位与人工判断一致的文案占比达到 *≥85%*；且每个任务的总人工用时不超过现状。该比例的分母只含系统已给出定位的文案，未给出定位的单独统计。

**目标三：降低同类问题的重复处理成本**

- KR1：建立案例回流机制。人工确认的问题和处理经验结构化入库，记录适用场景、问题与处理方式，供后续生成时检索参考。与不使用案例复用的对照组相比，同根因复发率下降 *≥30%*。
- KR2：规则更新前用回归集检查原案例、同类变体和历史正确案例，防止误伤率上升；若发现规则被错误执行、可能导致平台生态安全风险的，*24 小时*内给出初步原因和方案；其他情况下发现的规则漏洞，*72 小时*内修复。

上述目标值均为拟定目标，尚未实测，以斜体标注。首轮任务成功率按视频任务统计，放行准确率与合格召回率按文案统计；无产出和技术失败的任务仍留在分母中，不剔除。

## 4. 项目价值

**对一线审核人员：** 将审核所需的推荐文案、视频主旨、材料依据和风险提示集中呈现，减少人工查找和核对材料的时间，使审核人员更聚焦于最终判断。

**对规则运营人员：** 将分散的问题和处理经验沉淀为可检索的案例，为问题定位、规则调整和效果验证提供依据，减少相似问题反复排查，以及规则修改后的验证负担。

**对组织：** 在既有人力条件下，提高推荐文案的审核覆盖率和可用性，减少未完成审核时对视频原标题的依赖；同时让审核结果和规则调整经验能够持续积累，为后续质量优化提供依据。

## 5. 为什么这件事要用 Agent 做

先回答一个反问：这件事，规则引擎、RPA、一张 SQL 报表，或者多招几个人，能不能做？

**输入是非结构化的，规则引擎读不懂。** 任务的输入是一条完整的视频——标题、几分钟的口播转写、画面信息。要判断“这条视频能写什么”，得先把口语化的转写读成主旨和事实，再判断哪一点能代表整条视频。规则引擎和 SQL 的前提是字段已经定义好，而这里的输入没有字段，只有自然语言。

**判断是模糊的，规则穷举不完。** “这条推荐文案算不算合格”看起来能写成规则，实际写不出来。审核规则能明确的是硬项：长度、禁用表述、必要前缀、与材料冲突的事实；判不了的是一条文案“有没有说到这条视频真正的看点”。看点因题材而异，同一句文案换到另一条视频上就是跑题。写死规则的结果是每周都要打补丁，而补丁之间会互相冲突——这正是现有规则只加不减、越积越多的来源之一。

**需要跨多种资料综合推理。** 判断一条文案能不能用，要同时看三样东西：视频材料本身、对应品类的文案规范、历史上有过哪些同类判定。RPA 能把这些资料搬到一起，但搬完之后“两条规则冲突以哪条为准”“材料里没有这个事实该怎么办”，它不回答——而这恰恰是判断本身。

**长尾场景多于头部场景。** 头部题材（品类清晰、表达模板稳定）确实可以写成规则；但每天 3—4 万条视频的题材分布是长尾的——新话题、跨品类内容、突发事件的表述边界，各不相同。为长尾逐个写规则并持续维护，人力成本已经高于让模型判断的成本。

**为什么是现在做。** 两个条件同时成立。一是模型能力到了可用线：长文本理解和结构化抽取的稳定性，已经足以把几分钟的口播转写归纳成主旨、要点和带位置的证据，并逐句判断文案有没有材料支撑。二是成本到了可接受区间：按当前模型价格核算，一条视频走完理解、生成与评审的全部调用成本，已经低于人工审一条所需的人力成本（按 30 秒/条核算）。在这两个条件成立之前做同样的事，要么判不准，要么算不过账。

**最后划一条边界，这一段不用模型。** 链路里的长度校验、必要前缀检查、候选去重，以及“评审结论决定走哪条分支”的路由，用的是程序和规则，不是大模型：这些环节的输入是结构化的，规则是确定的，交给模型只会引入不确定性、延迟和额外成本。模型只负责它真正擅长的部分——把非结构化的材料读懂，以及在规则写不出来的地方做语义判断。

# 二、产品方案

## 1. 整体运行机制

**主链路**

```text
【输入视频信息】
   ↓
【理解视频内容，整理事实与证据】（视频理解 Agent）
   ↓
【结合规则判断哪些内容能写、哪些需要限定】（视频理解 Agent）
   ↓
【校验证据引用、主体归属、数值冲突，并做外部核查】（程序）
   ↓
【确定视频主旨与核心看点】（文案生成 Agent）
   ↓
【检索历史案例，生成最多 3 条同一主旨、不同写法的候选】（文案生成 Agent）
   ↓
【检查长度、必要前缀等硬性要求】（程序）
   ↓
【检查事实、看点和表达，给出评审意见】（文案评审 Agent）
   ↓
【综合校验和评审结果，决定后续处理】（程序）
   ↓
┌─ 有候选可送审：择优推荐 → 人工确认 → 采用或记录问题
├─ 无候选可送审，但问题可修复：按评审意见定向重写（文案生成 Agent）
│                              → 再次评审（文案评审 Agent），最多 2 轮
├─ 事实或风险存疑：转人工核实
└─ 无可写内容或任务失败：停止生成并记录原因
```

**规则迭代与案例回流链路**

```text
【人工审核并记录问题】
   ↓
【整理 Bad Case 与相关证据】
   ↓
【人工核实原因，确定修复方式】
   ↓
【修改规则、提示词或程序】
   ↓
【回归测试】
   ↓
【人工批准并观察效果】

人工确认的案例进入 Memory，后续生成文案时按条件检索，命中后作为参考。
```

一条视频进入链路后，先由**视频理解 Agent** 把标题、转写和画面读成视频主题、候选看点、可写边界和带位置的事实证据，并结合品类规则判断哪些内容能写、哪些需要限定；随后由**程序**校验证据引用、主体归属和数值冲突，并对材料无法自证的现实断言做外部核查。校验通过的内容交给**文案生成 Agent**，由它确定采用的主旨与核心看点，并结合由程序检索出的历史案例，生成最多 3 条同一主旨、不同写法的候选；再由**程序**做长度、必要前缀等确定性校验，交给**文案评审 Agent** 检查事实、看点和表达；最后由**程序**综合校验与评审结果，决定这条任务的去向。

四种去向对应四种处置：有候选可送审的，择优推荐给人工确认，由人工决定采用或记录问题；无候选可送审但问题可修复的，按评审意见回到生成环节定向重写，再评审一次，最多两轮；事实或风险存疑的，转人工核实，不由系统下结论；无可写内容或任务失败的，停止生成并记录原因，不产出文案。

人工在这里不是终点而是起点。审核时记录的问题连同证据整理成 Bad Case，由人工核实原因、确定修复方式（改规则、改提示词或改程序），修改完成、上线前先跑回归测试，再由人工批准并观察效果。人工确认过的案例进入 Memory，后续生成文案时按条件检索、命中后作为参考——这是系统越用越准的来源，也是同类问题不必反复判断的原因。

**各节点的承担者**

| 节点 | 承担者 |
|---|---|
| 整理事实与证据、判断可写边界 | 视频理解 Agent |
| 内部校验与外部核查 | 程序 |
| 确定主旨与看点、生成候选、定向重写 | 文案生成 Agent |
| 事实、看点与表达评审 | 文案评审 Agent |
| 长度、必要前缀等硬性校验 | 程序 |
| 分支路由与结果汇总 | 程序 |
| 案例检索与结果回流 | 程序 |
| 最终采用、问题记录、事实核实与修复决策 | 人工 |

三个 Agent 只做语义判断，程序只做确定性判断、外部核查和路由，人工做最终采用和修复决策。系统不给出发布结论，也不替人工挑选候选。

## 2. 视频理解 Agent：识别视频主题、候选看点和可写边界

**核心任务：** 将视频标题、口播转写和画面 OCR 等信息转化为四类结构化结果：视频主题、候选看点、可写边界和事实证据。

- **视频主题**：视频主要讲什么、包含哪些主要内容。
- **候选看点**：视频中值得提炼和推荐的信息，供下一个环节选定主旨。
- **可写边界**：哪些内容可以写，哪些需要限定，哪些不能写。
- **事实证据**：每条事实对应的原始文本及位置。

**模型与程序分工：** 模型负责理解，程序负责验证。

- 模型负责理解语义、提取主题和候选看点、判断内容边界。
- 程序负责可规则化的校验，如主体归属、数值冲突、引用完整性等。

**模型内部处理：**

- 输入：视频标题、转写与 OCR 文本，以及对应品类和内容形式的业务规则包。
- 输出：视频主题、候选看点、可写边界，以及带出处的证据和需人工核实的未决问题。
- 约束：该环节只负责内容理解，不生成文案。每条可写主张必须关联一手证据；缺少原始证据的主张由程序降级为不可写，并记录对应问题码，尽可能在生成前拦截事实编造。

**程序：质量校验与异常处理**

程序校验分两步。

第一步在系统内部完成：证据引用是否真实、主体归属是否准确、数值是否存在冲突、存疑信息是否进入了未决清单。

第二步调用外部检索工具：对材料无法自证的现实断言做外部检索。

- **什么时候查**：对可核查的品类开启（如时事社会、财经商业）；命中强制核查词（疗效、剂量、收益、判刑、伤亡等）的必须查，强制核查词优先于品类条件。
- **查什么、查几条**：每条视频最多核查 3 条断言，优先选择能被外部来源支持或反驳的事实断言。
- **怎么算查实**：判定“已被反驳”需要至少 2 个独立来源互证。来源不足或置信度不够时不直接判死，而是降级为限定表达（保留来源归属，或标注存在争议）。

根据校验结果分为四种情况：

- 证据充分：进入文案生成环节。
- 外部核查被反驳：标记为不可写，或降级为限定表达。
- 缺少一手证据：降级为不可写。
- 涉及外部事实且无法确认：标记为待核实，转人工处理。

对于不确定的信息不强行下结论，而是通过证据和来源校验决定是否放行，不直接采用模型自报的置信度。

**迭代优化**

内容理解涉及提示词、业务规则和信息抽取结构，修改成本相对较高。因此按照从低到高的顺序优化：先调整提示词，再补充业务规则，之后考虑调整抽取结构，最后才改造整体流程。每次修改后使用固定样本进行回归测试，观察首轮成功率及判断准确性是否下降。

## 3. 文案生成 Agent：生成候选推荐文案，按需定向重写

**核心任务：** 把视频理解结果转化为可交付的候选推荐文案。根据上游输出结果，确定视频主旨与核心看点，再结合历史案例，在同一主旨下生成最多 3 条不同写法的候选，提高至少产出一条合格文案的概率；候选被评审指出问题时，按问题定向重写。

**表达策略**

生成不是完全自由发挥，而是根据视频内容选择合适的表达策略。同一主旨下按三个固定槽各写至多一条：原题锚定的保守重述、整片主旨概括、同主旨核心钩子；每个槽按视频内容选用一种表达策略。

- 问题方法：突出问题及解决方式。
- 对照比较：突出不同事物之间的差异。
- 前后变化：突出变化过程与结果。
- 疑问留答：通过合理设问引导观看。
- 直接描述：不满足其他策略条件时使用。

**模型与程序分工：** 模型负责选择表达策略、组织语言和生成候选，生成必须遵守上游事实与可写边界，不得补充未经证实的信息；程序负责字数、格式等硬约束，具体校验项见下文“质量校验”。

**Memory 案例检索**

案例检索是为了让同类问题不必每次从零判断，但它只提供写法参考，不提供事实。

- **怎么进库**：人工审核确认过的判定（可用／勉强／不可用，加一句瑕疵说明），连同适用场景、问题类型和问题码一起写入案例库。案例库跨任务共享，供后续所有任务检索。
- **什么时候查**：查两次。生成前按主旨和问题类型查一次，供选写法参考；定向重写时按评审给出的问题码再查一次，找同类问题改对过的案例。
- **靠什么命中**：问题码精确命中优先于句子相似，同一问题码的案例比“读起来像”的案例更有用；检索结果按规则版本过滤，避免用旧版本下的判定指导新版本。
- **查多少**：每个任务最多 6 次检索调用、每轮 2 次，每类问题最多带回 5 条，不把整个案例库塞进上下文。
- **使用边界**：案例只能参考表达方式和处理方式，不能当作当前视频的证据，也不能把案例里的事实迁移到新视频。

**举例**：一条“实测洗衣凝珠清洁力”的测评视频进入生成前，系统按主旨和题材检索，命中一条历史案例——它对同类“结论与直觉相反”的测评视频，记录的写法是“标题写对比结论，不写过程细节”。这条视频的候选文案因此优先走结论表达，而不是去写包装、价格这类边角信息。检索取的是写法规律，不是案例里的事实。

**模型内部处理：**

- 输入：上游整理好的结构化信息，包括视频主旨、候选看点、对应证据、可写边界、字数要求、表达策略及历史案例。
- 输出：最多 3 条候选推荐文案，每条带所引用的主张与证据、采用的表达策略、所属主旨与槽位；重写产出的候选另带生成轮次和上一版来源。
- 约束：文案长度要求为前缀与正文合计不超过 20 字，其中正文至少保留 6 字，且不得以问号结尾。

**重写与异常处理**

重写只解决“有可写内容但写得不对”。如果所有可写内容都撑不起一个能被视频兑现的看点，停止生成并转人工，不用备选硬凑一条交差。重写分两类：表达问题只改措辞，不动看点；核心承诺没被兑现时，允许换一个看点重写，但不能为了好写而换掉整片主旨。

针对不同问题设置独立的处理上限，避免无限重试造成成本增加：

- 语义问题：最多重写 2 轮。
- 字数、格式等机械问题：允许定向修复 1 次，不占用语义重写次数。
- 模型返回格式错误：最多重试 2 次。

超过处理上限仍不合格的任务直接终止，并记录失败原因，为后续 Bad Case 分析提供依据。

**质量校验**

候选文案生成后，先由程序进行机械校验，包括字数、必要前缀、结构字段、事实证据引用是否有效及候选相似度。相似度超过 0.8 的候选进行去重。通过校验的文案才进入质量评审。

**迭代优化**

生成侧的问题优先从便宜的手段试起：先优化生成提示词，再补充历史案例与优质示例，然后考虑调整业务规则，最后才优化生成轮次与资源预算。对于第二次出现的同类问题，不再只依赖提示词提醒，而应考虑沉淀为固定规则或程序校验，避免重复犯错。

## 4. 质量评审 Agent：对每条候选文案独立评审

**核心任务：** 对每条候选文案进行独立评审，输出评审结论、问题原因、严重程度及后续处理建议。

**评审维度**

评审包含三个语义维度，加上由程序负责的一个机械维度，四类结果合并后一起输出。每个问题都要记录问题码、严重程度、是否可修复，以及应该回退到哪个问题环节（材料／理解／看点／表达／评审）。

- G1 事实与断言许可：是否有证据支持，是否存在事实错误或夸大。（评审 Agent）
- G2 业务政策：是否符合已经批准的业务规则。（评审 Agent）
- G3 内容交付与承诺：文案表达的看点是否与视频实际内容一致。（评审 Agent）
- G4 机械约束：字数、格式、前缀和引用是否符合要求。（程序）

此外，对表达清晰度、信息价值和观看吸引力分别进行 1—3 分评分，每项至少达到 2 分。

**为什么生成与评审需要分离**

- 生成负责产出，评审负责独立挑错，避免模型对自己的结果评价过高。
- 两者使用独立提示词和模型配置，可以分别优化和替换。
- 评审只提出问题，不直接修改文案，修改统一回到生成环节。

**评审输入与权限**

- 输入：候选文案、事实主张、证据、看点及已批准的业务规则。
- 输出：通过、可修复和需要人工判断三档结果。
- 权限：评审没有修改文案的权限，也没有放行权限；“需要人工判断”只是它的一种意见，最终是否采用由人工决定。

**评审结果与流转**

根据评审结果，分为三种处理方式：

- 通过：满足质量要求，进入人工确认队列。
- 可修复：将具体问题及回退目标反馈给生成环节，进行定向重写。
- 需要人工判断：涉及事实存疑或风险边界，转人工核实。

同时设置程序硬性拦截机制。对于 P1、P4、P6、P7 等明确禁止的业务政策，命中后直接拒绝，不能通过反复重写绕过限制。对于 P8 涉及的医疗、用药、投资、法律等高风险场景，以及灾害伤亡的具体数字或具体人物，如果材料缺少充分依据，则必须人工核实，模型和程序均不能单方面放行。

**评审效果验证**

上线前，以固定的 200 条公开视频样本作为评测集，人工标注随批次累积，计算模型评审与人工判断的一致率，并分别统计误杀和漏放情况。前者反映评审是否过于严格，后者反映是否放过了存在事实或质量问题的文案。这条线达标之前，评审不放行。

## 5. 人机分工

**核心任务：** 明确程序、模型和人工各自负责的工作，以及关键人工确认节点，保证流程可控、结果可追溯。

**三方职责：** 程序负责执行固定规则，模型负责理解和辅助判断，人工保留最终决策权。

| 执行主体 | 核心职责 |
|---|---|
| 程序 | 字数、格式、引用、数值冲突、外部核查、候选去重及流程路由 |
| 视频理解／文案生成／文案评审 Agent | 内容理解、看点提取、文案生成、质量评审 |
| 人工 | 最终文案确认、事实核实、风险判断、问题记录、规则修改审批 |

最终文案必须经过人工确认。对于事实存疑和 P8 高风险边界，也必须转人工核实。

**日志与可观测性：** 每个节点记录四类信息

- 输入：当前处理的数据。
- 执行：调用的模型、工具及配置。
- 输出：模型或工具返回的结果。
- 判定：处理结论、问题码及后续流转方向。

通过完整日志实现任务回放、问题归因，并统计单任务调用次数、耗时和成本。

**持续优化闭环：** 同类问题第二次出现时，按成本从低到高处理

1. 优化提示词：明确模型的判断要求。
2. 补充案例库：沉淀 Bad Case 和优质示例，供后续检索。
3. 增加规则或程序校验：将重复问题转化为固定约束，减少对模型的依赖。
4. 调整整体流程：前面几种方式无法解决时，再考虑流程改造。

人工确认后的有效判断可以沉淀为案例，供后续任务检索复用。

**护栏与成本优化：**

- 定期评估重试、重写次数等限制是否仍有必要。
- 模型升级后，使用同一批样本重新测试。
- 重点判断护栏拦截了多少真实问题，以及移除后质量是否下降。
- 对已不再必要的限制及时精简，避免增加不必要的调用成本和处理时延。

# 三、测试与验证

## 1. 验收标准：什么样的推荐文案可以使用

**第一步：判定只有三档，每档一句锚点。** 不定锚点，两个人对同一条文案会判出不同结果。

| 判定 | 标准 | 锚点判据 |
|---|---|---|
| 可用 | 准确、清楚，能兑现视频主要内容 | 一处都不用改 |
| 勉强通过 | 基本可用但有明确瑕疵，必须写出瑕疵 | 只差局部一处，改完读者对视频的预期不变 |
| 不可用 | 不能使用，要写明读者可能误解之处 | 要换看点、补事实或改方向，改完读者预期会变 |

分歧高发在“勉强通过”与“不可用”之间，判断方法只有一句：**改掉这一处之后，读者对视频的预期会不会变。** 会变就是不可用。

**第二步：六个指标，分两条口径。**

| 指标 | 属哪条口径 | 目标 | 怎么算 |
|---|---|---|---|
| M1 首轮可用率 | 首轮 | *≥78%* | 首轮至少一条候选被判可用的任务 ÷ 全部任务 |
| M4 重写挽救率 | 首轮 | *≥35%* | 首轮全部失败、经自动重写后至少一条可用的任务 ÷ 首轮全部失败的任务 |
| M5 交付可用率 | 交付 | *≥85%* | 最终至少交付一条可用候选的任务 ÷ 全部任务（未产出计入分母） |
| M6 误放率 | 交付 | *≤5%* | 系统放行里被判“非可用”的 ÷ 系统放行数（勉强通过也算误放） |
| M7 机械丢弃率 | 交付 | *≤10%* | 被机械规则判否、但人工判可用的候选 ÷ 人工判可用总数 |
| 首推严格可用率 | 交付 | *≥50%* | 首推那条被判可用的任务 ÷ 全部任务 |

M6 按“非可用”算，不按“不可用”算：系统放行的候选被判勉强通过，业务上仍需人工改一笔才敢发，所以也算误放。这两个算法的结果能差十个点以上，不能混用。

**第三步：两条口径的候选范围不同，不能混着算。**

| 口径 | 用在 | 候选范围 | 为什么这样定 |
|---|---|---|---|
| 首轮口径 | M1、M4 | 该任务所有轮次、所有候选，含被机械判否的、含更早候选集的判定 | 被机械规则误杀的候选，如果人工评过，它的判定必须计入。否则系统的 bug 会变成“生成失败”，等于用自己的错压低自己的成绩 |
| 交付口径 | M5、M6、M7、首推 | 只用当前冻结的候选与当前路由 | 这几项问的是当前路由的表现，混入历史候选会把路由责任摊薄 |

**第四步：三个目标值是一条链上算出来的，不是分别拍的。**

> **M5 ≈ M1 +（1 − M1）× M4**
> 代入目标值：0.78 +（1 − 0.78）× 0.35 = 0.857 ≈ 0.85

含义是：首轮就能产出可用文案的任务占 78%；剩下 22% 里，靠定向重写再救回 35%；两者相加正好落在 85% 的最终供给上。三个数字互为约束，改一个另外两个必须跟着复核。

**第五步：金标准怎么判。** 人工是主标注，也是金标准；另用一个更强的模型做独立副标注（不看人工结论），两者一致性用 kappa 衡量。分歧单独记录、不合并处理——分歧本身就是信息，说明锚点还有没对齐的地方。kappa 低于 0.6 时，先对齐锚点样例再扩样本。模型不能替代人工判定。

**第六步：样本固定。** 用 20 条公开视频样本，按 10 个内容领域分层、每类 2 条抽取，选定后不换、不扩。每条锁定视频号、任务号、规则版本、模型版本和日期，保证跑多少次都能横向比较。

## 3. 模型选型：比较质量、成本与耗时

**先写用例，再选模型。** 哪个模型合适，由“哪些用例过”回答，而不是反过来。

**生成与评审分成两个实验**，因为一个要变生成、一个要变评审，混在一起两个都测不准：

| | 实验 A（生成） | 实验 B（评审） |
|---|---|---|
| 变量 | 生成模型 | 评审模型 |
| 冻结 | 评审模型、流程、提示词 | 生成结果整个冻结 |
| 做法 | 走完整流程 | 从已存结果重跑评审，不重生成、不触发重写 |
| 主指标 | 人工一次通过率 | 放行准确率、召回率、kappa |

混跑的代价是：变量不隔离（换评审会连带改变生成收到的输入）、成本相乘（3 个生成 × 4 个评审 = 12 组）、指标互相污染（生成质量被评审松紧掩盖）。

**候选与成本。** 生成侧首轮 3 个候选加 1 个参考臂（当前在用的模型），单价在 ¥0.20—0.23/条之间；评审侧同理 4 个。**成本差不到 ¥0.11/条，20 条差不到 ¥2.2，所以成本不构成决策因素，质量才是。**

**实测成本（当前配置）。** 一条视频走完全流程：谷时 ¥0.18、峰时 ¥0.35；中位 ¥0.15/¥0.30；最差 ¥0.50/¥1.00。每条视频平均 8 次成功调用、输入约 19.3 万 tokens、缓存命中率 34.9%。**成本口径按“每条可用文案”算，不按候选算**：按当前成品率折算，一条可用文案的成本是 ¥0.59—1.17。

**执行顺序：** 先用一个更强的模型做评审裁判的快筛，确认裁判本身合格 → 3 条冒烟 → 20 条 × 4 个系统横评 → 人工判定 → 出冠军。裁判不合格，生成的结论一并作废。

**当前状态：** 成本对比已完成——同一批实测，强模型 *¥0.66/条*、Flash *¥0.177/条*，差约 *4 倍*，且 Flash 那批 0 条技术失败。质量横评在跑到第 17 条时因额度用尽中断（HTTP 402），17 条不足以得出结论，**该横评未完成**。按当前进度，模型选型不构成效果验证的前置条件：它影响的是成本，而当前的瓶颈在交付率，两者不相干。

## 4. 效果验证：简单链路对照、影子运行与后续线上测试

**先分清三本账。** 出质量数字之前，要说清用的是哪一本：

| 类型 | 规模 | 能说明什么 | 不能说明什么 |
|---|---|---|---|
| 自动化回归用例 | 46 个文件、555 个测试函数（展开 658 个） | 改动没把原来对的地方弄坏 | 文案质量好不好 |
| 可计分人工判定 | 156 条（可用 65／勉强 27／不可用 64），跨 11 个批次 | 固定批次与版本下，可用率是多少 | 跨批次合并算一个总可用率 |
| 仅定位人工判定 | 26 条（单独账本） | 某个具体问题错在哪 | 拿来算可用率 |
| Bad Case 档案 | BC01—BC09，21 个字段 | 一个典型问题从发现到修复的全过程 | 反映整体质量水平 |

那 156 条跨 11 个批次、来自不同模型版本，**只能作为“用例规模”引用，不能合并算成一个可用率**。要出质量结论，必须固定批次、固定版本。

验证分三层，从能控制变量的地方开始。

**第一层：简单链路对照（2026-11-02，后经口径审计）。** 基线与完整链路使用同一批 40 条视频，但每臂每视频最多只送评一条文本，且其中 4 条基线文本未送评，不能据此计算两臂完整的 40 视频通过率或三候选成功率。

| 评估对象 | 人工严格判为可用 | 口径说明 |
|---|---|---|
| 基线已评文本 | 26/36，72.2% | 仅限已评文本；另 4 条未送评 |
| 系统实际首推 | 9/16，56.3% | 仅限有首推的任务 |
| 系统首推，固定全部任务分母 | 9/40，22.5% | 无首推的任务计入分母 |

系统未推荐的 24 个任务中，14 个处于待核实状态，6 个停止任务仍有抽样文本，另 4 个无文案；不能将 24 个都说成未产出。该批用于问题诊断和调优，不是独立验证集。现有结果提示首推供给不足，但由于样本和送评口径限制，尚不能断言完整链路整体优于或劣于基线。

**已跑的一批（早期诊断基线）。** 2026-11-01 的 20 条批次是早期唯一有真实人工判定的数据：20 条中 18 条产出标题、2 条未产出；严格可用 30%（6/20）、含勉强通过 55%（11/20）。这一批由修复前的版本产出，且与后续批次只有 3 条视频重合，只能作为诊断参考，不能用来描述当前系统，也不能与本节的 40 条批次合并计算。

# 四、Bad Case 回收与优化

## 1. 问题定义：哪些推荐文案和运行结果属于 Bad Case

**先定契约。** 用户只看推荐文案、不看视频时形成的内容预期，必须能被视频实际内容兑现。这条契约被破坏，就是 Bad Case。

**三条底线：** 可兑现（文案承诺的内容，视频里真有）、合政策（不违反业务政策）、可交付（准确、清楚、能直接用）。违反任何一条，无论它停在哪一层、被谁拦下，都计入。

**具体情形清单。** 按出问题的位置列，共 12 类：

| # | 位置 | 具体情形 |
|---|---|---|
| 1 | 材料 | 转写缺失、OCR 中文占比低、可写内容因材料质量被漏抽 |
| 2 | 理解 | 漏抽关键事实，或抽错主体、数字、时间 |
| 3 | 理解 | 编造事实：把历史写成当前、把局部写成全部、把转述写成事实 |
| 4 | 理解 | 把陈述改写成原片没有的因果、目的或悬念 |
| 5 | 看点 | 抓了画面里的场景，漏掉视频真正在做的行为 |
| 6 | 看点 | 主旨选偏，文案围绕的看点不是这条视频的重点 |
| 7 | 表达 | 超长、丢必要限定、句子读不懂、内容空泛 |
| 8 | 表达 | 制作元素（字幕、弹幕、BGM、封面）进入文案 |
| 9 | 表达 | 归属写法违规：该带平台前缀没带，或不该带带了 |
| 10 | 评审 | 放水（该拦没拦）或过严（可用被判死） |
| 11 | 程序 | 判据假阳性、规则之间口径冲突、路由把候选丢掉 |
| 12 | 运行 | 技术失败、超时、停在待核实却没记录原因 |

**运行结果也算。** 第 11、12 类没有产出错误文案，但同样让一条视频拿不到可用推荐文案，一并计入。

**判断标准** 是七条：正确、完整、一致、合规、依据可追溯、可直接使用、该转人工时转了。

**三类不算：**

- 视频本身没有可写内容、系统按规则停下并记录了原因——这是正常停止，不是错误。
- 首轮不合格、但重写后救回——这属于重写机制在正常工作。
- 人工判定本身有分歧、锚点还没对齐的——先解决口径，不记问题。

**不看出错位置，看后果。** 同一类错误停在不同位置，性质完全不同：一条编造情节被程序拦下，和同一条被人工驳回，错误类型相同，严重程度差一级。所以定级依据是“停在哪一层、后果多重”，位置只用来回答“改哪里”。

## 2. 问题发现：人工反馈、运行日志、规则拦截与抽样检查

### 渠道一：人工反馈

**当前处于测试阶段，尚未接入生产审核。** 测试中，人工对推荐文案作可用、勉强通过或不可用判定，并记录问题说明；这些反馈可用于定位问题、整理案例和验证优化效果。

原业务的审核流程只有通过或驳回，不填写驳回原因。未来如果沿用这一流程，系统即使保存了驳回结果、推荐文案、视频材料和版本信息，也只能知道“被驳回了”，**不能据此确定为什么被驳回**。已有评审意见和程序错误码可以辅助排查，但不等于人工驳回理由。

**上线后的反馈方案：** 审核人员驳回时选择主要问题类型，包括事实与信源、看点偏差、表达问题、业务规则问题或其他；选择“其他”时可补充简短说明。一条文案存在多个问题时，先选择主要问题，后续复核可补充。系统可根据评审结果建议类型，但由审核人员确认或修改。

系统同时保存视频材料、被驳回的推荐文案、审核结果、问题类型和相关版本。规则运营对高风险、重复出现及抽样选中的案例进一步复核，补充具体原因、证据和责任环节，再决定是否用于规则优化或案例库。审核人员选择的问题类型是定位线索，不等于最终根因。

该反馈机制为**已确定的上线方案，尚未实施**；上线前需验证类型覆盖情况，以及新增操作对审核耗时的影响。

### 渠道二：系统自动回收

自动回收不能凭空想，办法是沿着链路逐节点问两句话：**这一步会以什么方式错？错了会在哪里留下痕迹？** 痕迹在哪，回收点就在哪。

| 节点 | 怎么错 | 留下什么痕迹 |
|---|---|---|
| 读材料 | 素材缺失、空转写、OCR 质量低 | 输入质量分级、材料不足标记 |
| 理解 | 漏抽或编造事实 | 事实条数异常、引用不在允许范围 |
| 边界 | 把不该写的判成可写、丢必要限定 | 边界判定结果、必需限定清单 |
| 看点 | 主旨选偏 | 看点候选与被排除项 |
| 生成 | 超长、丢限定、制作元素进文案 | 程序校验错误码 |
| 评审 | 放水或过严 | 评审结论与人工判定不一致 |
| 交付路由 | 候选去向错、成组丢失 | 每条候选的最终去向 |
| 人工 | — | 三档判定加终稿 diff |
| 全链路 | 技术失败、业务停止 | 失败原因码 |

**自动回收的错误先进问题台账，不进案例库。** 案例库的门槛是“人工确认过对错”，自动拦下的还没过这一关。它按周看各错误码的数量和趋势，够了再往上升级成案例。

## 3. 问题分类与分级

Bad Case 按出错环节分类，确定修改位置；按影响程度和流出范围分级，确定处理优先级。

| 问题环节 | 典型表现 | 修复方向 |
|---|---|---|
| 材料 | 转写缺失、OCR 质量低、视频信息不足 | 补充或重新获取材料 |
| 理解 | 关键事实遗漏、主体或时间理解错误 | 调整信息提取和理解要求 |
| 看点 | 主旨选偏、遗漏视频核心行为 | 优化主旨和看点选择 |
| 表达 | 超长、缺少限定、表述空泛 | 调整生成要求或表达规则 |
| 评审 | 不可用文案被放行、可用文案被拦截 | 调整评审标准或判定逻辑 |
| 程序 | 规则误判、候选丢失、任务异常 | 修复程序或流程 |

同一案例可能涉及多个环节。定位时以最先出现问题的环节为主要修复位置，同时检查后续环节为什么没有发现问题。

| 等级 | 判断标准 | 处理方式 |
|---|---|---|
| P0：严重事故 | 高影响问题穿过全部防线并进入业务，或造成实际损失 | 立即止损，保留记录并组织复盘 |
| P1：高优先级问题 | 高影响问题被人工发现，或关键防线出现系统性失效 | 逐例分析，优先修复并验证 |
| P2：一般问题 | 中等影响问题被人工发现，或问题被自动防线拦截但反映出质量缺陷 | 纳入台账，结合出现频率安排修复 |
| P3：轻微问题 | 影响较低的表达瑕疵或非关键环节异常 | 汇总观察，按周期优化 |

当前系统仍处于测试阶段，尚未接入推荐发布，因此暂不存在因本系统上线发布形成的 P0 事故。分级用于安排处理顺序，具体还需结合影响范围、重复情况和现有防护措施判断。

## 4. 问题记录

每条 Bad Case 需要回答：发生了什么、系统如何处理、问题出在哪里、修复后结果如何。

| 记录内容 | 主要信息 |
|---|---|
| 问题定位 | 案例编号、发生时间、视频及任务标识 |
| 系统表现 | 视频材料、推荐文案或任务状态、评审结论与候选去向 |
| 人工判断 | 人工判定、问题类型及判断依据 |
| 问题归因 | 出错环节、影响程度、可能原因及关联版本 |
| 修复验证 | 修复方案、测试结果和当前状态 |

记录应保留足以复现问题的信息。无法取得或不适用的字段应注明原因，不能补造：例如技术失败时没有推荐文案，人工驳回时也不一定存在修改终稿。同一视频存在多个独立问题时，应分别记录或分别跟踪。

## 5. 问题定位与修复

从系统结果和人工判断的差异入手，沿链路向前追溯，找到最早出现问题的环节。例如，文案没有体现视频重点，可能是理解时遗漏了事实，也可能是生成时没有采用正确看点，只修改最终文案不能避免同类问题再次出现。

| 问题类型 | 典型表现 | 修复方向 |
|---|---|---|
| 材料或理解问题 | 关键事实缺失、主体或时间理解错误 | 补充材料，调整理解和提取要求 |
| 看点或表达问题 | 看点选偏、文案新增视频未表达的含义 | 优化看点选择、生成要求和语义评审 |
| 规则问题 | 缺少必要约束，或已有规则执行不正确 | 补充规则，或修复规则执行逻辑 |
| 程序问题 | 程序误判、候选丢失、任务异常停止 | 修改判定条件、交付路由或异常处理逻辑 |

修复应针对根因选择影响范围适当的方案：明确的规则缺失需要补规则，程序路由错误需要改代码；涉及复杂语义判断的问题，可考虑调整提示词或评审方式。

## 6. 修复验证与经验回流

修复后从两方面验证：一是使用原视频和可比测试条件复测，检查原问题是否解决，并记录版本差异；二是使用相关正常样本和已有回归用例，检查修改是否引入误判。

| 去向 | 内容 | 用途 |
|---|---|---|
| 案例库 | 经人工确认、有参考价值的正确或错误写法及适用条件 | 供后续生成时检索参考 |
| 回归测试集 | 问题案例、相关正常样本及可自动判断的约束 | 后续修改时检查复发和误伤 |

并非每条案例都有修改后的正确文案；只有驳回结论时，先记录问题和判断依据，不补造正例。正式业务规则优先于历史案例；检索不到或案例不适用时，按正式规则继续处理。样本级正反例回归集仍需建设。

## 7. 持续监控与复盘

每周按问题环节和类型汇总，关注高频问题、相同根因是否复发，以及每项修复处于待定位、待修复、已修复待验证还是验证通过。高风险问题优先控制风险并保留记录；一般问题结合影响程度和重复情况安排处理。

BC06 的人工意见提到“之前已经说过的问题”，提示需要核查历史反馈是否已形成规则、规则是否生效，以及两次问题是否属于同一根因。当前案例数量有限且并非随机抽样，只能用于识别问题和制定优化方向，不能直接代表系统整体问题分布。

## 8. 典型案例：理解边界、看点提取与规则覆盖

以下案例分别说明系统在理解视频内容、选择核心看点、遵守业务规则时出现的问题及优化方向。

### 8.1 采访表态被包装为原因分析（BC07）

| 分析维度 | 具体内容 |
|---|---|
| 视频内容 | 赛后采访中，受访者萨戈夫表达自己不认为已强于德文，并称德文是传奇。材料含他对比赛和自身判断的解释；这些解释是否足以回答“为何称德文是传奇”，不能简单视为确定事实。 |
| 系统输出 | “赢过德文一次，萨戈夫为何仍称他传奇”；候选级评审通过，但任务最终因引用结构审计问题转人工，**并未最终推荐**。 |
| 人工判定 | 不可用：“视频展示了萨科夫受采访时的真实回应，而不是讲他为什么称德文是传奇。” |
| 问题归因 | 原评审把“不认为自己更强”的解释当作“为何称其传奇”的答案。人工认为这把受访者的个人表态包装成对传奇地位的原因分析，偏离采访重点；这不等于断言视频没有任何解释。 |
| 修复 | 强化生成和评审对表态视角、提问对象与主旨的核对；修复评审明确判定未兑现但状态误写通过时的程序兜底。不以疑问词机械拦截。 |
| 复测结果 | 换用 Evolink 的 DeepSeek V4.1 Flash 重跑原视频，系统再次生成同一句文案并判为通过、进入人工评审，人工复核仍判不可用。同一批正常新闻样本的三条文案全部被系统拦下，人工却判可用。 |

当前状态：**问题尚未修复**。程序兜底只在评审明确写出“未兑现”时生效，本次评审把两项判断都写成“已兑现”，兜底没有触发条件。复测同时暴露出误拦：正常叙述类文案被“来源归属”和“必要限定”规则成批拦下。原视频音画本次仍未能独立核对，访谈细节以用户说明及原始材料为依据。复测记录见《BC07 真实模型复测报告》。

### 8.2 看点提取偏差：识别场景，却遗漏核心行为（BC09）

| 分析维度 | 具体内容 |
|---|---|
| 视频内容 | 博主从东北搬到惠州后走访当地菜市场，记录并比较买菜价格。 |
| 系统输出 | “博主逛惠州菜市场，肉菜水果明码标价”，系统评审判定通过。 |
| 人工判定 | 勉强通过：视频重点不是商品明码标价，而是比较价格。 |
| 问题归因 | 系统识别到了菜市场和商品价格等场景信息，却没有突出人工认为更重要的比价行为。 |
| 修复方案 | 看点选择时同时识别场景和主要行为，结合材料判断核心内容；评审时检查文案是否覆盖核心看点。 |

当前状态：修复方向已记录，尚未完成原案例复测。

### 8.3 规则缺失：制作元素进入推荐文案（BC08）

| 分析维度 | 具体内容 |
|---|---|
| 视频内容 | 一条街头篮球单挑视频中，画面带有挑衅式字幕，主体内容是球场对抗。 |
| 系统输出 | 三条推荐文案均出现“字幕”；其中两条通过系统评审，一条进入重写。 |
| 人工判定 | 三条均不可用，理由是推荐文案不能出现“字幕”。 |
| 问题归因 | 生成和评审环节未有效覆盖这项业务要求，将制作元素写入文案。 |
| 修复方案 | 核实制作元素规则的适用范围，纳入生成和评审依据，并以问题案例和合规样例检查识别效果及误伤。 |

当前状态：修复方向已记录，尚未完成原案例复测。

### 8.4 案例结论

三个案例分别涉及内容一致性、核心看点选择和业务规则覆盖，不能统一归因于生成模型。后续需针对对应环节优化，并复测原视频及相关正常样本；三个案例均尚未完成修复验证，暂不能宣称问题已经解决。其中 8.1 已完成一次真实模型复测，结论是问题仍在，并额外发现同类误拦，说明修复需要改判断机制，而不只是增加提示词约束。


# 五、预期业务表现

本章描述完成产品建设、验证与业务接入后的目标状态；文中斜体数字为拟定目标，并非当前实测结果。实际效果以固定样本验收和上线后的业务数据为准。

## 1. 覆盖范围与人机分工

系统接入短视频推荐文案生成和审核流程，围绕视频理解、文案生成、质量评审与问题回收提供支持。审核人员集中查看推荐文案、视频材料依据和系统风险提示，负责最终通过或驳回；存在事实或规则疑问的内容转人工核实。

审核人员驳回时选择主要问题类型，规则运营结合文案、视频材料及系统记录复核重点案例，并将确认后的经验用于规则、案例库和回归测试集的优化。

## 2. 质量表现

在拟定的 *200 条*公开视频验收样本中，首轮至少产出一条可用推荐文案的任务占比达到 *78%*；首轮未产出可用文案的任务，经定向重写后，挽救率达到 *35%*。最终至少交付一条可用推荐文案的任务占比达到 *85%*，首推严格可用率达到 *50%*。

系统放行的推荐文案经人工复核，放行准确率达到 *95%*，合格召回率达到 *90%*。事实与信源、核心看点及业务规则问题得到更充分的识别；对于材料不足或存在风险疑问的内容，保留人工判断，不以提高通过率替代质量控制。

## 3. 效率表现

单任务审核耗时由目前约 30 秒缩短至 *24 秒*，降低 *20%*。审核人员可同时查看文案、视频主旨、材料依据和风险提示，减少查找与核对信息的时间；驳回类型选择、异常处理等新增动作均计入任务总耗时。

在视频量、人员投入和审核时间等条件满足产能要求的情况下，目标是将原业务审核覆盖率从 80%—90% 提升至 *100%*。覆盖率提升不仅依赖单条审核提速，还需结合实际任务量和有效审核工时验证，不能仅凭 20% 的耗时下降推定全量覆盖。

## 4. Bad Case 回收与风险控制

审核驳回时记录主要问题类型，规则运营复核高风险、重复出现和抽样案例，明确问题原因及修复位置。已确认的案例按适用场景和处理方式沉淀，并在规则更新时复测原案例、同类变体和历史正确样本。

与不使用案例复用的对照组相比，同根因问题复发率目标下降 *30%*；规则更新可能带来平台生态安全风险时，在发现后 *24 小时*内给出初步原因和方案；其他规则漏洞目标在 *72 小时*内完成修复。上述时限和效果均需通过实际运行验证。

## 5. 业务结果与验证

通过提高可用文案供给、缩短审核时间和减少同类问题重复处理，系统预期提升审核覆盖与规则维护效率，并为后续推荐文案采用及用户观看体验提供更稳定的内容供给。

质量指标先在固定的 *200 条*样本上验收；审核耗时、覆盖率和问题复发通过影子运行或实际业务记录，与原流程或对照组比较。推荐文案采用率、点击率和观看时长等下游指标须在正式接入并完成对照测试后评价，现阶段不预设具体提升幅度。
