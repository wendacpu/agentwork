# R01 评审模型选型：题库与实验方案

> 状态：**离线准备；尚未启动模型测试，也未批准候选、预算或正式验收集**。本文约束本次评审模型选型；历史 [模型选型方案](model-selection-plan.md) 的旧视频、模型名单、预算和结论不能直接作为本次执行依据。已有评审系统仍在修改，固定评审版本后才能执行。

## 1. 目标与范围

评估模型能否区分人工认为可用、勉强、不可用的标题，而不是一味调严或调松。首阶段固定已有标题，**只比较 R01 评审**，不重新生成、不自动重写、不变更历史任务；后续再另行设计端到端实验。模型候选、价格、预算和正式运行须事前确认并授权。

评审直接比较和流水线落地是两个测试：A. 同一模型输入与输出契约下的评审能力；B. 将评审输出交给相同程序门禁与路由后的候选最终状态。A 不可误称系统端到端结果；B 不可把程序拦截全归因于模型。明确记录抽取模型 verdict 的规则和 G1–G3/Q1–Q3 结果，勿只把推荐状态当评审 verdict。

## 2. 题库与来源

本地开发题库目录：`runtime/review_selection_development_v2/`（runtime 被忽略，不随代码提交）。构造命令 `python3 scripts/build_review_selection_bank.py`；源库只读，输出如已存在不同内容则拒绝覆盖。

- `blind_inputs.jsonl`：76 道候选，含匿名题目 ID、视频材料和待审标题；**没有人工标签、人工理由、历史判定或路由**。同一视频多个标题会共享素材，不能当作独立视频。
- `labels_provenance.jsonl`：人工判断及理由、原始任务/候选/标题 SHA-256、素材哈希、系统历史状态、引用、机械代码及标签来源。仅评分程序和获授权的人使用，绝不作为评审模型输入。
- `manifest.json`：来源路径、题量、分类与输出校验哈希。检查素材与标题哈希再运行；不得对历史反馈库、任务库回写。

来源是 `runtime/cost_ab_20261105/agent.db` 与其隔离反馈库，以及 `runtime/cost_ab_supplement_review` 的补评清单与反馈库。历史主键 `candidates` 存在跨任务同名覆盖，使用 `candidates_by_task` 并按任务 ID、候选 ID、标题 SHA-256 对齐，不按候选 ID 单独关联。

目前 20 视频、76 候选：原批冻结 48、原批诊断 2、补评 26；人工可用 33、勉强 13、不可用 30。另标识超 20 字的 10 条；补评均为内容判断，标签不可假装与原批交付口径完全相同，尤其超长 10 条的人判理由涉及字数，不能直接当纯语义负例。各分组不代表平台自然分布；这是针对历史问题富集且单人标注的开发库，不是独立测试集。

原批 48 条的旧系统候选级统计：通过 36 条中可用 26 条，精准率 26/36=72.2%；不含待核，人工可用 29 条中通过 26 条，召回率 26/29=89.7%；待核 6/48=12.5%。这是候选最终状态（包括机械与程序门禁），不是纯模型 R01 分数，也不能直接与新模型单独评审混比。

## 3. 数据隔离和防泄漏

这 20 条视频及其标签已经参与过调试、问题复盘和提示词讨论。**整库仅供开发、冒烟、定性诊断，不得切一部分后声称是独立验收**；未来独立集需选未接触、未用于调参的视频，先查任务历史、案例、作者/视频重复，按视频分组并冻结。素材是否完整及视频近重复仍需另行检查。

模型调用端只能加载盲输入及事先批准的同一份规则/系统输入。禁止注入人工 verdict、理由、历史模型结论、路由、题号含义、历史案例中关联答案。题库标识仍含视频 ID；盲文件是对**标签**盲，不保证对视频身份或互联网上公开视频盲。来源备注留在答案文件，结果计算后才关联。若题目由不同来源构造，须检查是否存在重复或标签冲突，不靠事件日志计数。

输入模式需在运行前决定：①统一原始材料的独立评审；②冻结同一版上游结构和机械检查的系统内 R01 复评。当前盲输入只覆盖①的原始材料与标题，**不是完整 R01 请求**。②须待评审代码完成后从同版本按任务+候选重建上游 state、引用和必要规则，并单独冻结哈希；未经逐条校验不得假称可直接重放。程序检查不作为模型正确性的真值。

## 4. 指标定义（本次预先锁定）

单位是独立候选；每个任务与标题哈希绑定，非首推不自动视作拦截。主要严格口径：`approved` 是可用；`marginal` / `rejected` 非严格可用。另报宽松口径：`approved` + `marginal` 为可用；两种口径并列，不选有利的报。补评超长项的内容/字数混合标签单独列出，不并入纯语义模型主比较，直至标签口径明确。

| 指标 | 计算 | 用途 |
|---|---|---|
| 精准率 | 明确通过且人判可用 / 全部明确通过 | 放行质量；待核不计分母 |
| 召回率 | 明确通过且人判可用 / 人判可用且模型明确通过或不通过 | 是否漏掉好标题；待核不计分母 |
| 待核率 | 模型待核 / 有效评审数 | 防止把难题全转待核 |
| 有效评审覆盖率 | 有可解析且符合契约的评审 / 应评总数 | 技术失败和缺失单列，不当作待核、通过或自动剔除后当全量 |
| 失败率 | 非法结构、超时、无法调用等失败 / 应评总数 | 报各原因及重试，零分母为不可计算 |
| 通过占比 | 模型明确通过 / 应评总数 | 显示过松/过严，不直接代表质量 |
| 风险漏放 | 人工确认的高风险负例中模型明确通过数 / 有风险标签且有效评审数 | 当前只有单人理由，不自动把拒绝等同事实风险；需单独人工核实风险标签 |
| 单题成本与耗时 | 实际请求含重试的输入、缓存命中、输出用量及账单；延迟报中位数和分位数 | 报币种、价格时间及不可得费用；不能按历史报价臆算 |

按视频聚类报告题数和视频数；同视频相关候选不能当独立样本。报告待核和失败的人工标签分布、各类候选数，显示选择性偏差。若对失败/待核给敏感性上下界，单独标为假设场景，不替代上述已确认口径。单人标签不能计算标注者间 kappa；一致性需要独立第二位标注者及同题配对。

业务指标 M1/M4/M5/M6/M7 和首推严格可用率是任务或交付层指标，与上面候选模型评审指标分开；固定标题重评不能算完整端到端重写挽救率。M5 包含待人工查看，但必须冻结何谓实际送达；自动放行另报。M6 只算实际自动放行的候选；M7 仅机械拦截且需要被拦候选有人评。未确认分母和未评项不得当成功或失败。

## 5. 正式运行前冻结的实验条件

1. 核查评审系统修改已完成、测试结果与提示词/schema/规则版本；锁定代码提交/工作树哈希、规则包与配置，禁止进行中改变。
2. 明确评审模型名单、版本、provider、上下文上限、结构化输出、温度/推理设置、每项超时、重试、单题或批量；公平对比统一模式，模型不支持时记兼容性差异，不静默调整。
3. 每个模型读取同一题目、同素材、同截断规则和无人工答案的输入；检查长输入是否被模型或网关截断。相同视频分组及缓存冷热条件需记录，必要时随机或交错运行，报告顺序和批次。
4. 预先锁定 strict / lenient 两套判定映射；语义复核中保留 needs_review、reject、revise 的差异，约定冲突/缺字段不自动通过。各模型单独隔离输出，保留原始响应和解析失败；不可暗中重试至成功。
5. 先对少量不计质量结论的题做格式与权限冒烟；实际运行前重新查询对应服务商价格，并设总请求、重试、费用上限；预算/候选名单须用户批准。此前一次 SiliconFlow 实验授权不等于未来多模型测试授权。
6. 未指定且未验证独立验收集前，只可说开发集现象，不能宣布冠军、显著改善或预测业务表现；同家族约束适用于实验臂还是最终生产组合，及质量/成本权重，均待用户决定，不沿用冲突的旧预算与权重。
7. 如运行产生需要人工判断的新标题测试，必须按仓库规定创建独立评审台、保留失败/缺槽及全部状态，验证入口后交付；不以机器结论替代人评，不写回旧批。
