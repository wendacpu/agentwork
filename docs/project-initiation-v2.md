## 0. 一句话

这是一套面向短视频推荐文案生产与审核场景的质量优化 Agent，主要解决模型生成质量不稳定、人工质量审核成本高、历史 Bad Case 难以有效复用的问题。通过多候选生成、多维打分评审、低分反馈重写及案例记忆机制，构建文案生成、质量评审、反馈优化的闭环，提高合格文案的产出率与人工审核效率，并通过历史案例复用持续改善生成质量，降低规则维护成本。

## 1. 为什么做：业务本质 → 部门目标 → OKR

### 1.1 业务本质：瓶颈不在"能不能生成"，在"能不能被可信地判断"

规模事实（取自 [product-design-draft.md](_archive/product-design-draft.md) §6.5 与 [experiment-preregistration.md](experiment-preregistration.md) §6.5 的测算）：

- 每天 700～800 万条视频，其中约 80% 符合初期标题撰写要求，对应 **560～640 万条／日**的适用范围；
- 原人工审核单条约 **45 秒**；
- 两者相乘就是这门生意的天花板：若 10% 的条数需要人看 ≈ **937 人**，1% ≈ 94 人，0.1% ≈ 9 人。**待审率必须压到 0.1% 量级才有意义。**
- 95% 的放行精度放在百万级量级，等于每天约 **30 万条错误放行**——自动放行要的是 99.9%+。

这是一门"负规模效应"的生意：产量每翻一倍，人工审核和规则维护的成本就同步翻一倍，而文案质量不会因此变好。传统规则能管禁用词、长度、必要字段这些确定性问题，管不了"这条标题有没有抓住这个视频真正的看点""是不是把边角事实当成了主轴"。

**所以规模化的瓶颈不是生成能力，是可信的判断能力。** 这也是这件事值得用 AI 重做的理由：让判断不再依赖人工逐条看，把人的注意力从"全量筛选"压到"高风险确认"上。第 1 条视频和第 600 万条视频，共用同一套判断标准。

### 1.2 部门目标

把模型判断用在"筛"和"定位"上，把省下的人工注意力与规则维护成本，换成更高的合格供给率、更低的单条可用成本。

### 1.3 OKR（两个）

| # | OKR | 口径 | 状态 |
|---|---|---|---|
| O1 | 预注册样本上**严格可用交付率 ≥50%** | 固定分母（无标题＝失败，不剔除），"可用"单独数、不与"勉强通过"合并 | 【待验收】 |
| O2 | **每千条人审分钟**较 45 秒／条参照**下降 ≥30%** | 人工判定总时长 ÷ 交付条数 × 1000；实测而非模型耗时 | 【待验收】人工耗时未实测 |

护栏（不作为 OKR，但一旦击穿就回退）：放行准确率 ≥95%、合格召回 ≥90%、误放 ≤5%、严重事实风险 0、超长流入率 0。

> 口径来源：[eval-spec.md](eval-spec.md) §1、[experiment-preregistration.md](experiment-preregistration.md) §6.5。O1 用严格率而非"含勉强率"，是因为把不可用改判成勉强通过会被算成质量提升。

## 2. 旧方案的结构性问题

### 2.1 原链路

标题生成：视频信息提取 → Prompt 规则约束 → 模型生成标题 → 模型基础审核 → 人工质量审核 → 通过／驳回。**审核不通过的文案直接作废，不进入重写流程。**

规则迭代：人工抽样巡检 → Bad Case 识别 → 问题分类与归因 → 运营提炼规则 → 小流量测试 → Prompt 更新 → 后续生成验证。

### 2.2 原稿列出的四条痛点

- 生成质量不稳定，规则难以覆盖复杂场景：固定 Prompt 和通用规则面对跨垂类内容、复杂看点、隐性表达规范时，反复产生事实不准、看点不突出、吸引力不足。
- 审核失败直接驳回，缺少自动修复机制：模型审核给不出问题定位和修改建议，造成内容供给损失。
- 人工审核效率低：模型只做基础合规与表达规范审核，标题质量判断仍靠人自行识别问题、自行筛选排序。
- 规则维护成本高：迭代靠人工抽检、归因、提炼、改 Prompt，周期长；历史 Bad Case 复用不足，相似问题反复出现。

### 2.3 合起来看，这是三个结构性缺陷

四条不是可以分别修的四个问题，是同一件事的三个病根：

1. **优化单位错了。** 原链路的优化单位是"单条文案是否合规"，所以每次迭代只能往 Prompt 里加一条规则；但真正要优化的量是**"给定审核能力下，一批视频里能产出多少条合格文案"**。单条最优 ≠ 批次最优——一条文案被驳回，损失的不只是这条文案，还有已经花掉的生成、审核和人工判断。
2. **判断不产生资产。** 审核的终点是"通过／驳回"，人工判断用完即散。同一类问题第二次出现，系统仍从零判断；老员工的经验留在人脑里，不在系统里。
3. **审核是终点，不是反馈起点。** 驳回即作废，"哪里不行"没有变成"下一步怎么改"。

**一句话：这不是模型精度问题，是优化单位和反馈路径错了。**

## 3. 把问题拆成一串待回答的子问题

原稿缺这一节。这串问题后面直接对应三个 Agent 的分工、60 条用例的分组和两层结构。

**单条视频维度（这条文案能不能交付）**

1. 哪些视频会生成跑偏？——材料不足、主旨不明、事实待核、政策风险。
2. 跑偏发生在哪一层？——理解、可写边界、看点选择、表达、评审。
3. 为什么在这一层失守？——材料缺、规则缺，还是案例缺？
4. 给一批材料，什么条件是"能写"的，什么条件必须停？
5. 同一件事，怎样写出三条不像通稿、又都能兑现视频的候选？
6. 哪些判断可以交给程序（长度、前缀、引用、政策词），哪些必须语义评审？

**批次与全局维度（这批视频的资源和注意力怎么分）**

7. 人工每一次"可用／勉强／不可用 + 理由"怎样变成下一次可检索的经验？
8. 出了事故，怎么定位它是在哪一层、哪一版、哪一句上丢的？
9. 调用预算与人工注意力有限，哪些视频值得多花一轮重写，哪些应该早停转人工？

1–6 是单条质量层，7–9 是全局分配与复盘层。

## 4. 架构决策：为什么在确定性 Workflow 里嵌 Agent

### 4.1 为什么不是纯规则

1. **视频理解与质量判断有很强的语义复杂性，固定规则穷举不了。** 标题、OCR、Caption 要综合，才能识别主体、核心事件、结果与看点，同时判断表达是否有吸引力、是否符合事实。同一个视频可能跨多个垂类，要叠加不同的撰写要求；规则引擎能处理禁用词、字符长度，处理不了看点提炼与主观质量评估。
2. **质量优化需要基于反馈动态调整。** 评审不只判"过／不过"，还输出扣分原因和修改建议；生成侧按反馈定向重写，形成有限轮次的动态优化。系统检索人工确认过的历史案例，为后续生成提供参考，减少对持续补细粒度规则的依赖。
3. **为什么现在做。** 现有大模型已具备较强的文本理解、结构化输出和指令遵循能力，为看点提取、多维评审、反馈重写提供了实现基础；但本项目尚未验证具体模型在这类任务上的能力与成本拐点，所以第一阶段先用独立人工评测、成本与延迟测试判断方案是否达标。

### 4.2 Agent 的使用边界（不是所有节点都该是 Agent）

- 基础规则校验：禁用词、长度、必要字段等确定性判断 → 程序规则。
- 质量路由：按评分、硬性门槛和重试次数走固定条件分支 → 程序。
- Memory 检索：结构化标签 + 相似度检索，不需要独立 Agent 决策。
- Case 入库：结构化处理 + 人工确认，避免未经验证的模型判断污染案例库。

生成与评审用大模型处理语义判断和反馈优化，其余优先确定性 Workflow，以控制成本、延迟和不确定性。**两条硬边界**：生成 Agent 不决定最终放行，它只能按评审反馈改文案；评审 Agent 不改文案，它只判质量、给理由，把结果交给确定性路由程序。这样减少职责重叠和自我验证风险。

> 产品名叫 Agent，节点不都是真 Agent——五种能力类型（理解／生成／评审／程序裁决／人工）在 [product-design-draft.md](_archive/product-design-draft.md) §4.6 有明确划分。

### 4.3 两层结构

| 层 | 解决什么 | 现状 |
|---|---|---|
| 单条视频维度 | 这条文案能不能交付：理解 → 可写边界 → 看点 → 生成 → 独立评审 → 定向重写 | 【已有机制】 |
| 批次／全局维度 | 这批视频的调用预算、重写轮次与人工注意力怎么分配；什么情况熔断转人工 | 【待建设】当前只有每任务固定上限 |

### 4.4 四步闭环

**监控**（材料与风险体检，判断这条视频能不能写）→ **规划**（主旨、看点与交付策略）→ **执行**（生成／按缺陷定向重写／独立评审）→ **复盘**（人工判定 → 案例回流与缺陷修复）。四步都落在同一套任务记录和事件日志里，不把判断散落在各处规则里。

## 5. 先定义"问题"，再做归因

### 5.1 什么叫一条"可用文案"（三档 + 锚点）

| 判定 | 标准 | 锚点判据 |
|---|---|---|
| 可用 | 准确、清楚，能兑现视频主要内容 | 不用改一处 |
| 勉强通过 | 基本可用但有明确瑕疵，必须写出瑕疵 | 只差局部一处，**改完读者预期不变** |
| 不可用 | 不能用；写出读者可能误解之处 | 要换看点／补事实／改方向，**改完读者预期会变** |

分歧高发在"勉强 vs 不可用"，判法是问一句：**改这一处之后，读者对视频的预期会不会变？** 会变 → 不可用。

### 5.2 归因：先定位失守层，再谈怎么改

不是"没写好就重写一遍"，而是沿服务路径找痕迹：

材料层（ASR/OCR 是否够）→ 理解层（主旨、事件、语义单元）→ 边界层（哪些能写成事实、哪些必须限定或排除）→ 看点层（主看点是否 core，有没有把边角事实当主轴）→ 表达层（长度、前缀、问号、元信息框架）→ 评审层（误放／误拦）。

评审用 G1–G4 与 Q1–Q3：G1 事实与断言许可、G2 已批准业务政策、G3 内容交付与承诺、G4 机械约束（长度／格式／有效引用，程序侧）；Q1 表达清晰度、Q2 信息价值、Q3 观看吸引力。每个问题都要能回指到具体节点（如 `rollback_to: N07`）。

**真实的一类 bad case：「事实片段正确但整片核心错位」。** 每个事实都对，主旨却跑了。这类问题不能靠"再加一条禁词"解决——它属于归因到看点与主旨层，修复方式是主旨卡、主旨锁和独立主旨复核，不是加词表。

> 口径来源：[bad-case-spec.md](bad-case-spec.md)、[eval-spec.md](eval-spec.md) §2.1、[root-cause-18-review-batch.md](root-cause-18-review-batch.md)。

## 6. 三个 Agent 的分工与验收标准

| Agent | 职责 | 关键验收思路 |
|---|---|---|
| Agent 1 内容理解与边界判断 | 抽看点与主旨、判定哪些陈述能写／须限定／须排除、识别材料缺口与风险 | 边界判定准确率；不可写陈述不得进入可写集合（漏放为 0）；材料不足时正确停下而不是编 |
| Agent 2 看点与文案生成（含定向重写） | 按主旨选看点，产出同一主旨下的三条不同表达槽候选；按评审缺陷定向重写 | 首轮严格可用率；重写挽救率；节点/槽位契约一致；长度、前缀、问号硬约束 100% 执行 |
| Agent 3 独立质量评审 | 独立对照原材料与规则判三档、给判据与理由、输出可执行的分流 | 放行准确率、召回率、误放率；评分一致性（kappa）；不得采用生成侧自评 |

**方法论：先写测试用例，再谈模型选择。** 已定义 TC01–TC60（覆盖三个 Agent + 全流程异常 + 反馈）与 HC01–HC10（运行约束与问题分级），每条写清输入、期望输出／验收标准、禁止行为。用例先于模型选型，是因为"哪个模型好"必须由"哪些用例过"来回答，而不是反过来。

## 8. 分阶段验证：口径检查 → 对照臂 → 影子 → 试用 → 线上

| 阶段 | 设计 | 判断什么 | 不能顺带宣称什么 | 状态 |
|---|---|---|---|---|
| 工程与口径检查 | 必过场景、身份与统计复核 | 流程是否按约定运行 | 不代表标题质量达标 | 【已有机制】 |
| 小样本方案对照（B/C 两臂） | 同模型、同材料、同展示约束，比简单链路与复杂链路 | 多出来的调用是否值 | 不据 20 条证明泛化或 95% 可靠 | 【待验收】预注册为草案，两臂未跑 |
| 影子运行 | 真实任务旁路处理，不替换原标题 | 建议、误拦、异常与真实工作负担 | 不等于质量收益 | 【待建设】未接业务 |
| 人工辅助试用 | 只在通过验收的领域给建议，人工确认后进原流程 | 实际采用率与人工负担 | 不等于可自动放行 | 【待建设】 |
| 有限线上对照 | 分组观察进入精排、曝光、点击、观看与负反馈 | 消费质量有没有变好 | 不把点击上涨单独当成功 | 【待建设】未接推荐 |

三条不能越线的约束（写进预注册，看结果前锁定）：

1. 分母固定、无标题与失败项留在分母里；"可用"与"勉强通过"分两行报。
2. 20 条样本全对时错误率的 95% 置信上界仍约 14%——**离线结论只能验证机制与方向，不能批准自动放行**。
3. 只在验证集上看过结果再调规则，该验证集就降级为开发集，必须另选新验证集。

> 依据：[experiment-preregistration.md](experiment-preregistration.md)（草案待批准）、[eval-spec.md](eval-spec.md) §5。

## 9. Bad Case 闭环：从捞取到结案

**怎么捞**（四路）：人工定期抽检 Agent 决策日志；评审侧与业务侧反馈；指标异常下钻并回溯当天决策；程序兜底与规则拦截触发的日志。

**怎么打标**：按出错环节（感知／规划／执行／经验）、按错误类型、按严重度 P0–P3。

**怎么修**：周度看板对当周 case 聚类，看 TopN 集中在哪个环节、哪个类型，归因到具体模块，然后分流到正确的修法——确定性问题修代码，语义不清改任务说明或样例，检索错改案例范围，流程传递错修分流。**同一个根因第二次确认出现，就必须评估升级为规则、必读规范或回归测试，而不是继续加一句提示词。**

**怎么算闭环**：修复要走完"提案 → 人工审核根因与改法 → 真实回归测试 → 原例／反例／正例三项人工核验 → 批准当前源码版本 → 上线后观察期 → 同族复发重开或结案"。修完还要能证明"原例好了、反例没误伤"，只在同批复测只能算回归验证，不算泛化变好。

> 依据：[bad-case-spec.md](bad-case-spec.md)、[feedback-repair-loop.md](feedback-repair-loop.md)、[product-design-draft.md](_archive/product-design-draft.md) §8。

## 10. 整体运行机制

一句话：**一批视频进来，先判断能不能写，再在能写范围内写出三条候选并独立评审，没过的按缺陷定向重写；人只判最后那一条，人的每次判断都变成下一次的经验。**

具体跑起来是这样。新任务进来先做材料体检——ASR/OCR 够不够、有没有高风险内容，够才往下走，不够就停在缺料或转人工，不允许硬编一条出来。够的进入理解与边界：把视频拆成事实陈述和语义单元，判定哪些可以写成事实、哪些必须带限定或归属、哪些直接排除，同时定出主旨和主看点；这一步的产物是"这次能写什么"的白名单，后面任何候选都不许引用白名单外的内容。

然后在白名单内选看点、按同一主旨生成三条不同表达槽的候选，交给独立评审判三档并给出具体判据；长度、前缀、问号、引用有效性这些确定性问题由程序先挡一道。没过审的候选按缺陷类型走定向重写，最多两轮，超过就停，不补造候选。最后交给人的只有一条系统推荐（或明确标为未产出），人只做"可用／勉强／不可用 + 一句话理由"。

人的判定同时触发两条回流：确认过的案例进共享案例库，供后续相似视频检索参考；被判有缺陷的进中央修复账本，按根因族聚合成提案，人工审核根因与改法、跑完真实回归测试、验证原例与反例之后才算修好，上线后进观察期，同族问题再出现就重开。看板按周汇总这一步的分布，回答"这周的问题集中在哪一层"。**短期看是质量闭环，长期看是这套系统自己越用越准的依据——但这条回流当前只走到"提案草案"，尚未有一次走完全程（见 §11）。**
