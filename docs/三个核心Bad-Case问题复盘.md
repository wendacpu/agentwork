# 三个核心 Bad Case 问题复盘

本文围绕三个短视频标题生成案例，按“发现问题 → 判断问题环节 → 查看日志和人工反馈 → 定位原因 → 确定修改方案 → 小流量测试 → 验证结果与后续放量”的顺序，还原问题的调查与修复过程。

**验证范围：** 本文记录的是针对具体案例的隔离测试和人工反馈，不代表已完成大规模放量验证。萨戈夫和南非案例是在各自当时的代码版本下复测；后续改动合入后，未再对这两个视频进行回归。

## 案例一：萨戈夫赛后表态——标题承诺与视频实际内容存在视角偏差

### 案例登记

| 项目 | 内容 |
|---|---|
| Case ID | BC07 |
| 任务类型 | 体育采访类视频标题生成 |
| 用户输入 | 萨戈夫赛后采访视频。他谈到与德文的交手，称德文是传奇，并表示不认为自己已经比德文更强。 |
| 问题期 Agent 输出 | “赢过德文一次，萨戈夫为何仍称他传奇” |
| 人工判断与修改方向 | 人工判定原问题标题不可用：视频展示的是萨戈夫接受采访时的回应，不是在解释他为何称德文为传奇。人工认可的标题方向是“萨戈夫赛后：我不认为已强于德文”。 |
| 问题环节 | 自动评审中对视频是否兑现标题承诺、标题是否覆盖视频核心内容的判断。 |
| 问题原因 | 评审对标题预期与视频内容的核对不够充分，尤其没有明确区分受访者的自我评价与对另一位选手地位的原因分析。 |
| 影响指标 | 不可用标题的候选级误放情况；自动评审与人工判断的一致性。 |
| 修改方案 | 增加标题承诺与视频内容的逐项对照；补充采访内容的视角区分；不因出现疑问词而机械否决标题。 |
| 回归测试结果 | 后续隔离批次生成三条新候选，均通过自动评审；人工复核三条均判可用。 |

### 问题复盘

**1. 发现问题。** 系统生成了“赢过德文一次，萨戈夫为何仍称他传奇”，并在候选评审中判定通过。人工复核却认为，这一标题会让读者期待对“为什么称德文为传奇”的原因分析，而视频主要展示的是萨戈夫在采访中表达自己的看法。

问题并非“传奇”这一表述完全没有出现在视频中，而是标题将一次采访表态包装成了原因分析，可能改变读者对视频内容的预期。原候选通过了评审，但原任务因其他校验问题转入人工处理，并未形成系统推荐。

**2. 判断问题环节。** 这条标题的争议不在于相关人物是否出现在视频中，而在于标题暗示的内容是否与视频实际交付一致。因此，我们重点检查自动评审中的两个问题：视频是否兑现标题带来的观看预期；标题是否覆盖视频核心，而非只截取一个相关细节。

**3. 查看日志和人工反馈。** 原始评审记录显示，系统对上述两项均给出了肯定结论；人工则认为，视频中的表态与标题暗示的原因分析存在视角偏差。进一步复测中，类似的问题标题再次出现并获得通过，说明当时的调整尚未稳定解决问题。

现有证据能够说明评审结论与人工判断不一致，但不足以证明模型完全没有核对证据，也不能仅凭有限几次复测断言任何提示词调整都必然无效。

**4. 定位原因。** 结合人工意见与复测结果，问题集中在两个方面：一是评审缺少便于逐项检查和追溯的承诺对照要求，容易因为人物和相关表态均已出现，就认为标题得到支持；二是采访类内容的视角区分不足——受访者对自身经历和态度的解释，不自动等同于对他人成就或地位的原因分析。

**5. 确定修改方案。** 评审需要先说明标题会让读者期待什么、哪些措辞产生了这一预期、视频实际讲了什么、对应的原始证据回答了什么问题，再判断两者是否一致。不一致时要求修改；证据不足时转人工；内容一致时仍需判断标题是否覆盖视频核心。

同时明确，不能仅因为标题出现“为何”等疑问词就否决。如果视频确实回答了标题提出的问题，疑问式标题可以通过；关键在于具体承诺是否得到兑现。

**6. 小流量测试。** 在包含原视频的隔离批次中，系统生成并通过了三条新候选：

| 候选标题 | 自动评审 | 人工复核 |
|---|---|---|
| 萨戈夫：不认为自己已强于德文 | 通过 | 可用 |
| 萨戈夫称德文是传奇，不认为自己更强 | 通过 | 可用 |
| 赢过德文一次，萨戈夫仍称他是传奇 | 通过 | 可用 |

**7. 验证结果与后续放量。** 本次测试中，三条新标题均获得人工认可，人工认可的终稿方向与第一条候选一致。该结果说明本次生成的候选与人工预期一致；但它不等于原问题标题已经在当前代码下被稳定复评并正确拦截，也不能证明同类视角偏差已全面解决。尚无大规模放量验证记录。

## 案例二：南非员工偷看球赛——多个独立缺陷叠加

### 案例登记

| 项目 | 内容 |
|---|---|
| Case ID | 南非员工偷看球赛案例。此前曾使用“BC11”作为工作编号，尚未核实是否已正式写入案例库。 |
| 任务类型 | 新闻事件类视频标题生成 |
| 用户输入 | 南非两名员工上班期间偷看球赛，被球场大屏拍到，随后转身装作认真工作。 |
| 问题期 Agent 输出 | 围绕“两名员工偷看球赛”的候选被判引用内容无效；另有标题未写日期却被判缺少日期限定，以及超长标题进入人工评审的问题。 |
| 人工判断与修改方向 | 人工认可“南非两员工上班偷看球赛被大屏抓包”的表达方向，并明确提出超长标题不应送到人工评审台。 |
| 问题环节 | 引用合法性校验、限定条件的分类与执行、超长标题的交付路由。 |
| 问题原因 | 允许引用的内容范围遗漏结构化看点；“写到时不能写错”的日期条件被当成“必须写出”的限定；超长候选没有从人工评审入口隔离。 |
| 影响指标 | 候选交付数量、可用标题误拦情况、人工评审资源消耗。 |
| 修改方案 | 统一允许引用的内容范围；区分必须表达的限定与仅在涉及相关事实时才需核对的条件；超长候选移入只读诊断区。 |
| 回归测试结果 | 后续复测中，未写日期却报缺日期的问题未再出现；两条候选通过自动评审并被人工判可用；超长候选的只读隔离机制得到验证。 |

### 问题复盘

**1. 发现问题。** 同一视频任务中出现三类异常。首先，围绕“两名员工偷看球赛”的部分候选被判引用无效，而这一事件正是视频核心。其次，部分标题没有写日期，却被要求补充日期限定。最后，超过字数限制的候选进入了人工评审台，人工不得不逐条以“字数超了”为由拒绝。

用户进一步明确要求：既然超长标题肯定不会通过，就不应送到评审台。这使超长问题从标题质量问题进一步成为人工评审资源分配问题。

**2. 判断问题环节。** 三个现象同时出现，但不能直接假设它们来自同一原因。我们分别检查候选引用与允许范围、日期要求如何记录和执行、以及自动校验后评审台如何筛选候选。逐项排查后，确认需要分别处理。

**3. 查看日志和人工反馈。** 引用记录显示，候选绑定的是视频结构中提炼的看点，而程序维护的允许引用清单主要包含另一类语义分析结果；看点虽然有效，却不在该清单中。边界信息中则存在“10 月 28 日是报道日期，不是事件发生日期”的提醒，它原本用于防止写错，却被当成标题必须表达的限定。

人工反馈库中多条超长标题被拒，理由均与字数有关。用户随后要求，超长候选可以保留供诊断，但不应作为正常候选进入可操作的评审区。

**4. 定位原因。** 引用问题源于允许范围不完整：有效结构看点没有被纳入同一套引用校验范围。日期问题源于不同性质的限定混在一起：必须写出的限定、写到时不能写错的条件、以及不要求写出的背景信息没有充分区分。超长问题则源于交付前缺少独立隔离。

**5. 确定修改方案。** 将有效语义内容、结构化看点和已确认可用的内容统一纳入引用范围，同时排除明确不可使用的内容；将限定区分为必须表达、涉及相关内容时才需遵守、以及纯背景信息；将超长候选移入只读失败轨迹，并由后端拒绝针对它们提交新的人工评审结果。

例如，标题不写日期时，不因“报道日期与事件日期不同”而报缺日期；标题写了日期时，再核对是否发生混同。

**6. 小流量测试。** 原视频后续隔离复测中，“未写日期却报缺日期”的问题未再出现；两条候选通过自动评审并获得人工可用判断。其中一条为“南非两员工上班偷看球赛被球场大屏抓包”。人工确认的标题方向为“南非两员工上班偷看球赛被大屏抓包”，两者主旨一致，人工版本删除了“球场”。

**7. 验证结果与后续放量。** 该次复测中日期误报未复现，可用事件标题能够通过评审，超长候选的只读隔离机制也得到验证。时间顺序需要区分：用户先拒绝超长候选并提出隔离需求，随后才验证只读隔离；不能表述为“在只读区接受了新的人工拒绝”。尚无大规模放量验证记录。

## 案例三：小包装商业观察——程序侧判定覆盖评审模型结论

### 案例登记

| 项目 | 内容 |
|---|---|
| Case ID | 小包装商业观察案例。此前曾使用“BC12”作为工作编号，尚未核实是否已正式写入案例库。 |
| 任务类型 | 个人账号商业观察类视频标题生成 |
| 用户输入 | 个人账号发布的视频，讨论小包装、小样等商品为何成为消费热点，以及背后的消费和商业逻辑。 |
| 问题期 Agent 输出 | 候选使用“商业观察”作为内容性质前置，仍被系统判定缺少来源归属，反复进入重写。 |
| 人工判断与修改方向 | 人工认为“商业观察”适合这条内容，并认可“商业观察：小包装走红背后的消费逻辑”。 |
| 问题环节 | 边界阶段的归属措辞、自动评审的归属判据，以及程序侧对来源归属的强制判定。 |
| 问题原因 | 来源建议过于依赖具体账号名；归属判断偏向固定句式；程序侧旧规则还会将部分模型已判通过的候选改判为需重写。 |
| 影响指标 | 可用标题误拦情况、候选交付数量、反复重写造成的模型调用成本。 |
| 修改方案 | 来源建议不再一律要求逐字复现账号名；结合内容性质和风险判断归属；调整程序侧过窄的形式判定。 |
| 回归测试结果 | 最后一轮复测中两条候选通过自动评审、任务正常交付；人工复核三条均判可用，其中人工选定标题与系统第二条候选一致。 |

### 问题复盘

**1. 发现问题。** 系统生成了“商业观察：小包装小样为何成消费热点”等标题。人工认为，“商业观察”能够说明这是观察与分析类内容，在这一具体场景下，没有必要再把创作者的完整账号名塞进标题。但系统仍反复以缺少来源归属为由要求重写。

早期生成还出现过直接使用创作者账号名的情况，使有限字数被来源名称占用，挤压实际内容。

**2. 判断问题环节。** 根据系统给出的拦截理由，最初重点检查来源归属审查：系统是否把账号名当作必须逐字保留的来源；评审能否识别“商业观察”这类内容性质前置；如果模型已经识别，后续程序是否又改变了结论。

**3. 查看日志和人工反馈。** 一次运行中，边界阶段给出的建议来源措辞是创作者的完整账号名。若下游将建议理解为必须逐字写出，就可能使标题因没有账号名而被判缺失。

调整边界与评审说明后，部分教程和美食样本表现有所变化，但小包装在一次复测中仍有大量候选被拦。于是继续对照评审输入、模型原始输出和程序最终结论。对部分候选，评审模型实际上认为归属已经表达并给出通过；程序侧另一套较严格的词法判定却没有识别到它期待的固定转述句式，并在后续裁决中覆盖了模型结论。

因此，至少对已检查的部分候选，问题不是评审模型没有理解“博主”，而是模型通过后，程序仍按旧规则改判。

**4. 定位原因。** 来源建议被过度具体化，可能从辅助措辞变成事实上的硬约束；归属判断过度依赖“某人称”“某人表示”等固定句式，不充分识别其他自然表达；程序侧旧的词法标记又可能覆盖模型对具体标题的判断。

对本案而言，人工认可“商业观察”作为内容性质前置。但这不意味着所有情况下都可以省略具体来源：涉及政策、医疗、金融、争议性指控或必须区分发言人的内容，仍需结合具体风险保留必要归属。

**5. 确定修改方案。** 将建议来源措辞定位为辅助参考，不一律要求标题逐字复现账号名；评审时结合读者可能形成的理解，判断是否会把个人观点误当成已证实事实或官方信息；调整程序侧过窄的词法判定，避免仅因缺少特定转述句式，就直接覆盖评审结论。

**6. 小流量测试。** 最后一轮小包装复测得到以下结果：

| 候选标题 | 系统判断 | 人工判断 |
|---|---|---|
| 商业观察：小包装小样生意为何走红 | 通过自动评审 | 可用 |
| 商业观察：小包装走红背后的消费逻辑 | 通过自动评审 | 可用 |
| 商业观察：小规格能否独立成一门生意 | 要求重写 | 可用 |

**7. 验证结果与后续放量。** 该次复测中，系统没有再因来源归属问题拦下全部候选；两条通过自动评审，人工认为三条均可用。人工选定的“商业观察：小包装走红背后的消费逻辑”与系统通过的第二条候选一致。

第三条仍存在系统与人工的分歧：系统要求重写，人工判可用。应将其保留为后续评审标准校准样本，不能简单断言系统判断正确。尚无大规模放量验证记录。

## 跨案例总结

**1. 核对中间结论如何传递。** 小包装案例表明，最终的“缺少来源”不一定完全来自评审模型。排查时需要区分模型原始判断、程序增加的额外判定和最终路由，避免把程序问题误认为提示词问题。

**2. 相同的拦截结果可能来自不同机制。** 南非案例中的引用范围、日期限定和超长交付都影响候选交付，但需要分别定位、分别修复和验证，不能统一归为“评审太严格”。

**3. 将人工意见转化为具体判断标准。** “视频是在展示表态，不是在分析原因”对应承诺与交付核对；“字数超了不要送来”对应超长隔离；“商业观察适合作为前置”对应结合具体语境判断来源表达。

**4. 区分案例验证与放量效果。** 三案已有针对性小流量测试和人工反馈，但这些证据主要支持具体案例层面的观察，不能直接证明全量误拦率下降或已完成大规模放量验收。
