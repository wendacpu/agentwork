# 推荐文案生成工作流：设计基线 + 现状系统诊断

> 2026-11-04 · 基于本仓库代码与两个实测批次（v_eval_20261104 / v_eval_fixed_20261104）的取证
> 定位：不是「再加一层」的方案，而是回答「这套东西一开始该怎么设计，现在错在哪、按什么顺序纠」。

---

## 一、成本结构的第一个事实

先把问题量化，否则设计讨论会变成偏好之争。

| 批次 | 任务数 | 成功调用 | 无效调用 | prompt tokens | completion tokens | 每任务 node_failed |
|---|---|---|---|---|---|---|
| v_eval_20261104 | 20 | 90 | **103** | 2,122,383 | 165,802 | 15 / 20 |
| v_eval_fixed_20261104 | 20 | 163 | 3 | 3,671,213 | 238,754 | — |

三条结论，全部是硬数据：

1. **输入侧占成本的 93%。** prompt / completion ≈ 12–15 : 1。任何「加节点提质量」的设计都会先撞在成本墙上，因为成本几乎等于「传了多少上下文」。
2. **无效调用曾经比成功调用多。** 第一批 103 次失败 vs 90 次成功；一次失败 = 一次 22K prompt tokens 全废，而且重试会把上次坏输出（截 600 字）追加进 prompt，第二次更贵。
3. **第二批把无效调用压到 3 次，成本反而升了 72%。** 因为 `review_per_candidate=true` 把评审拆成单候选，固定 system prompt（REVIEW 16K 字符 ≈ 5K tokens）重复发三次。这是典型的「用可靠性换钱，但没有定价」。

所以设计的核心命题不是「怎么生成得更好」，而是：**在 22K tokens/次的预算下，把多少 token 花在真正决定判定的信息上，其余全部靠契约和缓存省掉。**

## 二、我会怎么设计（六条骨架，按杠杆排序）

### 1. 判定输出必须「短到能被约束」，而不是「全到能被检查」

现状是让模型一次输出 15 个必填字段（gates × GATE_IDS、quality × QUALITY_IDS、issues、rewrite_guidance、memory_query），于是出现注释里记录的现象：一次评 3 个候选要么漏字段（1100–2300 tokens），要么失控到 16384 被砍断（26%）。

这不是模型能力问题，是**输出 schema 的体积问题**。正确做法：

- 判定层只输出**枚举 + 一句理由**：`{candidate_id, verdict: pass|revise|reject, core_point_hit: bool, reason: str}`。5 个字段，30–80 tokens。
- 结构化的 15 字段留给「人要看」的产物，由程序从判定 + 候选 + 证据拼装，不让模型生成。
- 结果：单次评审输出从 2.4K tokens 降到 100 tokens 量级，且几乎不可能结构失败。

**代价**：丢掉模型写的「诊断理由」丰富度。**取舍**：理由是给人看的，程序拼装同样能给人看，且一致性更可控。

### 2. 把不可信边界收窄到一个点：解码层

现在 `pipeline.py` 4428 行 / 129 个函数里，`_normalize_*`（12 个）、`_apply_*_gate`（5 个）、`_limit_*`（18 个）全是在模型输出之后做的手写补偿。这是**把「不信任模型」的成本转移成「维护代码」的成本**，而后者随规则线性增长、随并发加速劣化。

工程上正确的收窄点是：结构化输出 + 一个 JSON Schema。校验失败就重试，重试失败就降级 —— 不在业务代码里逐字段兜底。

`structured_output` 字段已经存在（auto/on/off），但它目前只在一个 config 里被打开。这是本仓库性价比最高的一个开关。

### 3. 缓存必须跨任务，且分三层

现状：`cached_model_reply(task_id, request_hash)` 把 `task_id` 绑进缓存键 → 跨视频零复用、跨批次零复用。v_eval_fixed 20 个任务只命中 1 次。

三层缓存，各自的键不同：

| 层 | 键 | 命中场景 | 现状 |
|---|---|---|---|
| 理解层 | `(video_id, 证据内容哈希, prompt_hash)` | 同一视频换模型重跑、换个批次再跑 | 无（62 个 config 反复跑同一批视频，每次都从零理解） |
| 前缀层 | 稳定的 system prefix 顺序 | 服务端 KV cache | 靠运气 |
| 判定层 | `(标题规范化哈希, 核心证据集哈希, rubric_version)` | 已判过的标题再出现（重写谱系、跨批次同候选） | 无 |

62 个 config 快照 × 126 个 runtime 批次 = 703MB，基本都是「同一件事重复算了一遍」的化石。

### 4. 成本必须是第一等公民，带硬闸

现在 `usage` 只写进 event 表，没有任何聚合、预算、降级。设计上：

- 每任务 token 预算（硬上限），超预算从「重写」开始降级，先保交付一条保守稿，再保三条。
- 阶段成本记账（understand / boundary / highlight / generate / review / rewrite 各自花了多少），否则无法回答「哪一节点该砍」。
- 每批次产出 `cost.json` 与 `metrics.json` 并列，跟质量一起看。

没有这条，前三条都无法验证收益，只能靠感觉。

### 5. 并发：任务级并行 + 节点级异步，而不是「线程池套串行链」

现状：`ModelAdapter.complete` 完全同步，并发只存在于 `scripts/run_acceptance.py` 外层 ThreadPoolExecutor。单任务中位 8 次串行调用、最坏 21 次，按每次 30–60 秒算是 5–10 分钟/视频。

高频高并发的正确形态：

- 任务级：worker 池消费队列（已有雏形）。
- **节点级**：`understand` / `thesis_review` / `verify` 三者互不依赖，应并发发出；`review` 三个候选天然可并发，不必为了「省前缀」串行。
- 失败局部化：单节点坏 JSON 不应让整任务 `technical_failed`（现状 15/20 任务 node_failed）。降级路径应该是「该节点缺省 → 下游按缺省继续」，而不是整链抛异常。

### 6. 质量门放在交付口，中间只放「硬」校验

现状的错配：每个节点都设 gate，语义判定散落在 N03 / N05 / N07 / R01 / R00 五处，导致「约束不贯穿」—— 上游判定「待核验/已排除」，下游仍能把引用它的标题推荐为合格（这是 Hindsight 记录里反复出现的同一类漏洞）。

更好的形态：

- **中间层只做机械校验**（字数、前缀、禁用词、元信息短语、引用闭包完整性）—— 确定性、可单测、不会和模型判断打架。
- **语义判定只做一次**，独立调用，输入只有「原始材料 + 候选」，不带上游结论（避免 Anchoring）。
- **交付口做一次终审**：把「已排除单元 / 待核验事实 / 限定条件」作为黑名单与必含条件，机械比对。这一步是唯一需要「贯穿」的地方，因为它是唯一面向交付的。

这样「约束贯穿」不再依赖每个节点都写对，而是依赖一个交付口闸门 —— 一个能写对的地方。

## 三、现状诊断（七条病症，按严重度）

### 病症 1 · 补偿性复杂度：校验逻辑被用 Python 重写了一遍

**证据**：`pipeline.py` 4428 行、129 个顶层函数，其中 `_normalize_*` 12 个、`_apply_*_gate` 5 个、`_limit_*` **18 个**（`_limit_is_prohibition` / `_limit_is_attribution` / `_limit_needs_body` / `_limit_covered_by_narration` …）。`_execute` 单方法 425 行（已用 `dsh-skip-func-length` 豁免）。

**性质**：每一项都源于一次真实 badcase，所以不能简单说「删掉」。但后果是：**改一条规则要动三处**（prompt 正文、normalize 兜底、mechanical_check 判定），而测试只覆盖想到的路径。

**这就是「一开始没有设计规范」最直接的物证** —— 系统是用补丁长出来的，不是设计出来的。

### 病症 2 · 无效调用率曾 > 100%

**证据**：v_eval 批次 `model_reply_invalid` 50 + `model_error` 53 = 103，成功 90。`node_failed` 15 次（20 个任务里 15 个失败）。

**性质**：这是纯浪费 —— 失败调用的 prompt tokens 全额计费且不产生任何产物。更糟的是重试把坏输出尾部追加进 prompt，第二次调用更贵，形成「越坏越贵」。

**关键取证**：v_eval_fixed 把同一指标压到 3 次，用的只是三个开关（structured_output=auto、review_per_candidate=true、review_input_scope=compact），**没改模型、没改 prompt**。所以这 100% 是工程配置问题，模型不背这个锅。

### 病症 3 · 输入侧失控，且「拆调用」在放大固定成本

**证据**：prompt/completion ≈ 13:1；`review_input_scope` 默认还是 `full`（注释自己写了：R01 拿到 72K 字符，evidence 有 36/68 条没被任何结论引用，risk_signals 65 条每条重复同一组常量字段）；拆成单候选评审后，REVIEW 的 16K 字符 system prompt 被重复发送 N 次。

**性质**：用「更小的请求更不易崩」换来了「固定成本 × N」。这个交易在 N=3 时还能接受，但既然根因是 schema 太大（病症 1），正确解法是缩小 schema 而不是拆请求 —— 拆请求只是把崩溃概率摊薄了。

### 病症 4 · 缓存作用域错误，导致「同一件事反复算」

**证据**：`cached_model_reply(task_id, request_hash)`，键含 task_id；v_eval_fixed 20 任务命中 1 次。62 个 config 快照（`compare_v2_flash` / `compare_v2b_flash` / `compare_v3_flash` / `real_run_001` …）反复跑同一批 `recent-portrait-100/300` 视频。runtime 703MB / 126 个批次 / 几十个 agent.db。

**性质**：这是「实验文化」的必然产物 —— 每次想验证一点东西就得重跑全链路，因为缓存不跨任务，所以只能整批重算。成本高 → 实验少 → 质量迭代慢。这是一个负向飞轮。

### 病症 5 · 编排与兜底混在一个函数里，故障放大

**证据**：`_execute` 425 行，同时包含节点编排、12 处 `storage.event` 遥测、异常兜底、状态推进。一个节点抛异常即整链 `node_failed`。

**性质**：无法回答「这次失败是内容问题还是工程问题」—— 因为失败的处理和成功的路径写在同一层。15/20 任务失败里，有多少是模型判定「不该交付」（业务停止，正常）和有多少是坏 JSON（工程失败，不可接受），从代码层面看不出来，只能事后翻 event 表。

### 病症 6 · 配置、产物、补丁三类无主资产

**证据**：
- 57 个 `config*.json`，差异集中在 `asset_root` / `model_provider` / `output_dir` 三处。**更致命的是语义分叉**：`config.siliconflow-300.json` 显式写了 `structured_output: auto` / `review_input_scope: compact`，而 `config.canary_v28.json` / `config.deepseek.json` 根本没这些键，走默认值 `off` / `full`。**同一个仓库里的两个配置描述的已经不是同一个系统**，所以跨批次实验结论不可比。
- `scripts/_patch_*.py` 12 个一次性补丁脚本（`_patch_prompts.py` / `_patch_understand.py` / `_patch_samevideo.py` ×2…）—— 说明改 prompt 靠的是临时脚本，不是可复现的版本化。
- `runtime/` 126 个批次 703MB 无生命周期策略。

**性质**：这三件事共同指向同一个缺失：**没有「一次运行」的规范定义**。所以每次实验都是新目录、新配置、新补丁，而「当时的系统是什么样」无法重建。

### 病症 7 · 测试度量的是实现，不是交付

**证据**：Hindsight 记录 `235 项测试通过、217/217 回归全绿`，同期产品原样可用率 33.3%。且 `_normalize_highlights` 从不读取 `main_thesis` 这种 bug（导致 18/18 条主旨在 state 里为空）能穿过全部测试。

**性质**：测试断言的是「我写的行为」，不是「承诺的质量」。一个只有 33% 可用率的系统，回归测试必须是绿的 —— 这本身就说明测试与目标脱钩。

## 四、专项解剖：评审为什么吃掉 41%

实测（v_eval_fixed_20261104，15 条有效视频，2.75M prompt tokens，184K/条）：

| 节点 | prompt tokens | 占比 | 调用次数 | 单次均价 |
|---|---|---|---|---|
| review | 1,141K | 41% | 59 | 19.3K |
| generate | 426K | 15% | 16 | 26.6K |
| highlight | 375K | 14% | 17 | 22.0K |
| boundary | 319K | 12% | 15 | 21.3K |
| understand | 302K | 11% | 15 | 20.1K |
| thesis_review | 155K | 6% | 16 | 9.7K |
| rewrite | 28K | 1% | 6 | 4.7K |

### 4.1 59 次里没有一次是多余的

按任务级事件表核对，59 次由三部分构成，逐项对得上：

| 来源 | 次数 | 说明 |
|---|---|---|
| 首轮三候选 | 15 × 3 = **45** | 每个候选一次，符合 `review_per_candidate` 设计 |
| 重写产出的新候选 | 6 次重写 × 2 条 = **12** | `rewrite_candidate_count=2`，新候选必须新评 |
| 重试/补漏 | **2** | 结构不合格后 `review_single_retry` / `_retry_single_review` |

**所以「评审调用太多」不是问题**——每一个调用都对应一个真实的待判候选。沿着「减少调用次数」修，直接砍的就是评审覆盖度，伤质量。真正的浪费在**单价**上。

### 4.2 单价 19.3K 的构成：95% 在重复

`_review_input()` 的 payload 结构是：

```
video_materials: { description, caption, asr_segments(全文), ocr_segments(全文) }
evidence: 全量证据（compact 只裁未被引用的）
claims / risk_signals / boundary / highlights
thesis_contract + review_thesis_contract
matched_rules / business_policy / rubric
candidate_titles: ← 唯一因候选而异的部分，几百 tokens
```

同一条视频的三个候选，前 95% 逐字相同。`review_per_candidate=true` 后拆成三次请求，
等于**把同一份 23.5K 上下文重发三遍**，只为让每次多带一条几十 tokens 的标题。

`_compact_review_payload` 只裁 `evidence` 与 `risk_signals`，**不动 `video_materials.asr_segments` / `ocr_segments` 全文**——
而这两项恰好是 payload 里最大的单一字段。

### 4.3 真正的问题：184K/条 = 同一条视频被读了约 20 遍

拉宽看，七个节点的单次 prompt 全部落在 4.7K–31K 这个区间，**没有一个是"小请求"**：

- understand 20.1K：合理，它必须读 ASR/OCR 全文
- boundary 21.3K：只需要 claim + 证据摘要，不需要重读全文
- highlight 22.0K：只需要 semantic_units + claim 索引
- generate 26.6K：还带 memory_cases
- review 19.3K：只需要「标题 + 主旨 + 边界判定 + 被引用 claim 原文」

原因在 `_generate_and_review` 与各节点构造 payload 的方式：都直接塞 `to_dict(video)`（含 asr/ocr 全文）+ 上游全量产物。
**这不是「9 个节点各司其职」，是「9 次独立的全文阅读」。** 加一个节点 = 多读一遍全文，这才是「加节点提质量」在当前结构下必然撞成本墙的机制。

### 4.4 诊断：把「输出体积问题」误诊成了「批量问题」

`_review_with_fallback` 的注释记录得很清楚：一次评 3 个候选时，模型要么只写 1100–2300 tokens 漏必填字段，要么失控写到 `max_tokens=16384` 被砍断（26%）。

根因是一次请求要输出 **3 候选 × 15 必填字段 = 45 个结构化字段**。
但被选中的解法是「拆成单候选」——降的是**单次输出体积**，代价是**输入 × 3**。
而输入占成本 93%。

**方向的错配。** 正确解法是缩输出 schema（`verdict` + 一句理由，5 字段），让一次请求覆盖 3 个候选、上下文只发一次。
同一个开关，一个方向成本 ×3，另一个方向成本 ÷2。

### 4.5 附加发现：成本分布与重要性错配

| 节点 | 任务性质 | 成本占比 | 适合的模型档位 |
|---|---|---|---|
| review | 语义裁判，最需要强模型 | 41% | 强 |
| generate / rewrite | 创作 | 16% | 强 |
| understand | 读材料写摘要 | 11% | 中 |
| thesis_review | 只读原材料写主旨契约（纯摘要） | 6% | 中/便宜 |
| thesis_consistency | 两份契约比对，5.9K tokens | 0.2% | 便宜 |
| boundary / highlight | 分类/挑选 | 26% | 中 |

understand + thesis_review = 17% 的成本花在「读材料 + 写摘要」上，现在和 review 用同一个模型。这是唯一适合做模型降级的地方，
而 review 恰恰最不该降级——它现在被调用最多、单次最贵，但其中大部分 token 是重复上下文而不是判断难度。

### 4.6 量化修复路径

| 修复 | 动作 | 预期 |
|---|---|---|
| A · 材料视图分层 | understand 保留 ASR/OCR 全量；boundary / highlight / generate / review 只拿「视图」（主旨 + 判定 + 被引用 claim 原文，一手材料凡被引用无条件保留） | 156K → 约 60K（-60%） |
| B · 评审合批 + schema 瘦身 | 恢复整批一次请求，输出从 15 字段降到 5 字段（`verdict / core_point_hit / reason` 等），15 字段产物由程序拼装 | 59 次 → 22 次，review 1,141K → 约 570K（-50%） |
| C · 跨任务缓存 | 理解层 / 边界层 / 看点层 / 主旨复核层是「同视频同证据」的确定性产物，跨批次可复用 | 1,151K（42%）在重复跑同一批视频时可免 |
| D · 模型分层 | understand / thesis_review 路由到便宜模型 | 17% 的成本单价降 5–10× |

A + B 叠加后：184K → 约 60–70K/条，同批 15 条从 2.75M 降到约 1M。再叠加 C，稳态约 40K/条。

**风险**：A 有信息损失风险，必须保留现有 compact 已确立的「一手材料凡被引用无条件保留」原则并扩展到 ASR/OCR 段落级；
B 需要一次 20 条对照验证「缩 schema 后整批是否仍然稳定」——如果仍崩，再退回拆单，但那时上下文已经只发一次，代价可控。

## 五、行动顺序（按「每单位改动换来的成本/质量」排序）

**P0 · 本周，只改配置和缓存键，不动架构**

1. 把三个开关设为默认：`structured_output=auto`、`review_input_scope=compact`、`review_per_candidate` 按「评审 schema 缩小后」再决定是否保留。预期无效调用从 100 次量级降到 5 次量级。
2. 缓存键去掉 `task_id`，换成内容寻址（视频证据哈希 + prompt_hash 用于理解层；标题 + 证据集 + rubric 版本用于判定层）。预期跨批次成本降 40–60%，因为 62 个 config 里大半在重算同一批视频。
3. 建一份**唯一配置基线** + overlay（`base.json` + `<experiment>.json` 只写差异），删掉语义重复的快照。没有这一步，后面所有实验数字都不可比。

**P1 · 本月，砍固定成本**

4. 判定输出瘦身：评审从 15 字段降到 5 字段（枚举 + 一句理由），程序拼装 15 字段产物。这一步同时消掉「拆单请求」的必要性。
5. 成本记账进产物流水线：每任务/每阶段 token 汇总 + 硬预算 + 超预算降级顺序（先砍重写，再砍三候选到两候选）。
6. `runtime/` 产物策略：批次只留 DB + 最终产物 + metrics/cost，中间大文件（截图、全量 payload dump）不落盘或定期清理。

**P2 · 架构级，需数据支撑再动**

7. `pipeline.py` 拆成三层：`orchestration`（节点推进）/ `gates`（机械校验）/ `normalize`（契约兜底）。拆分本身不掉风险，但**必须先在 P0/P1 拿到成本与失败分布数据**，否则不知道哪层该薄。
8. 节点合并（9 → 5）需要对照实验：现有流程 vs 合并流程，同批 20 条视频，看可用率是否掉。**现在没有这个对照数据，所以这是赌，不能先做。**

## 六、一句话总纲

这套系统的核心问题不是「节点不够多」或「prompt 不够好」，而是：

> **它把「信任模型」的成本转移成了「不信任模型的代码」的成本。**
> 后者随规则线性增长、随并发加速劣化，且不能靠测试保住质量。

工程化设计的本质是把不可信边界收窄到**一个**点（解码层 schema），其余全部靠契约、缓存和交付口闸门。规则越多，越要靠结构而不是靠代码去承载。

**主要风险**：P0 的缓存跨任务复用在「同视频换了 prompt 版本」时必须让 prompt_hash 参与键，否则会把旧判定当成新判定 —— 这是唯一可能悄悄引入质量回归的地方。**机会成本**：P0/P1 大约 2–3 天工作量，但不做的话，每次实验都在为「同一批视频重新理解一遍」付钱，实验频次上不去，质量就上不去。
