# 核查选择：off / static / dynamic

本文说明「这条视频要不要做外部实时核查」这件事由谁决定、边界在哪、怎么验收。
实现落在 `agent_system/verification/router.py`，接线点在 `agent_system/pipeline.py` 的 N03V。

## 一、改之前是什么行为

两处静态判断：

1. 全局开关 `verification_enabled`，**默认 false**；
2. 品类路由 `is_verifiable(video.domain, config)`——一级领域是「资讯」就整域核查，否则看二级领域是否在 `verifiable_domains` 里。

**它读的是视频的领域标签，不是模型对内容的理解。** 一个品类标签决定整条视频查不查；查哪几条也只看 `claim_type` 白名单取前 N 条。结果是：同品类下「其实没有外部事实主张」的视频照样发起检索，而跨品类的真实事实主张（例如美食视频里提到卫生处罚）一律不查。

## 二、三档模式

`verification_mode` 与 `verification_enabled` 是两层，不是替代关系——前者决定「谁来选」，后者是总闸。

| mode | 行为 | 用途 |
|---|---|---|
| `off` | 完全不核查，即使 `verification_enabled=true` | 临时停用 |
| `static` | 按品类路由（**默认值，历史行为**） | 保持已有配置语义不变 |
| `dynamic` | 模型在理解阶段给出建议，程序按「强制条件 ∪ 模型建议」决定 | 新增能力 |

未知取值一律退回 `static`，不静默升级为 `dynamic`。

## 三、强制条件：dynamic 的安全网

dynamic 下模型的判断力只作用在**非强制项**上：

- 命中强制清单 → 必须核查，**模型无权关闭**；
- 未命中 → 模型可以判断「不必查」，允许跳过，但理由要留痕。

这条不对称是刻意的：让模型有权说「不用查」，一旦判断错了，后面没有防线能纠正；而它说「要查」最坏只是多花一次调用。

### 清单来源：对齐已批准政策 P8

强制清单直接对齐 `config.business-policy.json` 里的 P8（边界情形兜底，`action=review`）：

> P8 触发条件：标题给出医疗、用药、投资、法律等专业结论，或涉及灾害伤亡的具体数字／具体人物，而材料未提供可核验依据。

| P8 方向 | 落地形式 | 取值 |
|---|---|---|
| — | 品类 | `时事社会`、`财经商业` |
| 医疗、用药 | 关键词 | 治愈、疗效、诊断、处方、剂量、用药、确诊、手术 |
| 投资 | 关键词 | 收益、涨幅、涨停、回报、理财、基金、股票、利率 |
| 法律 | 关键词 | 判刑、判决、量刑、起诉、拘留、立案 |
| 灾害伤亡 | 关键词 | 伤亡、遇难、死亡、事故、地震、火灾、洪水、暴雨、灾害 |

四点说明：

- **品类只放资讯下的两个高风险二级域，没有写「医疗健康」**——本项目 taxonomy 没有这个一级域（实际一级域：资讯、时尚美妆、美食、生活记录、健康运动、知识科普）。P8 的判据是「出现了专业结论」，不是「属于哪个品类」，所以这份清单主要由关键词承载。
- **P3（暴力与猎奇细节）不单独设项**：它的关键词（事故、伤亡、死亡）已被灾害伤亡一组覆盖。P3 的合规判断归业务政策，核查只管事实真伪。
- **P6（隐私暴露）不进清单**：住址、车牌这类不是「事实真伪」问题，核查帮不上，由 P6 的 reject 分支处置。
- 清单已写入 `config.example.json` 与 `config.business-policy.json`。**P8 变更时要同步这三处**（含本文档）。

关键词的误伤代价是多查一次，漏检代价是把未经核实的事实写进标题——两边不对称，所以取值偏宽。

### 无从核查时转人工

命中强制项、却**没有权威白名单可查**时（当前白名单只覆盖「时事社会」），不能停留在「留个痕继续跑」：

- 事件 `verification_skipped_no_whitelist` 留痕；
- 任务转 `pending_human`，`verification_hold.reason = NO_WHITELIST_FOR_REQUIRED_CHECK`。

没有这一步，强制清单在非资讯品类上等于一句空话。

## 四、判定来源必须可审计

每次判定都写入事件 `verification_decision`，带 `decider` 字段：

| decider | 含义 |
|---|---|
| `off` | 模式关闭 |
| `disabled` | 总闸关闭 |
| `mandatory` | 命中强制条件 |
| `model` | 模型建议（dynamic） |
| `static` | 品类路由（static 模式） |
| `static_fallback` | dynamic 模式下建议缺失/解析失败，回退品类路由 |

`static_fallback` 单独成一档，是为了能统计**回退率**。回退率过高说明模型没按格式输出建议，dynamic 实际上没有生效——这时不该继续跑对照实验，要先修提示词或解析。

## 五、三条硬约束

1. **强制条件优先于模型建议。** 模型说「不必查」但命中强制清单时，仍须核查或转人工。
2. **建议解析失败必须回退静态。** `verification_needed` 不是布尔值、字段缺失、整个对象不存在——一律当「无建议」。绝不能读成「模型说不用查」。
3. **dynamic 下白名单为空时不搜全网，并转人工。** 模型点名要查、但该品类没有权威站点白名单时，不退回开放式检索：搜来的来源不可控，等于用不确定结果去裁决事实。此时留痕 `verification_skipped_no_whitelist` 并转 `pending_human`。

三条都有对应测试锁在 `tests/test_verification_routing.py`。

## 六、验收：先证明没有漏检，再谈省了多少

动态跳过的风险全在「该查没查」，所以验收顺序不能反。分两轮，不要混在一次实验里：

**第一轮**：`verification_mode=static`，只验链路其余改动，得到干净对照。

**第二轮**：固定同一批视频，`static` 与 `dynamic` 两臂对照。

| 优先级 | 指标 | 通过条件 |
|---|---|---|
| 1 | 漏检审计：dynamic 跳过的视频里，人工回看有无本该被核查拦住的问题 | 不高于 static 臂 |
| 2 | 高风险必过用例 | 100% 通过，任一失败即阻断 |
| 3 | 检索调用次数、耗时、成本 | 相对 static 臂下降 |
| 4 | 可用文案比例、转人工比例 | 不能变差 |

漏检审计必须人工做——这是唯一能证明「跳过」没造成损失的证据，模型自己的判断不能自证。

## 七、什么情况说明不值得做

- 强制清单已覆盖绝大多数核查需求 → 模型判断的增量价值很小；
- 事后核对下来，模型「不必查」的判断准确率不够高 → 退回 static；
- 省下的调用成本相对总成本可忽略 → 不值得承担新增的不确定性。

这个方向的收益是**减少无效检查**，不是提升内容质量。如果当前最痛的仍是「合格文案太少」，它的优先级低于把生成质量做上去。

## 八、当前状态

已实现并离线验证（23 条路由测试 + 全量 432 项回归通过）：

- 三档模式与配置项、环境变量 `AGENT_VERIFICATION_MODE`；
- 强制条件、建议解析、判定来源留痕、白名单缺口处置与转人工；
- 强制清单已按 P8 定下，写入 `config.example.json` 与 `config.business-policy.json`；
- 理解提示词已包含 `verification_suggestion` 输出要求。

**尚未做**：没有跑过 dynamic 与 static 的真实对照实验；没有验证真实模型输出建议的格式遵从率；白名单仍只覆盖「时事社会」，因此强制清单里其余品类一旦命中就会转人工——启用 dynamic 前建议先把高频品类的白名单补上，否则人工队列会积压。

因此 dynamic **当前不应用于正式批次**，保持默认 `static`。
