## 一句话结论

**链路能跑、规则可追溯、评审有结构，但项目没有"验收"：没有人工金标准、没有评测脚本、没有可比较的基线。** 所以现在改任何规则都无法判断好坏——这才是"不知道往哪走"的真实原因，不是结构乱。

## 七个阶段：输入 / 输出 / 验收目标 / 现状

### S0 数据准备

- **输入**：B 站竖屏短视频（15–180s，播放 ≥500，10 品类 × 10 条）
- **输出**：`data/source/video_dataset.json`（100 条）+ 外置 `asset_root/`（mp4 / metadata / asr / ocr / frames）+ 采集与标注规范
- **验收目标**：① 100/100 资产可定位 ② 主表字段齐（标题/领域/形态/时长/画幅）③ 分类遵循 taxonomy
- **现状**：✅ 通过。`audit` 无缺失。
- **已知限制**：`description`/`caption` 是模型派生、未经人工核验，代码已标 `model_derived_uncalibrated`——**只能当证据，不能当金标准**。

### S1 规则包

- **输入**：业务规则（通用 / 领域 / 形态）+ 数据集 taxonomy
- **输出**：`rulepacks/{common,domains,forms}.md` + `RuleBundle`（含 `match_trace`、`gaps`、`conflicts`）
- **验收目标**：① 三文件可解析 ② 领域与形态**分别**匹配 ③ 覆盖率：每条样本至少命中 1 条 V + 1 条 F，缺口率 <10% ④ 规则 ID 跨版本稳定
- **现状**：形态 **100/100** 命中；领域 **38/100**（62 条 `no_domain_rule_matched`）。缺口可诊断 ✅。
- **关键问题**：V 规则（宠物 / 美甲 / 兽装 / 水果品鉴…）和资料集的领域体系（资讯 5 类、美食、时尚美妆、健康运动、知识科普、生活记录）**不是同一套**。领域规则层目前等于半空。

### S2 生成链路

- **输入**：`VideoInput` + `RuleBundle`
- **输出**：`Understanding` → `BoundarySet` → `HighlightSet` → `AgentDraft`（≤3 条）→ 机械检查结果
- **验收目标**：① 结构校验通过率 100% ② 引用合法率 100%（claim / evidence / highlight 全在范围内）③ 长度合格率 ④ 每节点产出非空且可追溯
- **现状**：真实模型 8 条走完到评审；19 条重写 2 轮仍未通过被停止。`pipeline.py` 里 8 组归一化别名处理说明——**模型输出结构长期不稳定，靠代码硬兜**。
- **关键问题**：长度口径没定。真实 77 条候选里 **19% 超过 20 字**，超长的恰好都是"据通报 + 主体 + 数字"这类**正确的归属表达**。这是 U-B06（长度 hard）与 U-S02（归属 conditional）的结构性冲突，不是模型不听话。

### S3 独立评审

- **输入**：候选 + 原始材料 + `boundary` + 规则切片 + 机械检查结果
- **输出**：G1–G3 + Q1–Q3 + `issues` + `rewrite_guidance`；G4 与总决策由程序做
- **验收目标**：① schema 校验通过率 ② 与人工金标准的一致率 ③ G1 误拦率 / 漏拦率 ④ 硬问题不被质量分抵消
- **现状**：结构 ✅（有 schema 校验、唯一语义裁判、程序唯一决策者）；**②③④ 从未测量**。

### S4 人工决策

- **输入**：`pending_human` 任务
- **输出**：`human_decisions` + `labels` + 状态流转
- **验收目标**：每条待审任务都有判定；判定与最终采用一致
- **现状**：37 条待审，**只判过 1 条视频的 mock 输出**。等于没验证。

### S5 案例记忆

- **输入**：人工判定 + 问题类型
- **输出**：`CaseRecord`（draft → confirmed）+ Memory 检索
- **验收目标**：确认的 case 能被检索命中、出现在 `used_case_ids`；同类问题下次改善
- **现状**：`cases=1`，`used_case_ids` 在真实运行中**从未出现过**。且 `config.rule_version` 默认 `temporary-v1`，与规则包版本从未对齐。

### S6 评测

- **输入**：固定样本 + 人工金标准 + 固定配置
- **输出**：一次通过率 / 人工一致率 / 长度合格率 / 返工率 / 单条调用成本
- **验收目标**：同一条命令跑两版规则/两版 Prompt，能给出对比表
- **现状**：❌ **完全不存在**。没有脚本、没有金标准、没有基线。这是所有"不知道往哪走"的根因。

### S7 界面 / 交付

- **现状**：单任务调试台（本机 8765，含候选卡、驳回原因分类、流程时间线、证据/规则/Prompt/事件）+ 任务报告 HTML + 设计稿 HTML + 2 张流程图。
- **判断**：已经超过这个阶段的需要。**冻结，不再投入。**

## 六处真实断裂（按严重度）

1. **没有版本控制**：34 个 `agent.db`、58 条任务散在 `runtime/`，没有任何标记说哪条是基线。无法回答"这版代码比上版好还是差"。
2. **G2 恒为 `needs_review`**：没有配置 `extra.business_policy`，所以任何任务在结构上**不可能**产出 `ready_for_human_review`。验收目标里"合格候选"目前没有落点。
3. **领域规则覆盖 38% 且体系错配**：62/100 样本拿不到领域规则，V01–V10 是按另一套领域划分写的。
4. **长度口径未定**：19% 真实候选超 20 字，超长的都是正确归属。是改长度、改归属、还是改交付标准，需要一次业务决策。
5. **人工闭环是空的**：37 条待审，0 条真实输出被判定。没有判定就没有金标准，没有金标准就没有质量。
6. **案例版本错位**：唯一的 case 记在 `temporary-v1` 下，检索时 `config.rule_version` 也是 `temporary-v1` 能命中，但语义上它来自旧规则——**能命中不等于该用**。

## 三个"假验收"

- `20 passed` —— 只证明结构正确，不证明生成或评审质量。
- `audit 100/100` —— 只证明文件在，不证明输入质量（`description/caption` 未核验）。
- `37 条 pending_human` —— 只证明跑得动，没证明有人认可过其中任何一条。

## 建议

### 主线判断

这个项目目前的形态是 **(a) 一个能证明"规则约束 + 独立评审"是否有效的实验**，不是 (b) 一个可交付业务使用的系统。你的时间（秋招中）和资源只支持 (a)。

如果是 (a)，**"做完"的定义不是界面和 100 条全跑，而是那张评测表**：在固定样本上能报出"一次通过率 / 人工一致率 / 长度合格率 / G1 漏拦率"，并且改规则前后能对比。在拿到这张表之前，所有规则改动都是盲改。

### 顺序：先立 S6，再回头改 S1 / S3

理由：你已经攒了 8 + 21 条可评审任务，评测的边际成本最低；而再改一轮规则，仍然无法判断好坏。

**第一步（约 10 分钟）时间轴**

```bash
git init && git add -A && git commit -m "baseline: 100 样本 + 9 节点链路"
mkdir -p runtime/runs && mv runtime/preliminary_* runtime/deepseek_* runtime/rulepack_* runtime/red_dot_run_001 runtime/runs/ 2>/dev/null
```

之后每次实验建一个 `runtime/runs/<日期>_<改了什么>/`，并在里面写一行 `README.txt` 说明意图。**一个 run 目录 = 一个可引用的事实。**

**第二步（约 30 分钟）让链路有终点**

写 `config.json` 的 `extra.business_policy`：`status: "approved"`、`version`、3–5 条 `rules`（`rule_id` + 触发条件 + 说明），覆盖你最在意的三类风险（性暗示 / 暴力猎奇 / 营销导流）。不做这一步，G2 永远 `needs_review`，"合格候选"这个概念在系统里不存在。

**第三步（约 1 小时）造 15 条金标准并算 4 个数字**

选 15 条覆盖 6 个领域 × 主要形态的样本，逐条自己判：`可用 / 不可用`，可用的话写出你认为的最终标题（20 字内，或放宽到 25 字并说明理由——**这就是长度口径决策**）。然后写 `eval.py`（约 50 行）：读任务库 + 金标准，输出

| 指标 | 含义 |
|---|---|
| 一次通过率 | 同一视频至少 1 条候选被人工判"可用"的比例 |
| 人工一致率 | 系统"推荐候选"与人工选择一致的比例 |
| 长度合格率 | 候选 ≤ 上限的比例 |
| G1 漏拦率 | 人工判"事实有问题"但系统 G1 pass 的比例 |

这 4 个数字出来，你第一次有资格说"这条链路到底行不行"，也第一次知道 S1/S3 该改哪。

### 之后（有数字再动）

- **P2**：按 taxonomy 的 6 个一级领域重写 V 规则，替换 V01–V10。现在 62% 样本无领域规则，这一层是空的。
- **P3**：拿第三步的 3 条"不可用"判定造 case，跑同一个视频验证 `used_case_ids` 命中——这是 Memory 闭环唯一一次真实验证。
- **P4**：把 `understand` 节点接上 `RuleBundle`（当前 handoff 论证的设计没落地，属于一致性问题，不是质量问题）。

### 现在不要做

- 界面（调试台已经够用；设计稿 HTML 冻结）
- 100 条全跑（15 条金标准够定位问题，全跑只是花额度）
- "理解/边界/看点要不要合并"的实验（这是调优题，不是当前阻塞）
- 联网核实能力（V1 不做，继续不做）
