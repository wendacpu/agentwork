## 原稿正文

### 1. 产品一句话定位

这是一套面向短视频推荐文案生产与审核场景的质量优化 Agent，主要解决模型生成质量不稳定、人工质量审核成本高、历史 Bad Case 难以有效复用的问题。通过多候选生成、多维打分评审、低分反馈重写及案例记忆机制，构建文案生成、质量评审、反馈优化的闭环，提高合格文案的产出率与人工审核效率，并通过历史案例复用持续改善生成质量，降低规则维护成本。

### 2. 目标用户是谁

- 目标用户：短视频推荐文案生产、质量审核及规则运营人员。
- 使用场景：推荐文案生成、质量审核、低质文案修复、Bad Case 巡检与规则迭代。
- 核心痛点：
  - 生成质量不稳定，规则难以覆盖复杂场景。现有模型主要依赖固定 Prompt 及通用生成规则，面对跨垂类内容、复杂视频看点和隐性表达规范时，容易反复产生事实不准确、看点不突出、吸引力不足等 Bad Case。
  - 审核失败直接驳回，缺少自动修复机制。原有链路以通过/驳回为主要审核结果，模型审核无法提供充分的问题定位及修改建议，导致部分内容供给损失。
  - 人工审核效率低：模型只承担基础合规性与表达规范性审核，标题质量判断仍依赖人工自行识别问题做出判断，难以充分利用模型辅助完成候选筛选和质量排序。
  - 规则维护成本高：原有规则迭代依赖人工抽检、问题归因、规则提炼及 Prompt 更新，周期较长。历史 Bad Case 复用不足，使得相似质量问题反复出现，模型难以及时利用历史经验改善生成结果。

### 3. 原来的业务链路

原链路：

标题生成：

视频信息提取 → Prompt 规则约束 → 模型生成标题 → 模型基础审核 → 人工质量审核 → 通过/驳回

其中，审核不通过的文案直接作废，不进入自动重写流程。

规则迭代：

人工抽样巡检 → Bad Case 识别 → 问题分类与归因 → 运营提炼规则 → 小流量测试 → Prompt 更新 → 后续生成验证

改造后的 Agent链路：

主链路：

【视频信息输入】→【看点抽取】→【规则约束与 Memory 检索】→【生成 3 版候选文案（生成 Agent）】→【多维评分与问题归因（评审 Agent）】

- 至少 1 条达标：保留所有合格候选 → 按评分择优推荐 1 条 → 展示推荐文案、评分及判断理由 → 人工校对确认。
  - 人工通过：采用该文案，进入推荐链路。
  - 人工驳回：记录驳回原因，优先检查其他合格候选；必要时触发定向重写或终止任务。
- 3 条全部不达标：根据评审反馈，选择可修复候选 → 生成 Agent 定向重写 → 评审 Agent 再次评分。
  - 最多额外重写 2 轮。
  - 任一轮出现达标文案：停止自动重写 → 择优推荐 → 人工校对确认。
  - 2 轮后仍不达标：停止自动生成 → 驳回或转人工异常处理。

规则反馈链路：

【人工识别 Badcase】→【问题类型与原因标注】→【结构化Case】→【人工确认入库】→【Memory 更新】→【后续生成复用】

- 规则型 Case：特定垂类或表达场景下的常见错误与正确约束。
- 事实型 Case：视频信息理解错误、主体混淆、结果虚构等问题及修正依据。
- 表达型 Case：吸引力不足、信息密度低、表达不自然等问题及优质改写示例。

### 4. 最终目标

1. 质量目标：提升文案生成质量和评审准确度
   1. 生成质量：在200 条公开短视频样本上，任务级首轮成功率由 52% 提升至 78%。
   2. 评审准确度：Agent放行文案的准确率由84% 提升至95%，合格文案召回率由 70% 提升至90%。同时监测错误放行率、错误拦截率、评分一致性和问题归因准确性。
   3. 重写效果：
      - 重写挽救率：首轮全部失败、经重写后至少产出 1 条合格文案的任务占比。
      - 重写质量改善率：比较重写前后候选的人工质量评价。
      - 历史 Bad Case 复发率：验证 Memory 是否减少相似错误再次出现。
2. 效率目标：减少人工判断成本，提高合格文案产出效率
   1. 降低单条最终合格文案的平均生产耗时与综合成本。
   2. 提升系统首推文案的人工接受率。
   3. 降低单任务人工审核耗时，减少人工逐条筛选与问题定位工作。
   4. 利用结构化人工反馈，降低后续案例整理与规则维护成本。
   5. 后续：在评审准确性、错误放行风险及业务灰度结果达到要求后，逐步探索低风险文案的自动放行机制。
3. 业务目标：
   1. 有效供给提升：提高每批视频任务中能够产出合格文案的比例，减少因生成质量不足造成的文案作废。
   2. 内容质量提升：减少事实错误、标题与视频内容不匹配、过度吸引等问题，降低用户点击后的预期落差。
   3. 推荐消费提升：后续通过线上 A/B 实验验证入口 CTR、UCTR、点击后人均观看时长及其他消费质量指标的变化。

### 5. 为什么选择 Agent而非 workflow

#### 1. 视频理解与质量判断具有较强的语义复杂性，难以通过固定规则穷举。

短视频推荐文案需要综合标题、OCR、Caption 等信息，识别视频主体、核心事件、结果与看点，同时判断表达是否具有吸引力、是否符合事实。

同一个视频可能同时涉及多个内容垂类，需要综合适用不同的标题撰写要求。传统规则引擎能够处理禁用词、字符长度等确定性问题，但难以完成复杂语义理解、看点提炼及主观质量评估。

#### 2. 文案质量优化需要基于反馈进行动态调整。

传统 Workflow 主要按照预设流程生成并审核文案，审核失败通常意味着拦截或人工处理。

本方案引入生成 Agent 与评审 Agent 的协作：评审 Agent 不仅判断是否通过，还输出具体扣分原因和修改建议；生成 Agent 根据反馈进行针对性重写，形成有限轮次的动态优化过程。

同时，系统检索人工确认的历史案例，为后续生成提供参考，减少对人工持续补充细粒度规则的依赖。

#### 3. 为什么现在做？

现有大模型已具备较强的文本理解、结构化输出和指令遵循能力，为看点提取、多维质量评审及反馈重写提供了实现基础。

但本项目尚未验证具体模型在该任务上的能力与成本拐点。因此，第一阶段将通过独立人工评测、模型调用成本和处理延迟测试，判断双 Agent 方案是否达到实际业务可用标准。

#### Agent 的使用边界

并非所有节点都需要 Agent：

- 基础规则校验：禁用词、长度限制、必要字段等确定性判断采用程序规则。
- 质量路由：根据评分、硬性门槛和重试次数执行固定条件分支。
- Memory 检索：使用结构化标签及相似度检索，不需要独立 Agent 决策。
- Case 入库：通过结构化数据处理和人工确认实现，避免未经验证的模型判断直接污染案例库。

生成与评审环节使用大模型处理复杂语义判断及反馈优化，其余环节优先采用确定性 Workflow，以控制成本、延迟和系统不确定性。

需要明确两条边界：

生成 Agent 不决定最终放行；它只能根据评审反馈修改文案。评审 Agent 不修改文案；它只负责判断质量、给出理由，并将结果交给确定性的路由程序。

这样可以减少双 Agent 的职责重叠和自我验证风险。
