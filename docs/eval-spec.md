### 1.4 长度合格率：重新定位
你说得对：生成时已约束 ≤20 字，它是**硬门槛**，不是质量指标，正常就是 100%。所以：
- **不要把它当「质量」报**，要当 **G4 硬约束执行率**（= 1 − 超长流入率）：
  - 只统计**系统最终交付**给人工的候选（handoff / needs_review），**不统计中间候选**——中间候选超长被 G4 拦下进重写，是正常流程，不算缺陷。
  - 一旦 < 100%，说明有超长标题**穿过 G4 漏到了交付层**——这是 P2 防线漏洞，不是「生成质量不好」。
- 建议改名 **超长流入率**，只在 > 0 时报警。

### 1.5 重写挽救率：两个口径
你问的 (a) vs (b)，答案是 **a + 一个前提**：
- **(a) 系统内 Agent 自动重写（R02）**：R01 评审发现 issue → R02 定向重写 → 再评审。这是**系统能力指标**，也是立项口径。
- **(b) 你人工给修改意见 → 重写**：这是「改系统 / 改规则后重测」，不是同一条任务的重写，**不计入重写挽救率**。
- 立项口径「重写挽救率」= **首轮全部失败、经自动重写后至少产出 1 条合格文案的任务占比**（任务级）。
- 需要的数据：同一任务「重写前候选判定」+「重写后候选判定」两套金标准。
- eval.py 现在算的 rewrite_outcomes（issue 是否被修掉）是**轮次级中间代理**，不等于任务级挽救率，先当临时指标用。

## 2. 金标准判法

### 2.1 三档 + 锚点（不变）
| 判定 | 标准 | 锚点判据 |
|---|---|---|
| 可用 | 准确、清楚，能兑现视频主要内容 | 不用改一处 |
| 勉强通过 | 基本可用但有明确瑕疵，必须写出瑕疵 | 只差局部一处，**改完读者预期不变** |
| 不可用 | 不能用；写出读者可能误解之处 | 要换看点/补事实/改方向，**改完读者预期会变** |

分歧高发在「勉强 vs 不可用」：问「改这一处后，读者对视频的预期会不会变？」会变 → 不可用。

### 2.2 标注方案：人 + 强模型双标注
你一人标注 → 引入一个参数更大、懂评测的模型做**第二标注者**：
- **主标注（金标准）**：你。
- **副标注（模型）**：deepseek-v4-pro（或同级），对同一候选独立判三档 + 一句理由，**不看你的判定**。
- 用途：
  1. **算 kappa**（人-模型一致性）：< 0.6 → 先对齐锚点样例，再扩样本。
  2. **扩样本**：模型标注可覆盖更多候选，但只有你的判定是金标准。
- 注意：模型不能替代你；它是「第二标注者 + 缩放器」，不是裁判。

### 2.3 字段 + 坑
gold.csv 14 列：video_id / **task_id（必填，防错配）** / candidate_id / 标题 / 系统路由 / 系统推荐 / 人工判定 / 人工最终标题 / 命中判据 ID / 回退节点 / 一句话理由 / 判定人 / 判定日期 / 驳回原因。

四个坑：① task_id 必填，否则跨版本错配（eval.py 报 ambiguous）；② mock 样本剔除；③ 双标注才算得出 kappa；④ 判据 ID 可选但决定归因。

## 4. 跑顺标准（验收）
「跑顺」= 同时满足这 5 条：
1. eval_manifest.json 20 条落盘，每条有 video_id + task_id + 领域/形态；
2. python scripts/eval.py 对 20 条能出数，**不报 ambiguous / missing**；
3. 人 + 模型双标注跑一轮，**kappa 可算**（≥ 2 条可比）；
4. **基线 pipeline** 跑同一批 20 条，出对比表；
5. 报告带版本号，**同一版本跑两次结果一致**（可复现）。
