# 与参考项目的差距：一个"完整 Agent 项目"该有什么

> 标尺：`docs/_ref/懂车帝复杂 agent 产品.md`（下称"参考文档"）+ 你给的五种能力分层与 Harness 六问。
> 对照对象：本仓库当前状态，依据见 [status.md](status.md)（58 条任务、34 个库、20 个测试的实测结论）。

## 先说结论

参考文档的价值不在架构——它的架构比你的粗。它的价值在于**证据链**：

> 可量化目标 → 50 条业务用例（含验收线）→ 多模型横评 → shadow → AB 增量归因 → bad case 看板 → 修复到模块

**你的代码比它细**（有 prompt 哈希、checkpoint、schema 校验、独立评审、断点续跑），但你缺的正是这条证据链。所以差距不是"工程能力差一截"，而是**你做的是系统，它交的是证明**。

这一句话决定补法：不需要再写节点，需要开始产出证据。

## 二、三个结构性认知缺口（最贵的三个）

### 缺口 1：没有"坏标题定义表" ← 等于没有长难车定义

参考文档最扎实的一段是：

| 核心指标 | 定义 | 业务含义 |
|---|---|---|
| 绝对库龄 | 入库到现在的天数 | 资金占用与贬值 |
| 相对库龄 | 高于同车型均值 30% | 排除车型天然慢周转 |

它把"这辆车有问题"变成**可计算、可对齐、可争论**的东西。你的项目里对应物应该是"这条标题不可用"，现在是：

- 有 G1–G4 四个 Gate，但每个 Gate 的**触发条件和阈值**散在 Prompt 自然语言里；
- 有 Q1–Q3 三维打分，但没有"多少分以下算不合格"的定论（`quality_min_each=2` 是个临时值）；
- 于是**两个人看同一条标题会给出不同结论**，人工一致率永远测不出来。

这就是为什么你现在不敢做金标准——不是懒，是没有判据。

### 缺口 2：没有用例表 ← 等于没有 50 条 TC

参考文档的 TC 表有个硬结构：`ID | 测试目标 | 输入 | 期望输出/验收标准`。它同时承担三件事：验收、回归、沟通。

你有 20 个测试，全是 `assertEqual(state["rules"]["rule_ids"], [...])` 这类结构断言。它们永远不可能告诉你"这条标题该不该放行"。

### 缺口 3：没有归因路径 ← 等于没有漏斗矩阵

参考文档的图（`_ref/图片和附件/image.png`）左边是行为路径、右边是干预渠道，箭头标的是"这个渠道作用于哪一层"。它的作用是：指标掉在哪一层，就知道该查哪个模块。

你的对应物应该是：

```
一条候选被判不可用
  ├─ G4 机械失败 → N10 代码（bug 或口径）
  ├─ G1 失败 → N05 边界（判错）还是 N09 生成（写超了）？
  ├─ G3 失败 → N07 看点（选错主看点）还是 N09（承诺过头）？
  ├─ Q 分低  → N09 表达（改 prompt / 换策略）
  └─ 无法归因 → 说明日志缺字段
```

你现在有数据支持这条路径（`issues[].primary_dimension` + `evidence_ids` + `candidate.claim_ids`），但**没有把它画出来，也没有按它统计**。这是最便宜的一次性投入。

## 四、两件不要学参考文档的事

1. **不要做"真 Agent"**。参考文档的 plan agent 让模型自己规划动作组合（加曝光/补资料/暂缓）。你的场景里路径是可穷举的 5 步，让模型自己规划只会增加不可控性。你已经克制了，保持。
2. **不要在没有下游指标时硬造 AB**。参考文档的 AB 成立是因为有 CTR/线索/毛利。你离线拿不到点击数据，所以"一次通过率 + 人工一致率"是**替代指标**，不是同一个东西——这个必须在文档里写死，否则面试被问"你怎么知道标题变好会提升 CTR"会答不上来。
