## 先说结论（早期分析）

参考文档的价值不在架构——它的架构比你的粗。它的价值在于**证据链**：

> 可量化目标 → 50 条业务用例（含验收线）→ 多模型横评 → shadow → AB 增量归因 → bad case 看板 → 修复到模块

**早期分析认为代码工程化程度较细**（prompt 哈希、checkpoint、schema 校验、独立评审、断点续跑），但当时证据链薄弱。当前仍需以最新人工样本与可复现评测验证质量；下文关于历史缺口的判断，不应直接当成现状。

这句话概括的是早期建议方向：在流程结构已有基础后，应优先建立可复核的质量证据；不应据此认为当前无需补节点或已经具备充分证据。

## 二、三个结构性认知缺口（最贵的三个）

### 缺口 1：当时缺少"坏标题定义表"（历史判断，判据现已存在）

参考文档最扎实的一段是：

| 核心指标 | 定义 | 业务含义 |
|---|---|---|
| 绝对库龄 | 入库到现在的天数 | 资金占用与贬值 |
| 相对库龄 | 高于同车型均值 30% | 排除车型天然慢周转 |

它把"这辆车有问题"变成**可计算、可对齐、可争论**的东西。早期分析时认为项目里缺少统一的"这条标题不可用"判据；现有判据表已建立，但实现与校准情况需分开看：

- 当前已有 `templates/criteria.csv` 与人工锚点；它们定义判据，但不等于代码逐条覆盖；
- 路由门槛由 `agent_system/rules/rubric.py` 的 `quality_min_each` 决定，值及其适用性应以当前实现复核；
- 人工一致率需要双人重复标注后统计，不能从规则表是否存在直接推断。

上述三点是早期问题的重述，不是当前测试结果。

### 缺口 2：早期分析认为业务用例覆盖不足（现存用例不等于覆盖参考项目的 50 条 TC）

参考文档的 TC 表有个硬结构：`ID | 测试目标 | 输入 | 期望输出/验收标准`。它同时承担三件事：验收、回归、沟通。

早期分析记录的自动化测试仅覆盖结构与接线，不能直接判断标题业务质量；当前测试数量与覆盖面应以重新运行测试及测试文件为准。

### 缺口 3：归因路径尚需验证是否有汇总视图（历史判断）

参考文档的图（`_ref/图片和附件/image.png`）左边是行为路径、右边是干预渠道，箭头标的是"这个渠道作用于哪一层"。它的作用是：指标掉在哪一层，就知道该查哪个模块。

你的对应物应该是：

```
一条候选被判不可用
  ├─ G4 机械失败 → N10 代码（bug 或口径）
  ├─ G1 失败 → N05 边界（判错）还是 N09 生成（写超了）？
  ├─ G3 失败 → N07 看点（选错主看点）还是 N09（承诺过头）？
  ├─ Q 分低  → N09 表达（改 prompt / 换策略）
  └─ 无法归因 → 说明日志缺字段
```

早期分析指出候选问题可通过 `issues[].primary_dimension`、`evidence_ids` 与 `candidate.claim_ids` 做归因；是否已有可视化或按维度统计，需检查当前报表实现，不能沿用旧结论。
