## 六项复盘

### 1. 是否有来回反复的流程？

有。测试依次经过 Mock 冒烟、DeepSeek 初跑、契约修复后重跑、单样本/最终检查、再次三样本运行。真实运行先暴露了 `candidate_claims`、高亮字段别名、评审分数结构等契约问题；修复后重跑有其必要性。但缺少 API 前的契约 fixture 和单节点小样，导致以完整模型链路发现、修复、再发现问题，等待和额度成本偏高。

两轮规则 Mock 冒烟结果分别只耗时约 0.1 秒，适合保留作快速回归；同一完整 DeepSeek 流程的多次全量重跑应改为“离线契约验证通过后，仅跑一个代表样本，再扩展样本集”。

### 2. 是否存在任务断点？

有。最终批次被 402 分成一条成功、两条未完成；失败状态落库，但没有从失败节点续跑的机制。首条完成后进入 `pending_human`，没有配置已批准业务政策，也没有接着执行人工复核，所以准入和反馈闭环没有完成。阶段间依赖上下文继续排查，运行目录和结论也分散在多份数据库中。

### 3. 日志记录是否完整？

不完整。SQLite 记录了任务状态、输入快照、节点名称、模型请求成功/失败、输出、部分 usage 和 latency，足以还原部分数据流与失败位置；但未形成可复现的运行记录：

- 没有存储最终渲染的 system/user Prompt 或 Prompt 哈希。
- 没有绑定规则包/代码版本哈希和完整运行配置到每个任务。
- `model_reply` 有 latency，但规则匹配、归一化、校验、路由没有统一的节点开始/结束和耗时事件。
- 测试轮次分散在多个数据库，缺少一个汇总 manifest；日志也没有统一标记“预期失败/中止批次”。

输入与模型输出保存在本地数据库，复盘时应按受控调试数据处理；凭据不得写入日志。

### 4. 哪里存在没必要但反复测试？

同一新闻样本在初跑、重跑、最终检查和验证批次中被重复执行；瑜伽样本也在多轮批次出现。契约缺陷修复后的新闻回归是合理的，但在没有离线 schema fixture 的情况下重复花模型调用验证解析逻辑，性价比低。HTTP 402 后再次重试同一任务也属于无效调用，应将额度错误标记为不可重试并停止批次。

### 5. 哪里没有执行？

- 最终三条样本中，只有新闻完整跑到评审；瑜伽和跑鞋都没有形成可评审结果。
- 本轮没有完成 `needs_review` 后的人工决策、批准政策下的发布准入，也没有验证重写分支。
- 没有覆盖模型恢复、任务续跑或单节点重放。
- 没有从人工反馈创建并确认可检索案例。

### 6. Case 沉淀机制做好了吗？

**机制有骨架，沉淀闭环没有完成。** 代码中已有 `cases` 表、草稿/确认操作、按规则版本和范围检索的 `MemoryStore`，CLI 也能创建案例；但本轮所有 smoke 数据库的 `cases`、`human_decisions`、`labels` 都为 0。最终新闻任务仍在 `pending_human`，没有人审结论可沉淀。因此尚未验证“人工判定 → 标签/Case 草稿 → 确认 → 下次检索 → 生成引用案例”的闭环，也不能说案例机制已做好。

## 改进顺序

1. **先补可复现日志**：为每次 run 生成统一 `run_id` 和 manifest，记录输入摘要、Prompt 哈希/版本、规则版本/哈希、模型名、非敏感运行配置、每节点开始结束时间、重试原因与耗时；保留失败节点的结构化状态。
2. **补离线契约回归与节点续跑**：用真实模型曾返回的 JSON 形状制作 fixture，覆盖各节点归一化、校验和路由；失败从最后成功节点续跑，避免重新调用已成功节点。
3. **调整真实模型测试顺序**：本地契约和规则测试通过后先跑一个代表样本；确认链路及成本再跑类型不同的样本。遇到 402 立即停止后续批次。
4. **完成 Case 闭环验证**：对 `pending_human` 保存明确人工决策；将可复用错误沉淀为 draft case，经确认后检索回归，并验证版本/范围过滤和 `used_case_ids` 追踪。

## 本轮修复落地

- 每个模型节点现在记录 `node_started`、Prompt/用户输入快照、模型回复或错误、`node_completed`/`node_failed`；同时保存请求指纹、Prompt 哈希、模型名、模型耗时和尝试次数。

- HTTP 400/401/402/403/404/422 作为不可重试错误；CLI 批处理在不可重试故障处停止，避免同一额度错误继续发请求。
