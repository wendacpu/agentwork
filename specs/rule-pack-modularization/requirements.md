# 规则包拆分与模块化需求

## 简介

将当前混合存放通用规则、领域规则、形态规则和流程说明的单一 Markdown 规则包，重构为清晰的规则源文件与可测试的模块化加载器。保留通用规则作为共享层；领域规则和形态规则分别存放、分别读取。清理不属于可执行规则的冗余说明，但不改变现有规则语义或命中结果。

在拆分前，先修正规则设计中实际存在的问题：约束等级混用、事实/断言/信源属性不正交、标题完整性被错误绑定到单一信息链，以及 Gate 与质量维度的职责重叠。当前链路已只有一个语义评审节点和程序机械检查，不增加语义预检节点；G1–G4/Q1–Q3、程序决策与人工最终确认的基本结构保留。

## 需求

### 需求 1：分离规则内容

**用户故事：** 作为维护者，我希望领域规则和内容形态规则分别在独立 Markdown 文件中维护，以便单独查找、修改和审阅。

#### 验收标准

1. 当维护者浏览规则源文件时，系统应将通用规则、领域规则、内容形态规则分别组织，领域与形态规则不得继续混放在同一规则文档中。
2. 当加载特定视频的规则时，系统应分别读取通用规则、匹配到的领域规则和匹配到的形态规则，并保留规则 ID、版本、匹配原因、缺失项和冲突信息。
3. 当规则迁移到新文件时，系统应保持现有样本的规则 ID 与适用范围；除明确修复的问题外，不改变规则本身的含义。

### 需求 2：清理冗余说明

**用户故事：** 作为维护者，我希望规则文档只保留规则本身及必要的维护说明，以减少无关信息对检索和模型上下文的干扰。

#### 验收标准

1. 当整理规则文档时，系统应移除与规则执行无关的流程叙述、重复说明和类似“如何放弃现有流程”的内容。
2. 当删除说明性内容时，系统应保留规则 ID、适用条件、行动要求、必要示例及规则之间的约束关系。

### 需求 3：模块化规则加载

**用户故事：** 作为开发者，我希望规则按模块选择和加载，而不是每次从一个大型 Markdown 文件解析全部内容。

#### 验收标准

1. 当加载规则时，系统应通过独立的领域与形态模块读取规则，并只将本次匹配的规则内容传递给对应节点。
2. 当领域或形态没有匹配项时，系统应明确记录规则缺口，不得静默加载无关规则或丢弃诊断信息。
3. 当规则模块或解析失败时，系统应返回可定位的错误信息，指出规则文件或规则 ID。

### 需求 4：兼容现有链路并可验证

**用户故事：** 作为维护者，我希望拆分后现有生成链路仍能正确获得规则上下文，并能用自动化检查发现规则路由回归。

#### 验收标准

1. 当 pipeline 请求规则上下文时，系统应继续提供生成、边界、看点和评审节点当前依赖的结构化字段。
2. 当运行现有规则路由样例时，系统应保持预期的规则 ID 与匹配 trace；例如资讯时事社会、资讯播报仍匹配 `U + V04 + F11`。
3. 当运行规则加载与 pipeline 测试时，系统应验证拆分文件可解析、规则路由稳定、缺失规则可诊断。

### 需求 5：校正规则层级与事实模型

**用户故事：** 作为标题规则维护者，我希望每条规则明确是不可妥协约束、条件性要求还是表达偏好，并分别记录事实支持、来源身份、传播路径、时间状态与允许的断言方式。

#### 验收标准

1. 当生成提示词同时面对长度约束与内容优化目标时，系统应按明确优先级处理，并将哪些字段可省略、哪些触发时必须保留写清楚。
2. 当理解或边界节点输出事实时，系统应分别表示 claim 类型、证据状态、原始信源、传播路径、时间状态和允许的断言强度，不得用一个枚举混合多条分类轴。
3. 当标题由教程、展示、观点、故事、资讯等不同形态构成时，系统应按能否独立理解和兑现观看承诺判断信息充分性，不得把“主体+动作+结果”作为所有标题的硬门槛。
4. 当材料存在事件主体、受影响对象、信源、转述者或地点时，系统应按实体角色判断标题是否需要保留，不能将所有具体名称统一当作事件主体。

### 需求 6：统一评审职责与路由

**用户故事：** 作为评审流程维护者，我希望每个 Gate 和质量维度有互不重复的职责，并由唯一的节点与程序阶段作出相应判断。

#### 验收标准

1. 当评审标题时，系统应将事实与断言许可、业务政策、内容交付、机械约束分别归到清晰的 Gate，并将清晰度、信息价值、吸引力分别评分；每个问题只能有一个 primary_dimension。
2. 当生成、预检和评审处理候选时，系统应只允许一个语义评审节点作质量裁决；机械预检由程序执行，生成与重写节点不得输出自评或通过状态。
3. 当汇总评审结果时，系统应继续采用单一 1–3 分制、统一 Gate 状态和程序化决策；`ready_for_human_review` 只表示转人工确认，不表示已发布。
